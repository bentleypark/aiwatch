# Fallback Tier Priority — Full Reference

> Extracted from CLAUDE.md to keep the auto-loaded project file lean. CLAUDE.md links here; this is the canonical reference.

- **Fallback tier priority**: same-tier services are recommended first, then adjacent tiers by distance. Within each tier, sorted by AIWatch Score descending. **#859 exception — specialized non-LLM API sub-tiers don't bleed cross-tier**: `getFallbacks` fills the top-2 by tier distance, which is right for the LLM tiers (1 Major LLM / 2 LLM / 3 Infra-router — any LLM API substitutes another) but wrong for the specialized sub-tiers, where the 2nd slot would leak into an unrelated adjacent tier (a degraded **Vector** DB was offered an **Image** model; **Image**→**Observability**; **Video**→**Observability**). So for a source whose tier is a **specialized sub-tier — Voice (4) / Video (5) / Observability (6) / Image (7) / Vector (8)**, i.e. `isSpecializedSubTier(tier)` = `tier ∈ [4,10]` — candidates are restricted to the **same tier only** (show 1 relevant sibling rather than 1 relevant + 1 nonsensical). LLM tiers 1-3 keep cross-tier fill; the coding-agent (11) and app (21) tiers are separate categories (filtered by `category`) and keep cross-tier fill within their category. Mirrored across all three copies (`worker/src/fallback.ts` `isSpecializedSubTier`, `src/utils/constants.js`, `api/is-down.ts` inline range check). Defined in `worker/src/fallback.ts`, mirrored in `src/utils/constants.js` (frontend) and `api/is-down.ts` (Edge SSR inline). `TIER_LABEL` lives in the same two files; `src/pages/Overview.jsx` imports it (no inline copy). All call sites use `tierFor(id)` / `tierLabelFor(tier)` helpers that warn once per missing entry — the bare `?? 99` lookup pattern was removed in #403 because it silently coalesced typos and forgotten service additions into Score-only ordering (the failure mode that produced the Junie-as-#1 bug, #402). Cross-mirror drift is pinned by `worker/src/__tests__/api-tier-sync.test.ts` — deep-equal assertion across worker ↔ frontend constants plus a string-match check that every canonical key appears in the `api/is-down.ts` inline literal. API tiers (1-8) and the coding-agent tier (11) use distinct number ranges so a single `TIER_LABEL` map stays unambiguous, and `getFallbacks` already filters by category so the two ranges never compare against each other:
  - **Tier 1** (Major LLM): `claude`, `openai`, `gemini`
  - **Tier 2** (LLM): `mistral`, `cohere`, `groq`, `together`, `fireworks`, `cerebras`, `deepseek`, `xai`, `perplexity`
  - **Tier 3** (Infrastructure): `bedrock`, `azureopenai`, `openrouter`
  - **Tier 4** (Voice): `elevenlabs`, `assemblyai`, `deepgram`
  - **Tier 5** (Video): `runway`, `luma` — generative-video AI. Given a dedicated tier (#602 / #601 step B) so a degraded video service recommends its video sibling (distance 0) first, instead of a higher-Score tier-3 infra/LLM-router service. Before step B, Runway↔Luma sat in tier 3 and a degraded Runway was offered `openrouter` (an LLM router), not Luma.
  - **Tier 6** (Observability): `langsmith`, `helicone`, `langfuse` — LLM observability/eval. Dedicated tier (#601 step B) so these recommend each other; `langsmith` un-excluded from `EXCLUDE_FALLBACK` once the category reached ≥2 members.
  - **Tier 7** (Image): `stability`, `bfl` — image-generation AI (#756 / #601 step B). Dedicated tier so a degraded image service recommends its image sibling (distance 0) first, instead of a higher-Score LLM/voice/infra service. Both `stability` and `bfl` un-excluded from `EXCLUDE_FALLBACK` once the category reached ≥2 members.
  - **Tier 8** (Vector): `pinecone`, `turbopuffer` — vector-search databases (#857 / #601 step B). Dedicated tier so a degraded vector DB recommends its vector sibling (distance 0) first, instead of a higher-Score LLM/voice/image/infra service. `pinecone` un-excluded from `EXCLUDE_FALLBACK` once the category reached ≥2 members (`turbopuffer` fallback-eligible from the start). NB `turbopuffer` has no official uptime (region-only status page, no `statusComponentId`) so its Score is probe-based — `medium` confidence once ≥7d of probe samples accrue, `low`/withheld during the initial ramp. Either way it stays a valid fallback target (`getFallbacks` filters on status/incident, not Score/confidence).
  - **Tier 11** (`Coding Agent`): `claudecode`, `codex`, `cursor`, `windsurf`, `copilot`, `junie` — all six share tier 11 (#1027), so same-tier distance collapses to 0 across every pairing and ordering reduces to Score within the category. The label matches `CATEGORY_LABEL[agent]` (like tier 21 matches `CATEGORY_LABEL[app]`), so grouped output reads "Coding Agent: Claude Code (Score 90)".
  - **Tier 21** (`AI Apps`): `chatgpt`, `claudeai`, `characterai`, `deepseekapp` — all four share tier 21, so same-tier distance collapses to 0 across every pairing and ordering reduces to Score (identical to the pre-#403 `?? 99` fall-through, just without the warn-once noise). Entries exist only to suppress the `tierFor` warn-once that would otherwise fire when chatgpt/claudeai/deepseekapp surface as the affected service in a fallback flow (Character.AI is in `EXCLUDE_FALLBACK` so it never does). Label deliberately matches `CATEGORY_LABEL[app]` so `buildGroupedFallbackText` output reads identically pre/post-#403.
  - **#1027 — why the CLI/IDE/Plugin sub-tiers were collapsed.** The old agent tiers 11 (`CLI Agent`: claudecode/codex), 12 (`IDE Agent`: cursor/windsurf), 13 (`Plugin Agent`: copilot/junie) encoded a delivery-**FORM** axis. That axis no longer distinguishes agents: each of the six now ships more than one form — every one has both a CLI and an IDE/editor surface (Claude Code and Codex, once terminal-first, both added IDE/editor integrations; Cursor and Windsurf, once editor-only, both added CLIs; Copilot and Junie, once IDE plugins, both added CLIs). A single-form label was therefore inaccurate and the IDE-vs-Plugin split was arbitrary. Unlike the LLM tiers (1-3, a still-valid capability axis), the form axis no longer distinguishes agents — and a capability ranking of agents is barred by the neutrality moat — so they fall back by Score within the category.
  - **#402 note (the re-exposed risk).** Pre-#402 the agent tiers were unset and every agent fell through to `?? 99`; the recommendation collapsed to a Score-only sort and Junie (new service, shallow incident history → inflated Score) showed up as #1 for unrelated outages. Collapsing back to one tier (#1027) restores Score-only ordering *within the agent category*, which **re-exposes that exact failure mode — there is no structural guard replacing the sub-tiers.** Note what does NOT protect the fallback path: the coverage gate (#802) is a rankings-page exclusion that `getFallbacks` never consults, and low-confidence withholding (#713) nulls a Score only when a service has neither official uptime nor a probe — every coding agent has official uptime, so its Score is always a real, non-null number no matter how shallow its incident history. Only a genuinely null Score sinks via `?? 0`. The mitigation is therefore **procedural**: verify after any agent addition that the new agent doesn't dominate the fallback slot on an unrelated outage. This is an accepted trade-off of #1027's design-A choice (Score-neutral ordering over a form axis that no longer discriminates).

- **#1062 — capability gating WITHIN a tier (Voice STT/TTS).** `isSpecializedSubTier` (#859) keeps a specialized sub-tier from bleeding *across* tiers, but assumed each sub-tier is internally substitutable. The **Voice tier (4) is not**: it mixes speech-to-text and text-to-speech, which do not substitute for each other. So a degraded **ElevenLabs (TTS)** was offered **AssemblyAI (STT)**, useless to a text-to-speech caller. `SERVICE_CAPABILITY` (`worker/src/fallback.ts`, mirrored in `src/utils/constants.js` + inline in `api/is-down.ts`) tags those three services by their **primary substitutable capability** (AIWatch's modelling, not a claim about each vendor's full API surface): `elevenlabs:['tts']`, `assemblyai:['stt']`, `deepgram:['stt','tts']`. `getFallbacks` additionally requires a candidate to **share ≥1 capability** with the source (`sharesCapability`). A service ABSENT from the map is not capability-gated (tier proximity alone governs it), so this narrows nothing outside Voice. When the only same-capability sibling is itself down the candidate set collapses to empty → **no recommendation** (route-else-suppress: suppress a wrong-capability peer rather than emit it). Cross-mirror guards (`api-tier-sync.test.ts` `SERVICE_CAPABILITY cross-mirror sync (#1062)`): the DATA map is deep-equalled across all three copies and the is-down filter **wiring** is regex-pinned; the frontend `getFallbacks` wiring is behaviorally pinned by `constants.test.js` (the worker by `fallback.test.ts`). This is facet A of #1062; facet B (below) routes a multi-capability service's sub-component outage to the right capability tier.
- **#1062 facet B — capability ROUTING for a multi-capability service's sub-component outage.** A service like OpenAI is worst-of'd across per-modality components (`Images`, `Audio`, `Embeddings`, `Realtime`, `Sora`, `Chat Completions`, …). When it goes non-operational because ONLY a secondary-capability component is degraded (e.g. `Images` down, `Chat Completions` still operational), recommending LLM peers is wrong — Claude has no image-generation API. `routingTier(svc)` reads `ServiceStatus.components[]` (#604): if the degraded set is exactly one secondary capability it returns that capability's fallback tier via `CAPABILITY_TIER` (`image→7` Stability/FLUX, `video→5` Runway/Luma, `audio→4` Voice); `getFallbacks` then draws candidates from that tier instead of the source's. **NB the routed audio path is NOT STT/TTS-gated** — facet A's `sharesCapability` only filters when both source and candidate are tagged, and the routed source (OpenAI) is untagged, so all Voice services are eligible. That is correct: OpenAI's `Audio` component spans Whisper (STT) + TTS, so the whole Voice tier is a valid substitute. A capability with **no `CAPABILITY_TIER` entry** returns a suppress sentinel → **no recommendation**: `realtime` (no monitored peer) and `embeddings` (no embeddings tier exists — Voyage is both `EXCLUDE_FALLBACK`'d and untiered; #880 would add the sibling, the tier, and the entry). It returns **null (default, unchanged LLM-peer behavior)** when the primary `llm` surface is among the degraded (whole-API outage), when there is no `components[]` signal or none is non-operational (Mistral's single-`API` Nuxt page — covered automatically once #761 gives it components), or when **≥2 distinct** secondary capabilities are degraded (ambiguous — don't guess). Component name → capability is a first-match keyword map (`COMPONENT_CAPABILITY`: `/image/`, `/\b(sora|video)\b/`, `/audio|speech|voice|transcri/`, `/embed/`, `/realtime/`; anything unmatched is `llm`) — coupled to today's status-page names + list order, failing SAFE (an unmatched rename → `llm` → default, never a wrong reroute). `getGroupedFallbacks` labels a routed group by the affected **CAPABILITY** (`CAPABILITY_LABEL`: `Image generation` / `Video generation` / `Audio / speech`, via `routedCapability`) so the recommendation **self-describes WHY it switched** — a routed OpenAI-`Images` outage reads `Image generation → Stability AI · FLUX`, not a bare `Image → …` (or the wrong `LLM → …`); the group also carries a `capability` field, and the is-down page names it in its `🔄 Alternatives for image generation` / `Alternatives for image generation when OpenAI API is Down` headings. It resolves candidates **before** reserving a group key, so a **suppressed** anchor never steals a later LLM sibling's group. Mirrored across all three copies; `api-tier-sync.test.ts` deep-equals `CAPABILITY_TIER` + `capabilityOfComponent` behavior worker↔frontend and source-pins the is-down inline (CAPABILITY_TIER data, each `COMPONENT_CAPABILITY` regex literal, the `routingTier` guards, and the `routingTier(target)` wiring); behavior is pinned by `fallback.test.ts` + `constants.test.js`.
- **#1062 facet C — the REVERSE: a dedicated capability service's outage also recommends the multimodal provider.** Facet B routes OpenAI-`Images` → the Image tier (Stability/FLUX); the symmetric direction was missing — a **Stability** (image) outage recommended only its same-tier sibling FLUX (`isSpecializedSubTier` #859 keeps the pool same-tier), never OpenAI's DALL·E, even though OpenAI provides image generation. `CAPABILITY_PROVIDERS` (`image`/`video`/`audio` → `['openai']`) lists the multimodal LLM services that provide a specialized capability **via a MONITORED component**, and `getFallbacks` widens a specialized sub-tier's candidate pool with `isCapabilityProvider(candidateId, sourceTier)`. Only **OpenAI** qualifies: its `Images`/`Sora`/`Audio` are monitored `statusComponentIds`, so its worst-of'd overall status is a **faithful health proxy** (an operational OpenAI has an operational image/video/audio component) — no per-capability check needed, and the normal `status === 'operational'` filter already drops a degraded OpenAI. **Gemini is deliberately excluded**: its Imagen/Veo are separate Vertex products AIWatch does not monitor (no `components[]`), so its status would not reflect their health. The tier-distance sort ranks the dedicated sibling first (FLUX, dist 0) then the provider (OpenAI, dist 6): `Stability down → [FLUX, OpenAI]`; `Stability + FLUX both down → [OpenAI]`. Tiers without a capability (observability 6 / vector 8) are not widened. `CAPABILITY_PROVIDERS` + `isCapabilityProvider` are mirrored across all three copies and pinned by `api-tier-sync.test.ts` (deep-equal + `isCapabilityProvider` agreement + is-down inline data + filter-wiring); behavior + a drop-the-clause mutation are pinned by `fallback.test.ts` + `constants.test.js`.
- **Candidate eligibility (#550)**: a fallback candidate must be *genuinely clean* — `status === 'operational'` **AND** no unresolved incident. The latter is `!(incidents ?? []).some(i => i.status !== 'resolved')`, i.e. any `investigating`/`identified`/`monitoring` incident disqualifies. Status alone is insufficient because a service can stay `operational` while carrying an active incident (the phase hasn't flipped its status, or the impact is minor) — without this rule the Overview banner recommended Codex as a Claude Code fallback while simultaneously listing Codex under "🔍 Investigating" on the same screen. The check is applied identically on all three surfaces (`getFallbacks` in `src/utils/constants.js` + `worker/src/fallback.ts` via a `hasActiveIncident` helper; inline in `api/is-down.ts`); `getGroupedFallbacks`'s `nonOperationalIds` guard mirrors it defensively. The three copies are independent (no shared module across frontend/worker/edge) and are NOT yet pinned by a sync test the way the tier maps are — keep the predicate in lockstep when editing.
- **Same-provider exclusion — REMOVED for parity (#554)**: the dashboard `getGroupedFallbacks` used to additionally drop any candidate sharing a provider with an affected service. This rule existed **only** there (never in `worker/src/fallback.ts` `buildGroupedFallbackText` or `api/is-down.ts`), so the dashboard and the Discord/is-down surfaces recommended **different** sets for the same incident — and it dropped an *operational* sibling (e.g. claude.ai for ChatGPT when only Claude Code was degraded), collapsing ChatGPT's app group to zero fallbacks. It was removed: a candidate's own live-status filter (#550, applied on all three surfaces) already catches the genuine correlated-failure case (the candidate itself is hit), so the provider rule was redundant there and harmful for the operational-sibling case. **All three surfaces now apply the same selection rule** (live-clean only); the dashboard's `perGroup` cap remains a display bound, not a selection difference. Pinned by parity-guard tests on both surfaces (`constants.test.js` `#554 …` + `fallback.test.ts` `#554 …`) — re-adding a provider exclusion to either surface breaks them.
- **Region-switch suppression, and what "switchable" means (#641 / #973)**: when an affected service has a *region-switch* recommendation, the cross-service fallback is suppressed on the same surface (`getGroupedFallbacksExcludingRegionSwitchable` in `src/utils/constants.js`, and `buildIncidentAlerts` skipping `fallbackText` when `buildRegionHint` returns text). Rationale: moving to a healthy region of the SAME provider is cheaper to execute than switching provider, so showing both is redundant noise. The suppression keys on `regionStatusOf().recommendedRegion` being non-null, which #973 narrowed: a `SERVICE_REGIONS` entry makes a service region-**aware** (we can say *which* region broke), but only membership in **`REGION_SWITCHABLE`** makes it region-**switchable** (the caller can move traffic). `openai` is aware-but-not-switchable — its region keys were copied from `services.ts` `incidentKeywords` (region names OpenAI cites in incident text), while the OpenAI API exposes no selectable region endpoint. Pre-#973 it therefore printed "Switch region: OpenAI API → US West (us-west-2)" *and* suppressed the Claude fallback — an unactionable instruction displacing an actionable one. Non-switchable services now get `recommendedRegion: null`, so all four consumers (Overview banner, ServiceDetails callout, is-down SSR line, Discord `buildRegionHint`) fall silent and the cross-service fallback returns. The per-region status list still renders: "us-east-1 is the one that's down" is useful even when you can't leave it.
