- Phase 3 AI Analysis (Beta): Hybrid AI auto-analysis on incidents — Gemma 4 26B via Workers AI binding (primary, zero API key, free tier) + Claude Sonnet via Cloudflare AI Gateway (fallback). Triggered by cron, stored in KV (`model` field tracks source), shown in Topbar Analyze modal + Is X Down AI Insight card. `ANTHROPIC_API_KEY` Worker secret required for Sonnet fallback. Recovery time "N/A" displayed as "Exceeded typical pattern" via `formatRecoveryDisplay()`. **Ongoing-past-estimate**: an ACTIVE incident whose elapsed time (now − startedAt) exceeds the estimate's upper bound no longer shows the stale short range (a 2–4h estimate on an incident ongoing for days) — it shows how long it's been running vs the estimate: "약 12시간째 진행 · 예측(2–4h) 초과" / "Ongoing ~12h · exceeded ~2–4h est." (shared `estimateExceeded`/`exceededRecoveryText` in `src/utils/predictionAccuracy.js`, mirrored EN-only in `api/_is-down/html-template.ts` `recoveryEstimateExceeded`/`exceededRecoveryTextEn` for the visible AI card; is-down meta/share keep the terse wording; parity mirrors the worker's `recoveryExceeded` gate). **#900 — graduated far-exceeded**: once elapsed > `FAR_EXCEEDED_FACTOR` (3) × the estimate's upper bound, the specific short range is DROPPED as noise (a 4–8h estimate keeps repeating on a 69h incident) → "약 69시간째 진행 · 예측 대폭 초과" / "Ongoing ~69h · far exceeded est."; mild overshoot (≤3×) keeps the range. The `FAR_EXCEEDED_FACTOR` const is defined in BOTH `predictionAccuracy.js` + `html-template.ts` and pinned equal by `is-down-render.test.ts`. Layer 2: `buildAnalysisPrompt`'s re-analysis `prevPredictionText` forbids an estimate whose upper bound is < elapsed hours (with an "N/A" escape hatch) so a re-run stops regenerating a sub-elapsed range — verify via `/api/status/cached` raw `estimatedRecovery` (Layer 1 hides it from the UI, so there's no in-app surface; a `verify-after` human ping tracks it).   - **Contextual fallback** (`needsFallback`): AI analysis includes a boolean flag assessing if an incident warrants switching to an alternative. Gating differs per surface (#454): the **AnalysisModal + Overview ActionBanner gate the Score-based fallback list on service status** (`down`/`degraded`) via `shouldShowFallback()` — NOT on `needsFallback` — because the AI classifies partial degradation as `needsFallback:false`, which previously hid the modal's recommendations for degraded incidents while Overview still showed them. The **Is X Down AI Insight card** (`api/_is-down/html-template.ts`) and **Discord alerts** still gate on `needsFallback`. Shared `getFallbacks()` / `shouldShowFallback()` utilities in `src/utils/constants.js` (used by AnalysisModal + Overview)
  - Grouped fallback: when an incident affects multiple categories, the dashboard/AnalysisModal (`getGroupedFallbacks`, `src/utils/constants.js`), the **Discord alert**, and the **RSS/Slack feed** all show per-category alternatives (LLM + App + Coding-Agent, not LLM-only). **#781**: the worker side (`worker/src/fallback.ts` `getGroupedFallbacks` → `buildGroupedFallbackText` for Discord; `rss.ts` `fallbackLine` for the feed) was wired to match — before #781 grouping shipped ONLY on the frontend and the worker alert/feed showed a flat top-2 of the PRIMARY service's category (so a multi-surface Anthropic incident wrongly recommended two LLMs, missing the App/Agent alts). perGroup mirrors the dashboard: 2 when single-category, 1 per category when multi.
  - **Fallback tier priority**: same-tier first, then adjacent tiers by distance, Score-descending within a tier. Defined in `worker/src/fallback.ts`, mirrored in `src/utils/constants.js` + `api/is-down.ts`; drift pinned by `worker/src/__tests__/api-tier-sync.test.ts`. Tier ranges: API **1** Major LLM / **2** LLM / **3** Infra / **4** Voice / **5** Video / **6** Observability / **7** Image / **8** Vector (#857 — `pinecone`+`turbopuffer`); agents **11** CLI / **12** IDE / **13** Plugin; apps **21**. **#859** — the adjacent-tier fill is capped for **specialized non-LLM API sub-tiers** (`isSpecializedSubTier`, tier ∈ [4,10] = Voice/Video/Observability/Image/Vector): those recommend their OWN tier only (no cross-tier bleed — an image model is not a vector-DB alternative), while LLM tiers 1-3 keep cross-tier fill. A candidate must be operational **AND** carry no unresolved RELIABILITY incident (#550 — a service can stay `operational` with an active investigating/identified/monitoring incident; recommending it would contradict the same screen's incident banner). **#811** — a non-reliability ADVISORY does NOT disqualify: `hasActiveIncident` ignores an incident whose title is a compliance/access-revocation-or-**suspension**/deprecation/scheduled-change advisory with no outage signal (shared `isNonReliabilityAdvisory` in `worker/src/utils.ts`, reused by aws.ts #707, mirrored in `constants.js`, parity-pinned). So a Claude model-access suspension (operational badge) no longer excludes Claude/Claude Code as fallbacks; a genuine outage-signal incident still does. Full tier membership, candidate eligibility, the `tierFor`/`tierLabelFor` warn-once rationale, and the #402/#403 (Junie-as-#1) history are in **[docs/reference/fallback-tiers.md](fallback-tiers.md)**.
  - `EXCLUDE_FALLBACK` services are excluded from both source and candidate lists (keep in sync across `worker/src/fallback.ts`, `src/utils/constants.js`, `api/is-down.ts`): `replicate`, `huggingface`, `fal`, `voyageai`, `modal`, `characterai`, `bedrock`, `azureopenai` (stability un-excluded in #756 — paired with `bfl` in the Tier 7 image sub-tier; **pinecone un-excluded in #857 — paired with `turbopuffer` in the Tier 8 vector sub-tier**)
  - **No-official-uptime services** (`bedrock`, `azureopenai` — incident feeds only, no rolling uptime%): **#713 — AIWatch invents NO uptime value** (the prior #653 `estimateUptimeFromIncidents` / `uptimeSource:'estimate'`, the #707 "No reliability incidents" wording, the 90-day uptime merge, and `score.ts`'s `assumedUptime` fallback were all removed). The worker leaves `uptime30d` null; the Score is computed on the **available components rescaled to 100** (`score.ts` — drop the 40-pt uptime component, no assumed value; `confidence` low when only incidents+recovery). Display/ranking via `serviceReliability.js` (mirrored in `api/is-down.ts`): `noOfficialUptime = uptime30d==null && !stale` → **"No official uptime — incident-tracked"** (`uptime.noOfficial`); `isUnreliableUptime = uptime30d==null || stale` blanks uptime + drops it from the Uptime ranking; `hasReliableScoreData = !stale && scoreConfidence !== 'low' && hasSufficientCoverage` gates the **Score** ranking — confidence `high` (official uptime) / `medium` (no uptime but a probe — Gemini/xAI/OpenRouter) stay ranked; for `low` (NEITHER uptime nor probe — Bedrock/Azure, would be scored on just 2 components → over-scores) the worker **emits a null `score`/`grade`** (withheld, not 0), so it's absent from the ranking AND the detail-page Score card (`score.ts` returns null when `confidence==='low'`). **#802** adds the **coverage gate**: `ServiceStatus.coverageDays` (from `ServiceConfig.addedAt` via `coverageDaysFrom` on the worker `base`; absent = established = full coverage) `< MIN_COVERAGE_DAYS` (30) holds a recently-added service OUT of the ranking (its incident/recovery/responsiveness components rest on a thin observed window → would rank off insufficient data) → routed to the "Insufficient Data" group, auto-rejoins at 30d. The detail Score CARD still shows the score with a "Building data (<30 days) — not yet ranked" note. **Stamp `addedAt` on every newly-added service** (adding-a-service checklist); old services are intentionally absent. is-down mirrors the coverage gate. **Cross-repo:** the monthly report ranking needs the same full-month-coverage gate (aiwatch-reports#45) — **#809** wired the signal it consumes by exposing the static per-service `addedAt` in the monthly archive (`/api/report`); #802 itself only added `coverageDays` to the LIVE `/api/status`, which is now-relative and wrong for a historical month. The Score CARD (detail + Overview) gates on `aiwatchScore != null && !incidentSourceStale` — NOT on `isUnreliableUptime` — so a probed no-uptime service (medium) shows its score on every surface it's ranked on; only the uptime% is blanked. `incidentSourceStale` (#591) is the separate frozen-feed case ("Not provided"). #713 also deleted the dead estimate helpers (`computeUptimeFromIncidents`/`resolveImpactWeight` in incident-io.ts, `readArchivedIncidentsForService` in monthly-archive.ts — no callers left). `/api/v1` `aiwatchScore`/`scoreGrade` are nullable + carry `scoreConfidence`. - Status polling proxy: `worker/` directory (monorepo), Cloudflare Workers
  - `cd worker && npm run dev` — local dev (wrangler default port 8787). For **dashboard** local-verify use `npm run dev:worker` (8788) instead — the SPA's default API URL + `VITE_API_URL` target 8788, so an 8787 worker leaves the dashboard on silent mock (#953)
  - **Worker deployment rules** (Workers Paid / Standard — 1M KV writes/month included; repeated deploys still reset per-isolate throttling, so minimize unnecessary redeploys to stay well inside the monthly allowance):
    1. During development → `npx wrangler dev --config worker/wrangler.toml --port 8788` (local test only, never deploy)
    2. Before deploy → `npx wrangler deploy --config worker/wrangler.toml --dry-run` (build check)
    3. Deploy → after commit + user approval, **once only** `npm run deploy:worker`
    4. No repeated deploys — each Worker deployment resets the isolate, resetting KV write throttle
  - **IMPORTANT**: Always use the npm script to deploy the worker — never run `wrangler deploy` or `cd worker && wrangler deploy` directly (both pick up the wrong config and deploy the SPA):
    ```
    npm run deploy:worker
    ```

- **Frontend deployment**: Vercel, domain ai-watch.dev — `git push origin main` triggers auto-deploy. `npm run build` is local only; changes are not live until pushed. **Hobby 12-Serverless-Function cap (#862/#867)**: Vercel builds every file under `api/` as its own Serverless Function, and a deployment may hold at most 12. A file is EXEMPT when it is `_`-prefixed (a helper, e.g. `api/_shared/…`) **or** declares `export const config = { runtime: 'edge' }`. Crossing 12 fails the deploy at `patchBuild` (`exceeded_serverless_functions_per_deployment`) **after** a green build — `tsc`, `vite build`, and unit tests all stay green and hide it. CI guard: `scripts/check-vercel-function-count.mjs` (via `npm run test:scripts`) replicates Vercel's counting rule and fails the PR before merge. This is why every `api/` handler is an Edge Function — the SSR pages (`is-down`, `intro`, `methodology`, `plugin`, `plugin-privacy`, `extension-privacy`, `badges`), the `confirm` opt-in endpoint, the `reports` proxy, and the `csp-report` violation sink alike — and why `/p/:slug` is a `vercel.json` `redirects` rule rather than a handler
- **CSP (#482)**: violations land at the `api/csp-report.ts` Edge sink (Vercel logs). **Edge SSR pages ENFORCE their own per-response CSP** (#823/#828/#829 + Phase-3 flip): each handler sets `Content-Security-Policy` itself, split by cacheability — **nonce** (`api/_shared/csp-nonce.ts`, `Cache-Control: no-store`) for low-traffic badges/methodology/intro, **content hash** (`api/_shared/csp-hash.ts` `cspForHtml`) for high-traffic **is-down** so it keeps its `s-maxage=60` edge cache (a content hash survives caching; a random nonce would be reused across all cached-page visitors). Every inline `on*=` handler was first refactored to a delegated listener. **The SPA also ENFORCES** via `vercel.json` `Content-Security-Policy` — `script-src` hash-locked to `index.html`'s two inline scripts (font preload→stylesheet swap, moved out of `<link onload/onerror>`, + the FOUC theme script; bundle is `'self'`, no eval/Worker/blob). Its header `source` is a **negative lookahead** excluding the Edge SSR surfaces + proxy routes (`reports`/`confirm`/`feed`/`api`) so each surface is gated by exactly one policy (no two enforcing policies intersect-block). Update the two `'sha256-…'` if those inline scripts change (pinned by `api/__tests__/csp-headers.test.ts`). **#482 complete — CSP enforces across SPA + all Edge SSR.** Full policy/rationale: **[docs/reference/reference-csp.md](reference-csp.md)** — read before changing the policy or adding an inline script/external origin

- **Monthly Reports proxy**: `api/reports.ts` — Vercel Edge Function that proxies `/reports/*` on `ai-watch.dev` to the aiwatch-reports Jekyll site (#264). Fetches directly from `bentleypark.github.io/aiwatch-reports/` rather than the public `reports.ai-watch.dev` subdomain so a Cloudflare Page Rule can 301 the public subdomain to `ai-watch.dev/reports/` without trapping the proxy in a redirect loop (proxy fetch and the 301'd public hostname must not share a hostname).
