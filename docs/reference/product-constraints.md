The `FAR_EXCEEDED_FACTOR` const is defined in BOTH `predictionAccuracy.js` + `html-template.ts` and pinned equal by `is-down-render.test.ts`. Layer 2: `buildAnalysisPrompt`'s re-analysis `prevPredictionText` forbids an estimate whose upper bound is < elapsed hours (with an "N/A" escape hatch) so a re-run stops regenerating a sub-elapsed range — verify via `/api/status/cached` raw `estimatedRecovery` (Layer 1 hides it from the UI, so there's no in-app surface; a `verify-after` human ping tracks it).   - Per-incident KV keys: `ai:analysis:{svcId}:{incId}` — each incident analyzed independently, supports multiple simultaneous incidents per service
  - TTL refresh: cron refreshes per-incident analysis keys every ~30min while incident is active
  - Re-analysis: re-triggers if expired/missing (max 2/cron, 30min cooldown on failure) + after 2h for long-running incidents (safe overwrite; timeline updates feed the prompt). Timeline-aware skip via stored `timelineHash` — skips when timeline unchanged or new entries are all boilerplate (`isBoilerplate()`)
  - **#1003 — re-analysis must never move the SCORING baseline.** Re-analysis fires only once an incident has outrun its own estimate, and its prompt forbids a new upper bound below the elapsed hours (the Layer-2 rule above), so `estimatedRecoveryHours` ratchets **up** with hindsight — on exactly the incidents the model got wrong. Grading recovery against it therefore inverted the verdict: Pinecone (first estimate `1–4h`, re-estimated `~15h` at the 4h mark, recovered at 4h 55m) shipped as `🎯 AI prediction: 4h 55m (faster than ~15h est.)` — a fabricated win — and wrote `15` into the durable corpus feeding both the accuracy aggregate and the RAG prompt grounding (self-poisoning). Fix: `AIAnalysisResult.firstEstimatedRecoveryHours` holds the first estimate, and **`putAnalysis` is the single chokepoint for every `ai:analysis:` write** (cron initial + time-based re-analysis + missing/lapsed-key + sibling-copy dedup + the recovery `resolvedAt` mark + `/api/admin/analyze`) — it pins the baseline in its own **durable `ai:first-est:{svcId}:{incId}` key** (write-once, 30d). The separate key is load-bearing: the 1h-TTL `ai:analysis:` key is deliberately allowed to LAPSE mid-incident (cap exhaustion stops its TTL refresh), and the replacement analysis would otherwise install its own hours-in estimate as "the first" — the same bug, one cycle later. Same for the sibling-copy path: copying the value byte-for-byte carried the baseline but pinned nothing, so a lapse on the *sibling's* key re-ran it one service over. A pre-#1003 prior donates its `estimatedRecoveryHours` (and self-heals into the durable key on the next write), so an incident in flight at deploy still scores honestly. **Two audiences, two values**: live surfaces (ongoing ETA, `recoveryExceeded`, `estimateExceeded`/`exceededRecoveryText`, the is-down active card) keep reading the CURRENT estimate — a user needs the live ETA, not the superseded original; every surface that SCORES predicted-vs-actual (Discord recovery embed, Slack `/feed`, `buildHistoryRecord` → corpus/accuracy/RAG, the SPA modal, **and the public `/is-*-down` resolved AI card**) reads the first one through the shared baseline helper: `scoringBaselineHours` (worker) / `baselineHoursFrom` (SPA) / `scoringBaselineEn` (Edge). `resolvedPredictionLine` takes the ANALYSIS rather than a bare number so the type checker enforces the baseline at each call site, and `first-estimate-write-paths.test.ts` **scans the worker source and fails CI on any analysis-key write outside `putAnalysis`** (both the inline and the via-a-variable form; the scanner is itself tested against synthetic offenders, since a vacuous guard is worse than none). **Caveat** — when the FIRST analysis produced no numeric estimate ("N/A"), the baseline is adopted from the next analysis that does produce one, which is made mid-incident and is therefore not strictly hindsight-free; the accuracy ledger cannot distinguish those records. **Forward-only** — records written before this carry the inflated value (the original was overwritten in KV and has expired; no backfill is possible)

- **PWA**: `public/manifest.json` + `public/sw.js` (stale-while-revalidate). **The cache name derives itself — there is nothing to bump by hand.** On `install` the SW fetches `/asset-manifest.json` and opens `'aiwatch-' + manifest.version`; the only literal is `FALLBACK_CACHE = 'aiwatch-static-v1'`, used when that fetch fails. `manifest.version` is not a semver string: `assetManifestPlugin` (`vite.config.js`) writes the first 8 hex chars of an md5 over the built `dist/assets/` **filename list**, and Vite content-hashes those filenames — so the cache name tracks the emitted bundle, byte for byte. Two consequences worth knowing, both measured: a `package.json` version bump *does* invalidate the cache, because `define.__APP_VERSION__` inlines the version into the bundle (rendered in e.g. `Sidebar.jsx` / `Topbar.jsx`) and therefore changes an asset hash — that define is the *only* path by which `pkg.version` reaches a built asset; and a source edit that survives minification identically (a stripped comment, say) produces the *same* cache name — correctly, since nothing shipped changed. (A `CACHE_NAME` constant and its manual-bump rule existed once; both are gone.) SW excludes `/is-*` (Edge SSR) and `/api/*` (real-time data) from caching. **Registered in production only** (`src/main.jsx` gates on `import.meta.env.PROD`); in dev the SW is proactively unregistered because its stale-while-revalidate cache serves previously-cached `/src/*` modules and masks source edits (#432). Verify SW behavior via `npm run build && npm run preview`, not `npm run dev`
