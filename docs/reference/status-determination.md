# Service Status Determination

> **Public mirror — keep in sync (#937):** the user-facing `/methodology` page §2 "STATUS DETERMINATION" cards (`api/_methodology/html-template.ts`, KO+EN i18n) restate these rules for visitors. When a rule below changes *user-visibly*, update those cards in the SAME commit. The `git-mutation-gate.sh` hook nudges when this file is staged without the page (the #934 drift this backstops).

Per-service status is resolved in `worker/src/services.ts` with this priority:

1. **Multi-component worst-of** (`statusComponentIds`, #379): when configured, look up each id in the page's `components`, normalize each, and pick the worst (`down` > `degraded` > `operational`). Used for coding agents whose user-facing surface spans multiple components — e.g. Cursor IDE primary + Cloud Agents + Automations + CLI; Claude Code component + Claude API dependency. `statusComponentId` (singular) remains the *primary* component for uptime parsing, calendar days, and component-miss alerting; `statusComponentIds` is purely for badge resolution. Convention: list the primary as the first entry of `statusComponentIds`. If none of the ids resolve in the components list, falls through to step 2.
1.5. **`displayAllComponents` dynamic worst-of** (#992): when `displayAllComponents` is set (and step 1 did **not** fire — a service with BOTH, e.g. BFL, keeps its curated `statusComponentIds` badge), the badge is the worst-of **every** page component minus `componentDenylist` names — mirroring the dynamic breakdown, so a new/churned model degrades the badge with NO config edit. Positioned AFTER step 1 and BEFORE step 2, so a dynamic service's uptime-primary `statusComponentId` (cerebras' Developer Console) does not pin the badge to that one component. cohere/groq have no `statusComponent*` → they return at step 4 (overall indicator) before reaching here. Falls back to overall if no component survives the denylist.
2. **Component match** (`statusComponentId` or `statusComponent`): use that component's status
3. **Component not found**: fall back to overall page indicator
4. **No component configured**: use overall indicator, BUT if no relevant unresolved incidents matched after `incidentExclude`/`incidentKeywords` filtering, treat as `operational` (prevents cross-contamination from unrelated incidents on shared status pages, e.g., ChatGPT incident should not affect OpenAI API status)
5. **`incidentExclude` component bypass** (#359): when an `incidentExclude` pattern matches the incident title, check if the incident's `componentNames` starts with `config.statusComponent` — if it does, include the incident anyway. Prevents "claude.ai and API unavailable" from being dropped from Claude API just because the title contains "claude.ai". Component tagging is more authoritative than title substring matching.
   - **#1032 — the same bypass on an ID axis, for `statusComponentIds`-scoped services.** The #359 branch is keyed on `config.statusComponent`, a component **NAME**, and a name is not always unique: `status.openai.com` carries **two components both literally named "Login"** — one in the APIs group (openai's badge) and one in the ChatGPT group (chatgpt's). On 2026-07-16 OpenAI opened `"Elevated Error Rates For SSO Login"` and tagged BOTH. openai's badge went `degraded` off its own API-group Login (multi-component worst-of, rule 1), while openai's `'login'` `incidentExclude` vetoed the incident by title — and the #359 bypass could not re-admit it, since openai sets no `statusComponent`. Result: **a `degraded` card with an empty incident list**, on the dashboard and on `/is-openai-down`. So when an incident's component ids intersect `config.statusComponentIds` (this service's own badge group), the exclude is bypassed: the provider tagging an incident onto a component WE badge is the provider asserting it affects us, and that outranks a title substring guess. The ids come from `Incident.componentIds`, tagged at the source by `attachIncidentIoComponentIds` from the page HTML's `component_impacts` (the incident.io JSON API returns `components: []` on every incident — see #1004 below); **absent ⇒ no bypass ⇒ pre-#1032 behaviour**, so a missing or shape-changed page fails CLOSED. Reachable only for a service with an exclude AND a badge group AND an incident.io page (the shared `canIdBypass` predicate, used by BOTH the fetch gate and the reader so the two cannot drift into a bypass that silently never fires) — openai/chatgpt/codex today; replaying all 25 live incidents on the page **as of 2026-07-16** admitted exactly **2, both on openai**: the SSO Login incident and `"Elevated Errors for Sora API"` (whose "Sora" component is likewise already in openai's `statusComponentIds`/`displayComponentIds` — the same contradiction). **Non-regressive by construction, not by luck**: the #990 FedRAMP advisories tag only the `FedRAMP` component, an id in **no** service's `statusComponentIds`, so the intersection is empty and they can never reach chatgpt/codex through this path — the provider's own component tagging encodes the environment scope that #990 had to infer from title wording. Deliberately writes `componentIds`, **never** `componentNames`: the EMPTINESS of `componentNames` is what `filterByComponentStatus` (#970) reads as "untagged → drop", and langsmith/langfuse are badge-id-scoped, so tagging page-wide would silently flip them despite having no stake in this bug (`includeUntaggedIncidents` keys on that emptiness too, but only for `incidentKeywords`-scoped services — which those two are not; supply-chain region attribution reads componentNames' CONTENT, not its emptiness, and no incident.io service is in `SUPPLY_CHAIN_AWS_DEPS` at all). The fetch side **warns loudly** when `canIdBypass` holds but no incident could be tagged — without it an upstream page-shape change silently reverts the openai card to `degraded` + empty incident list, i.e. this very bug, with nothing in the logs. Pinned by the real-config + real-ULID tests in `openai-login-attribution.test.ts`, including a `SERVICES`-derived lockstep assertion on the reachable set and an end-to-end HTML→attach→filter test (asserting the ordering in prose is what #940 proved insufficient).

Inert today because openai carries no `componentNames`, but `attachIncidentIoComponentNames` explicitly defers to the API ("an API that starts populating them again wins"), so if incident.io ever restores `components` on its v2 API, openai would get `componentNames: ['Login']` and a ChatGPT-only Login incident could name-match openai's badge group. Follow-up, not a blocker.

6. **Component-status incident filter** (`filterByComponentStatus`): if component is `operational` but provider bulk-linked incidents to all components, remove unresolved incidents (keep resolved + monitoring). Prevents e.g., Anthropic admin API incident from showing on claude.ai/Claude Code when their components are healthy
   - **#970 — an `impact: none` active incident is NOT covered by that premise.** The active-drop assumes "our component is `operational` ⇒ this incident is not about us", which only holds when the incident degraded **some** component (Statuspage derives `impact` from the worst status of the components linked to the incident — unless the provider sets an `impact_override`, the one case where `none` does not imply "nothing degraded"). For an **`impact: none`** incident there is no degraded sibling component to contrast ours against, so "our component is operational" carries **zero information** and the guard discarded a genuine incident on every cron cycle — **invisibly**: `buildIncidentAlerts` saw an empty list (no New alert), and the resolved path requires a prior New alert (`alertedNewMap.has(incId)`), so **neither Discord nor Slack fired**; the incident then appeared on the dashboard the moment it resolved (resolved incidents pass this guard). Production case: Runway's 2026-07-08 **"Aleph 2.0 delayed generations"** (`impact: none`, 23 min) — every component-scoped Statuspage service was exposed (18 at the time; Runway had already lost `Elevated GPT Image Errors`, 2026-06-04, the same way). Unlike #934's `scopeResolvedToComponent`, this active-branch rule is **not** flag-gated, so it also changes `claudeai`/`claudecode` (which reach the guard via `apiUrl` + `statusComponentId`); `mistral`/`perplexity`/`fal` have `apiUrl: null` and never reach it. **Fix:** an ACTIVE incident survives an operational component iff **BOTH** (1) `impact == null` (Statuspage `none`) and (2) its `componentNames` name a component in this service's badge group (`badgeGroupNames` maps `statusComponentIds` → names via the page component list; `statusComponent` matches by prefix per the #359 convention). **Both are required**: Anthropic's bulk-link — the #228 target — attaches 4 of 6 components, a strict subset that *does* intersect the Claude API badge group, so (2) alone would regress #228; its `impact` is always `minor`/`major`, so (1) is the discriminator. (2) in turn keeps a Billing/Support-only `impact: none` incident from alerting. An **untagged** `impact: none` incident is dropped rather than fail-open (on a shared page it would leak onto every sibling). Note the incident surfaces while the badge stays `operational` — correct, since the provider degraded nothing — so `buildIncidentAlerts` attaches no fallback recommendation, and the #767 phone push (impact non-null only) stays silent.
     - **Every drop here is silent by nature — so the two un-judgeable cases are made observable.** A silent drop of a real incident IS bug #970, so: (a) when the badge group is **unresolvable** (the `components` list is empty, or every configured id is missing from the page — e.g. the provider renamed a component), the guard **fails OPEN** (keeps the incident) and `console.warn`s, mirroring the "dropping a real alert is worse than a phantom" trade `shouldHoldNewIncident` makes; a *partially* resolved group is judgeable and still filters normally (the #135 miss-check already surfaces its unresolved ids — primary id → Discord alert, secondary ids → warn). (b) an **untagged** `impact: none` active incident is still dropped, but `console.warn`s so it is never invisible. `components` is a **required** param (call site passes `breakdownComponents ?? []`, matching `includeUntaggedIncidents`) precisely so an omitted list can't silently empty the badge group.
     - **Statuspage-only invariant:** `impact === null` means Statuspage `none` *because* `parsers/statuspage.ts` maps everything outside `{critical,major,minor}` to null. Other parsers (instatus/betterstack) also null out an **unmapped** severity, where null means "unknown", not "none". The sole call site is inside the statuspage `apiUrl` branch — keep it that way, or this rule silently misroutes those incidents.
     - **Known scope limit:** the rule reaches "`impact: none` incidents TAGGED with a badge-group component", which is narrower than "all `impact: none` incidents". An `impact: none` incident naming only an out-of-group component (Runway `Billing`, or a brand-new component not yet in `statusComponentIds`) is still dropped, and — unlike the untagged case — without a warn, because a tagged non-match is a *confident* verdict (warning on it would be constant noise on shared pages, where foreign incidents are legitimate). If a new component appears on a page, add it to `statusComponentIds` or it stays invisible while active.
     - **Fail-open leak-safety rests on a config invariant**, now enforced by the `#970 fail-open leak-safety invariant over SERVICES` test: every service that can *reach* fail-open (statuspage `apiUrl` + ids, no `statusComponent`) is either alone on its status page or already scoped by `incidentKeywords`/`incidentComponents` before the guard runs. Without it, a Runway-shaped service on a SHARED page could, during a momentary id-resolution failure, fail open onto a sibling's incident.
     - Pinned by the `#970 impact:none active incidents` + `#970 through the real call-site flow` tests in `filter-incidents.test.ts`, using the real Runway + Anthropic component lists. The call-site-flow test guards against a refactor dropping the `components` argument (the "tested twin" trap, see `debugging_fix_the_called_path_not_the_tested_twin`).
   - **#1047 — where `componentNames` comes from, and why a provider can delete it mid-incident.** Every rule above reads `componentNames`; `parsers/statuspage.ts` derives it. A provider can **UNLINK every component from an incident as it resolves**: Anthropic's 2026-07-16 `kqbd7wm6hnnr` ("Elevated errors for multiple models") went out tagged with 4 components (claude.ai / Claude API / Claude Code / Claude Cowork, all `partial_outage`) and resolved with `components: []`. Of its 49 siblings on the page, **43 kept theirs, 2 were likewise unlinked (`k5yvlfppnp4f`, `j8ghp7dk6lym`) and 4 were never linked at all** — so this is per-incident provider behaviour, not a page change (and those 2 are exactly why the claude page contributes 3 to the blast radius below, not 1). Because the title carries no `incidentKeywords` token, `componentNames` was the SOLE attribution path for `claudeai`/`claudecode`: both alerted while it was active, then it vanished from the resolved alert (`🔴 Anthropic (Claude API, claude.ai, Claude Code)` → `🟢 Claude API`), from their dashboard cards, and from `incidents:monthly` (absent for both siblings — most likely #975's phantom prune reading a real, newly-orphaned row as an upstream delete; unconfirmed). **Fix:** `resolveComponentNames` recovers the names from `incident_updates[].affected_components` when — and ONLY when — the live list is empty. Same empty-only rule as `attachIncidentIoComponentNames` (#1004); the two are now the house convention for this field. **Not a union**: `filterIncidents`' keyword match runs on every incident and matches these names, so a union would broaden attribution page-wide (the #361 cross-attribution class) to "fix" incidents that were never broken. **Blast radius, measured by replaying every live incident on the 24 statuspage-compat pages (14 Atlassian + 10 incident.io; 23 reachable — `status.character.ai` is the deactivated #800 source): 22 of 865 newly tagged** — `status.claude.com` (3) and `status.cerebras.ai` (19), nothing else. incident.io is untouched because it empties `affected_components` exactly as it empties `components` (**0 of 226 incidents across all 10 of its hosts carry either**) — inert **by data, not by construction**, which is the caveat on the #1032 note above. Whether cerebras' 19 are unlinks at all was **not investigated** (it populates `components` on just 12 of 45 incidents, so those may never have been linked); the rule recovers names whenever the live list is empty, whatever emptied it. **The only live filtering change is the intended one: `claudeai` +2, `claudecode` +3** (claudeai already matched the third by title; `claude` and `cerebras` outputs are byte-identical). It is nonetheless NOT "non-regressive" in principle — the *emptiness* of `componentNames` is itself a signal, so recovery reclassifies these incidents as tagged for every reader of that emptiness. Two such readers are **unreachable for them today**: every one of the 22 is `resolved` (by construction — the unlink happens AT resolution), while #970's "untagged `impact: none` → drop + warn" and `includeUntaggedIncidents`' valve both gate on a NON-resolved status. They stay reachable in principle (an incident whose components were never linked can be active), so `component-unlink-attribution.test.ts` pins **each of the two** — `activenone1` and `coworkonly1` — **prophylactically, with synthetic fixtures**; read them as guards, not as evidence of a live change. Two readers do see resolved incidents, neither changing a live outcome: `claude`'s #934 fail-open (`names.length === 0` → keep) stops being reachable for them (so a Claude-Code-only unlinked incident would now **drop** from Claude API instead of cross-attributing), and the #359 exclude-bypass can now re-admit a title-excluded incident that names our component. The test drives `fetchService` (the real path, per the #966/#940 tested-twin rule) alongside the pure fn. Residuals, both deliberate: a **partial** unlink leaves a non-empty list so recovery never fires (unobserved), and `new_status` is ignored so a component named only as `operational` still counts as affected (the alternative loses attribution outright when the resolve update is the only one carrying components — it fails toward keeping the tag).
   - **#934 — `scopeResolvedToComponent`: resolved/monitoring incidents component-scoped for exclude-only shared-page services**: keeping ALL resolved/monitoring incidents cross-attributed a **sibling-component-only** incident to a service once it RESOLVED. `claude` (Claude API) has no positive `incidentKeywords` — it relies on title-based `incidentExclude` + this guard — so a Claude-Code-only incident whose title names no exclude keyword (the 2026-07-06 **"Claude Tag seeing elevated GitHub operation failures"**, `componentNames: ['Claude Code']`) stayed in claude's candidate set. While active it was hidden here (Claude API component operational → drop unresolved); the moment it became `resolved` this guard kept it → it surfaced under Claude API + fired a Claude-API-included recovery alert. Fixed with an **opt-in `scopeResolvedToComponent` flag** (set on `claude` ONLY): when set, a resolved/monitoring incident is retained only if it **plausibly involved this service's own component** — its `componentNames` prefix-match `config.statusComponent` (same convention as the #359 exclude-bypass), OR it carries **no** `componentNames` (untagged → ambiguous → keep, fail-open). **Default-off** so single-tenant services (`mistral`/`perplexity`/`fal`, whose broad `statusComponent: 'API'` would wrongly drop a specific-component incident like `'Sonar API'`) and keyword-scoped siblings (`claudeai`/`claudecode`, which already scope upstream and could drop `'across surfaces'` incidents) are byte-unchanged. Pinned by the `#934 resolved sibling-component cross-attribution` tests in `filter-incidents.test.ts`.
7. **Status page fetch failure cross-validation** (post-processing in `fetchAllServices`):
   - If service is `degraded` from fetch failure (no incidents) AND probe RTT is normal → override to `operational`
   - If 70%+ of services on the same platform (Atlassian/incident.io/etc.) fail simultaneously → platform outage → override all to `operational`
   - Conservative: only overrides when evidence is strong (≥2 recent probes healthy, or quorum failure detected)
   - **#689 — dead-source 4xx** (`classifyStatusPageFailure`, in the statuspage fetch path itself, BEFORE the above): a `4xx` on the status-page API means the page is **deactivated/gone** (the SOURCE is dead, not the service — e.g. Character.AI's Statuspage → 401 "page inactive"), so it returns `operational` + `sourceDead` + `incidentSourceStale` (excluded from rankings) instead of `degraded`. `apiUrl` is kept, so it **auto-recovers** to live status when the page returns `200`. The cross-validation above can't rescue this case (it needs probe data, which apps lack, or a platform-wide quorum). The cron sends a distinct **"status source inactive"** operator alert (not a misleading "degraded"), deduped via `alerted:source-dead:{svcId}`. A `5xx`/network error stays transient → the normal `trackFetchFailure → degraded` path.
     - **#714 — 3-state source liveness (flap fix)**: the operator alert decision no longer keys on the boolean `sourceDead`. A boolean conflated "fetch succeeded (alive)" with "fetch threw / 5xx (indeterminate)" as one `false`, so a single transient hiccup mid-dead-source (the cross-host `302→4xx` redirect-follow throwing from CF egress) flipped the alert to a **false "Recovered"** → next-cycle "Inactive" → a repeating pair every cron (the Character.AI symptom). Now `services.ts` also sets **`sourceUnknown`** on the throw (outer catch) + 5xx return paths, and `sourceLivenessOf(svc)` derives `dead` (4xx, incl. 429) / `alive` (clean fetch — the ONLY recovery signal) / `unknown` (throw / 5xx). `decideSourceDeadAction(liveness, {alreadyAlerted, pendingExists})` (alerts.ts, pure + unit-tested) maps it: `unknown` while alerted → **hold** (keep the marker, send nothing); `recovered` fires only on a genuine `alive`. The rising **alert** edge is debounced by a #633-style 1-cycle confirmation marker (`pending:source-dead:{svcId}`, `PENDING_SOURCE_DEAD_TTL_S=600`) so a single-cycle 4xx blip never alerts
     - **#1004 — `sourceUnknown` is now a DISPLAY state too, not just an alert input.** The `degraded` that `trackFetchFailure` returns after 3 consecutive failures is not a verdict about the service — it's "we can't read the source" — but the UI rendered it as an ordinary amber `degraded`, indistinguishable from a real partial outage. JetBrains moved Junie's status page (Atlassian → incident.io) and 301'd the old host to the new **site root**, so our `apiUrl` fetch got `200 text/html`, `res.json()` threw, and Junie showed a **false amber `degraded` badge** — on the dashboard AND as the `/is-junie-down` SERP answer — while JetBrains reported all-green. Detection was NOT the gap: the #500 persistent-failure sweeper fired its "status page unreachable 1h+" operator alert on schedule (2026-07-14 00:37 KST, ~1h after the first failed fetch). What was missing was **containment** — nothing about the public surfaces changed while the operator slept, so the false outage was broadcast for ~9 hours until it was noticed by hand. That is what this display rule fixes: the alert tells the operator, the badge stops lying to everyone else. Note the asymmetry that hid it: a page *deletion* (4xx) is `sourceDead` → neutral `unknown` badge; a page *migration* (301 → parseable-looking HTML) is `sourceUnknown` → had no display path at all. So `resolveStatusDisplay(status, partialCount, sourceDead, sourceUnknown)` now maps **`sourceUnknown` + `degraded` → `'unknown'`** (Overview pill AND card stripe, ServiceDetails pill + an explicit "AIWatch can't parse the source — this does not mean the service is impaired" banner). `sourceUnknown` + `operational` (under the 3-strike threshold) stays operational — no news is not bad news yet — and a real `down` is never masked. Display-only, as ever: the raw `status` (and therefore Score / ranking / alerts) is untouched

## Operator incident suppression — orthogonal to `incidentExclude` (#904)

`incidentExclude`/`incidentComponents` above are **source attribution** — "this incident belongs to a
DIFFERENT service, don't attribute it here" (splitting a shared status page). Separately, an incident can
be **correctly attributed** to a service yet need to be **un-exposed for a policy/operational reason** —
e.g. OpenAI's FedRAMP "degraded performance" (gov-compliance-scoped, not general-API availability). That
is NOT an attribution problem, so it does **not** belong in `incidentExclude`.

- **The two FedRAMP cases are NOT the same — mind which layer (#990 vs #904).** #693's FedRAMP incident
  (`"FedRAMP workspaces and API orgs have degraded performance"`) is a genuine **API** degradation
  *correctly attributed* to openai — so openai KEEPS it (via the `api` keyword), and hiding it for policy
  would be a **runtime suppression** (#904), never an `incidentExclude` token. #990's incident
  (`"Codex, workspace analytics, … not working in FedRAMP workspaces"`) is a **kitchen-sink advisory**
  whose enumerated title merely *name-drops* Codex/ChatGPT; it is **mis-attributed** to codex/chatgpt by
  substring match, and is a **permanent structural scope** decision (this class is never a GA
  codex/chatgpt outage). That IS an attribution problem, so it correctly lives in a static
  `incidentExclude` token (`ENVIRONMENT_SCOPE_EXCLUDE = ['fedramp']`, spread into codex + chatgpt only —
  NOT openai, which would regress #693). Rule of thumb: **permanent, class-wide, reviewed → static
  `incidentExclude`; one-off, correctly-attributed, transient policy → runtime suppression.**

The **suppression layer** (`worker/src/suppression.ts`, operated via `GET/POST /api/admin/suppress` —
see [operator-tools.md](operator-tools.md)) handles it as a **separate step AFTER `filterIncidents`**, so
attribution logic (and e.g. the #693 "openai KEEPS FedRAMP" `filter-incidents.test.ts` assertion) is
**unchanged**. A single `incident:suppressions` KV list carries entries of scope `incident` (hide one id)
or `service-pattern` (hide any title-matching incident on a service — a runtime-editable `incidentExclude`,
e.g. `{svcId:'openai', match:'fedramp'}`). Applied at two points: `fetchAllServices` return (live list +
`scoreFor` + go-forward accumulator + `services:latest` cache) and `buildMonthlyArchive` build-time
(rebuild-safe drop from a stored past-month accumulator, aggregates recomputed). The **badge is
unaffected** — suppression runs after status determination, removing the incident only from the LIST +
Score inputs. Removing a suppression restores the incident with zero code change.

### Duration override — the "correct but overstated" sibling of suppression (#1019)

Suppression HIDES an incident; a **duration override** KEEPS it but PINS its duration. The problem it
solves: an incident's `duration` is the provider's **paperwork** span (`resolved_at − created_at`;
`parsers/statuspage.ts`), and some providers leave an incident open in `investigating`/`monitoring` long
**after the affected component actually recovered**. Cursor `h71m65my586h` (2026-07-14) — IDE went
`degraded_performance` at 19:52 UTC and was already `operational` well before the formal 09:11 UTC resolve
(its `affected_components` on the resolve update reads `operational → operational`), yet the stored
duration is **13h 20m**; the sibling `96m8j04k15r5` ("- Sol") on the same component resolved in **18 min**,
the best proxy for when the shared degradation cleared. That overstated duration feeds **MTTR / the
Recovery score** (median-robust at ≥3 resolved incidents, but the `<3` mean fallback lets one such outlier
tank a low-incident service) and the monthly report's `longestIncidentMin` / `totalDowntimeMin`.

The **override layer** (`worker/src/overrides.ts`, operated via `GET/POST /api/admin/duration-override`)
mirrors suppression: an `incident:duration-overrides` KV list of `{ id, durationMin, reason }`, applied by
`applyDurationOverrides` which recomputes each affected service's `totalMinutes`/`longestMinutes` from the
`durations` map (the `filterSuppressedFromMonthly` pattern) and updates `incidents[].durationMin` (the #915
`aggregateIncidentDurations` source of truth) AND, for a resolved entry, `incidents[].resolvedAt` (=
`startedAt + durationMin`) so the timestamp-derived consumers — the grouped-incident row duration
(`sumGroupDuration`) and the Uptime calendar span — agree rather than still painting the paperwork span.
It also flows into the calendar-month `monthlyScore` (#993), whose MTTR reads the same per-incident
durations. Applied on **READ/BUILD** of the monthly accumulator — NOT
by editing it — because `accumulateMonthlyIncidents`'s monotonic `if (dur > oldDur)` guard would re-inflate
a lowered stored value on the next cron while the incident is still in the live feed. Three apply points,
each right after suppression: `buildMonthlyArchive` (rebuild-safe), the `/api/report` current-month partial
(dashboard 30/90-day list — but for a still-live current-month incident the live `/api/status` value wins
in `mergeArchiveIntoMap`, so the override's visible effect there lags until the incident ages out of the
feed; the permanent archive is unaffected), and the weekly briefing. The live `/api/status` Score is
deliberately **not** overridden — MTTR robustness for the general case is tracked as #1019 Part B (a
confidence-gate or small-sample shrinkage on MTTR, vs. computing duration from AIWatch's own observed
`degraded → operational` edge). Removing an override restores the provider duration with zero code change.

## Status page URL selection

`apiUrl` (the machine-readable fetch endpoint) and `statusUrl` (the human-facing link) can differ. When selecting `apiUrl`, **verify it is reachable from Cloudflare Workers** — some providers host their status page on a custom domain that blocks Workers IPs while the canonical Atlassian/incident.io host remains accessible.

**Verification method**: `curl -sv "<url>" 2>&1 | head -20` — look for SSL connection reset or HTTP 000 (curl's notation for a connection-level failure — no HTTP response received at all), which indicate Workers-IP blocking even when a browser can reach the page.

### Known case: DeepSeek (2026-05, #498)

`status.deepseek.com/api/v2/summary.json` resets the connection from Workers IPs (Alibaba Cloud CDN with geo/bot filtering). `deepseek.statuspage.io/api/v2/summary.json` is the Atlassian-hosted mirror — identical component IDs and data, always accessible.

**Fix**: set `apiUrl` to the `.statuspage.io` URL; keep `statusUrl` as the branded domain for the dashboard link.

**Symptom pattern**: `fetch-fail:{svcId}` KV key reaches `3` (threshold) and stops refreshing — the write-back guard (`next <= threshold`) skips writes once the counter would exceed 3, so the TTL is last refreshed on the 3rd failure (writes on failures 1, 2, and 3 each extend it; no writes occur after that) and expires 1800s (~30 min) later. After expiry the counter resets; the threshold is crossed again after 3 more cron cycles (~15 min), so the re-alert fires roughly 45 min after the original alert rather than exactly 30 min. Probe cross-validation (Phase 1) may not fully suppress these if the API probe has a concurrent RTT blip, or if fewer than 2 recent probe snapshots are available (e.g., after a probe disruption).

**General rule**: when adding or updating a service with an Atlassian Statuspage, check both `{custom-domain}/api/v2/summary.json` and `{slug}.statuspage.io/api/v2/summary.json`. Use whichever responds with HTTP 200 from a non-browser client. Also confirm that the `statusComponentId` value in the service config resolves correctly against the chosen endpoint's component list — component IDs are not always identical between a custom domain and its `.statuspage.io` mirror.

## Parsers must map incident `impact` — null silently drops the incident from scoring (#556, #564)

A parser that leaves `incident.impact = null` makes the incident **invisible to the AIWatch Score's Incidents component**: `score.ts` excludes null-impact incidents from both `affectedDays` and `weightedAffectedDays` (the #261 filter, intended to drop informational/post-mortem posts). So a real outage parsed with null impact shows **Affected Days 0** and applies **no incident penalty** → an inflated score.

**#1021 — the DELIBERATE inverse: down-classify a non-reliability ADVISORY to null impact for ALL providers.** Some providers post usage-limits / quota / billing / deprecation notices as status-page "incidents" that are not availability outages (the live case: Codex's June 2026 **"Usage Limits Depleting Faster Than Expected"**, `impact: minor`, 72h — 79% of its archived downtime, and what dropped its Score 86→76). This generalizes the #707 AWS-Health carve-out (which only ran in `aws.ts`) to every provider via `downclassifyAdvisoryIncidents(services)` in `services.ts`, applied at the **single `fetchAllServices` return choke point** (beside the #904 suppression layer) so every consumer of the returned list agrees: the live /api/status list, the live Score (excludes null-impact per #707/#261), the go-forward monthly accumulator (stores the null impact), **and the cron push gate** (`alerts.ts shouldPushNotify` → no user push for an advisory; the Discord `new`-incident alert still fires — it doesn't gate on impact). Keyed on `isNonReliabilityAdvisory(title)` (shared `NON_RELIABILITY_RE`, `usage limit|quota|deplet|billing|invoice` joined #707's compliance/revoke/suspend/deprecation terms; `errors?` joined `OUTAGE_SIGNAL_RE` so a "Quota errors" real fault still wins; `model access` deliberately NOT a term — `suspend` covers the access-suspension case and a bare "model access" title collides too readily). The incident stays in the raw list/count (reclassified informational, not dropped). In the **monthly archive** the same title classifier also excludes advisories from `totalDowntimeMin` / `longestIncidentMin` (`aggregateIncidentDurations`) and from the `avgResolutionMin` divisor, and `computeMonthlyScore` down-classifies by title too — so a REBUILD of a pre-#1021 month (whose stored impact predates the down-classification) fixes downtime AND Score over one population, not just downtime. A frozen month is not retroactively changed unless rebuilt.

**Instatus status-page URLs drift — point `instatusUrl` at the CURRENT path, not a redirect (#761).** Mistral moved its incidents listing: `status.mistral.ai/incidents/page/1` now **301s** to `/activity/page/1` (verified 2026-07-20). `fetchWithTimeout` uses `redirect: 'follow'`, so a stale URL keeps parsing and the drift is invisible. The reason to fix it is that the scrape fetch fails **silently, not loudly**: it carries its own `.catch` (→ `null`, `parseErrors++`), and the Instatus return path calls `trackFetchFailure` but **discards** its `shouldDegrade` — the status returned is derived from the ROOT `statusUrl` response. So a throwing scrape URL does **not** degrade the service (the earlier "false-outage" reading of **#714** was wrong; #714's evidence is also a *cross-host* `302→4xx`, where Mistral's is a same-host `301→200`). It empties `incidents` instead, risking a false **recovery** — an ongoing incident silently vanishing — plus the loss of uptime and the components snapshot.

> **#1089 — that risk is now closed at the parse level, not just at the URL.** #761 removed one *trigger* (the 301'ing scrape URL); the *class* stayed open, because ANY structural parse failure still emptied `incidents` and fell through to `httpStatus`. Observed live 2026-07-20: the plugin monitor emitted `✅ Mistral API has recovered` then `🔴 degraded` minutes apart while incident `4288f6a2` stayed `investigating` since 07-17 — no incident state changed, so only an empty parse could have moved the badge. The guard covers BOTH ways the list can go unreadable: the scrape **fetch** failing (its own `.catch(() => null)`) or returning non-ok — the 404 case being #761's URL-drift scenario, and the likeliest real trigger — and the payload **parse** failing after a 200. An earlier cut covered only the parse, which would have missed the more probable cause. `parseInstatusIncidentsResult` (`parsers/instatus.ts`) returns `{ok:false, reason}` for the **six structural** exits — Nuxt: `no-nuxt-payload` / `no-incident-refs` / `no-incident-index` / `bad-json`; Next: `no-next-notices` / `next-shape-changed` — plus `scrape-unreadable`, which the caller sets when the fetch itself failed and `{ok:true, incidents:[]}` for a genuinely quiet page. The other five `return []` sites **in the Nuxt entry mapper** (`parseNuxtIncidentEntries`) are **per-item skips inside its flatMap** (a malformed entry; the deliberate <60s micro-incident filter) and are NOT failures — counting them would report every quiet day as an unreadable source. On any of these, `fetchService` stops deriving a status and returns `sourceUnknown: true` + `trackFetchFailure`'s `shouldDegrade` — i.e. it finally CONSUMES the `shouldDegrade` this paragraph says was discarded, reusing the same primitive as the summary-5xx/throw paths (§#1004) rather than a parallel one. Covers all three Instatus services — mistral (Nuxt) and perplexity/fal (Next) — but the two formats needed different mechanics, and getting Next to genuinely agree took three review rounds. Nuxt's per-entry skips are individually wrapped, so losing the whole list requires every entry to fail independently. Next parses its entire `notices` list through ONE regex, so a single mis-anchor (key order, an extra key between `notices` and `metrics` — its lazy quantifier spans across, matches, then the over-wide slice fails to parse — or ids no longer `[a-z0-9]`-initial) silently drops open incidents. Neither "is the envelope present" nor "did the regex match" separates that from the legitimate all-filtered case, so `parseInstatusNextIncidentsResult` decides from the envelope it extracted: `wouldYieldIncident` re-applies the two documented per-notice filters (unparseable `started`; a RESOLVED incident under 60s) and asks how many notices SHOULD have survived. Zero expected ⇒ the filters did their job (`ok:true`); some expected but none produced ⇒ the list was lost (`next-shape-changed`). It is deliberately conservative — an unreadable notice counts as should-have-yielded, so an unfamiliar shape biases toward reporting drift rather than toward a silent green badge. The Instatus arm is deliberately **not** gated on `scrapeRes?.ok`: the main status page is a separate fetch and usually still fine, so gating skipped the uptime + components read too and turned one unreadable incident list into a wholesale data loss. The two fetches now fail independently, as they actually do. **Accepted limitation:** under the 3-strike `trackFetchFailure` threshold the badge still reads `operational` (with `sourceUnknown` set, so the UI caveats it) — a single transient blip is not turned into a fabricated outage, which is the opposite error.

> The two Mistral pages are **not interchangeable, in both directions**: `parseInstatusIncidents` returns `[]` on the root `statusUrl`, while `/activity` carries no component tree. The root payload does, however, carry the currently-**unresolved** incidents with their `services[]` attribution — the overlay input to the Nuxt component derivation below, which is why the derivation reads `statusUrl` and not `instatusUrl` (its primary input, the component tree, is only on the root page too).

**Instatus is the footgun** (`worker/src/parsers/instatus.ts`): its two SSR formats expose severity under different field names/vocabularies, and both previously yielded null —
- **Nuxt** (e.g. Mistral): incident-level `severity` (`MINOR`/`MEDIUM`/`MAJOR`/`CRITICAL`) — the parser had `impact: null` hardcoded.
- **Next.js** (e.g. Perplexity): component-status `impact` (`OPERATIONAL`/`UNDERMAINTENANCE`/`DEGRADEDPERFORMANCE`/`PARTIALOUTAGE`/`MAJOROUTAGE`) — the parser only handled `MAJOROUTAGE`/`PARTIALOUTAGE`, so `DEGRADEDPERFORMANCE` fell to null.

**Instatus uptime% extraction** (`parseInstatusUptime`, #627/#635) — Instatus has no Atlassian-style `summary.json`, so the per-component official uptime% is scraped from the main status page, and the two SSR formats encode it differently: **Nuxt** (Mistral) as a flat-array index-ref scalar; **Next.js** (Perplexity) as a `componentsUptime` object keyed by component id, each entry carrying a precomputed `"uptime":"99.82"` string (reversing the original #627 "Next.js has no inline uptime" finding — Instatus now serializes it). The parser reads only the **percentage**, not the page's window (per #654 the window isn't surfaced since it varies by source — Next.js observed ~90d via `maxUptimeDays`). Selected per service via `statusComponent` (mistral/perplexity → `'API'`); a payload-shape change warns-once so a silent revert to "Not provided" is diagnosable.

**Atlassian Statuspage uptime% extraction** (`parseUptimeData`, `parsers/statuspage.ts`) — reads the embedded `uptimeData` JS object (`{ componentId: { component, days: [{date, outages:{p,m}}] } }`) from the status-page HTML and computes an Atlassian-weighted % (MAJOR 1.0 / MINOR 0.3). **#868** — Atlassian changed the embed from `var uptimeData = {…}` to `window.uptimeData = {…}` **plus** a `var uptimeData = window.uptimeData;` alias line; the old `indexOf('var uptimeData = ')` matched the alias → `JSON.parse("window.uptimeData;…")` threw → **`uptimePercent` null** → claude.ai / Claude Code / Cursor / Windsurf / Junie / Voyage AI silently lost official uptime and (having no probe) dropped to `scoreConfidence: low` → **withheld from the ranking**. The parser now locates the assignment whose RHS is the JSON object via a whitespace/minification-tolerant regex `/(?:window\.|var\s+)uptimeData\s*=\s*\{/` (the alias's RHS `window…` never matches; legacy `var uptimeData = {…}` still does), hardening against the next embed-shape change. Pinned by `parse-uptime-data.test.ts` (new-format bug-repro + minified + old-format regression + edge cases).

Both now go through the shared `mapInstatusImpact()` helper: `CRITICAL→critical`, `MAJOR(OUTAGE)/HIGH→major`, `MINOR/MEDIUM/LOW/PARTIALOUTAGE/DEGRADEDPERFORMANCE→minor`, `OPERATIONAL/UNDERMAINTENANCE/MAINTENANCE/NONE/empty→null`, and any **unknown value → `minor` + a warn-once** (an `/incidents`-feed entry is real, so surface it rather than hide it; the warning makes a new Instatus vocabulary value diagnosable). Note `impact:null` excludes from *scoring* only — a null-impact entry still appears in the raw incident list/count. **Display complement (#599)**: because `DEGRADEDPERFORMANCE → minor` tags Instatus auto-monitor blips `minor` (not null), the **display** grouping (`groupIncidents` — SPA + SSR mirror) also clusters `minor` `"<Component> Degraded[ Performance]"` titles via `isAutoMonitorTitle` (alongside the #597 BetterStack `— recovered` flap-suffix), so Mistral's per-component `"Conversations API Degraded"` series collapses to one group row instead of flooding the history. Per-model variants (`"… Degraded - model-A"` vs `"- model-B"`) stay separate; `major`/`critical` stay individual; Score/MTTR read the raw list — display-only.

**BetterStack is the second footgun** (`worker/src/parsers/betterstack.ts`, #564 — Modal/Together/Fireworks/HuggingFace/xAI): both incident paths hardcoded `impact: null`. BetterStack exposes no structured per-incident severity (the RSS `<item>` has only title/description; `index.json` `affected_resources` read `resolved` at rest), and — critically — its automated monitors emit a generic **"X went down" for ANY failed check**, so `"down"` is NOT a reliable severity signal (Together/Fireworks are 20/20 "went down" model-flaps, not declared outages). The shared `mapBetterStackImpact()` therefore maps **major only on explicit broad-outage wording** (`outage`/`unavailable`/`offline`) and **everything else → minor** — deliberately symmetric with the Instatus all-minor outcome, to avoid structurally over-penalizing monitor-flap services. The xAI path additionally needs its own maintenance-title skip (it has no `betterStackUrl`, so the `index.json` maintenance filter doesn't run) and maps from the tag-stripped description (raw CDATA markup like `class="offline-banner"` would false-match). **Display complement (#597)**: because this mapping tags monitor-flaps `minor` (not `null`), the **display** grouping (`groupIncidents` — SPA `src/utils/incidentGrouping.js` + SSR mirror `api/_is-down/incident-grouping.ts`) also clusters `minor` `— recovered`/`— down` flap-suffix titles, not just null-impact/generic ones, so the incident history (dashboard Incidents + ServiceDetails + is-X-down) isn't flooded by per-model blips. `major`/`critical` suffix incidents stay individual, and the Score/MTTR keep reading the raw incident list — grouping is display-only.

**Atlassian is the third footgun — `impact` is component-derived, not editorial (#983)**: Statuspage sets an incident's `impact` from the worst status among its affected components, so a **single sub-component** at `major_outage` yields `impact: 'major'` even on a 6-minute machine-emitted blip. Every AIWatch guard that used `impact != null` / `impact !== 'major'` as a proxy for *"a human curated this incident"* is therefore wrong on such a page. Observed on **Twelve Labs** (2026-07-09): its auto-monitor opened **four separate incidents in 7 hours**, identical title (`"Some API features are experiencing issues"`), identical machine-emitted timeline text, one component (`Analyze API - Pegasus1.5`), 5–16m each, three of them `major`. They reached Discord as 4 New + 4 Resolved alerts and rendered as four rows, because neither the `flapSuppression` title shape (`— down`/`— recovered`) nor `holdShortIncidents` (which bails on `major`) recognized them.

Unlike Instatus/BetterStack — where the fix was to widen a **title heuristic** in the display layer — this one **tags at the source** (the #940 precedent). `ServiceConfig.autoMonitorTitles` holds anchored (`^…$`) exact-match patterns for the provider's machine-emitted titles; `tagAutoMonitorIncidents` (`services.ts`) stamps `Incident.autoMonitor = true` on matches, and it is serialized on `/api/status` so **every** surface reads one verdict instead of re-deriving it:

| Consumer | Behavior when `autoMonitor` |
|---|---|
| `groupIncidents` (SPA + SSR mirror) | groups regardless of `impact` — one `×N` row per (local day, title) |
| `isShortIncidentHoldable` (`alerts.ts`) | hold-eligible regardless of `impact` — the tag is its own opt-in, independent of `holdShortIncidents` |
| `isFlapNotice` / `isFlapSuppressible` | a flap without needing the `— down` suffix → the 60-min same-title suppression window (#283) applies |

`critical` is checked **first on every path** and is never held or suppressed, tagged or not — it is the one level a status page never assigns by auto-monitor alone, so it stays the escape hatch guaranteeing a genuine broad outage alerts immediately. Tier-1 (claude/openai/gemini) is likewise never held. The patterns are anchored precisely because a substring match would swallow the provider's **real, human-written** incidents (Twelve Labs: `"Search API failure"`, `"API server failure"`) — a `SERVICES`-wide unit test asserts every configured pattern is `^…$`-anchored and carries no `g`/`y` flag (a stateful regex would alternate true/false across `.test` calls). Stamping happens **once**, on the `ServiceStatus` that `fetchService` returns, so it survives all ~10 parse branches, `filterIncidents`, `includeUntaggedIncidents` (which re-adds from the RAW parsed array) and the aistudio/xAI source merges; it never rewrites `title` — the #940-review Critical. Score/MTTR still read the raw incident list, and incidents supplemented from a **monthly archive written before the tag shipped** carry no `autoMonitor` and so still render individually (the accumulator is additive and does not self-heal — see #934/#975).

**xAI per-region source-merge (#940, `worker/src/xai-regions.ts` `mergeXaiRegionalIncidents`)**: xAI publishes the SAME event per region as SEPARATE RSS items (distinct guids, titles differing only by a `[API (<region>.api.x.ai)]` prefix — e.g. us-east-1 + eu-west-1 + us-west-2 for one "Imagine Video 1.5 …" degradation). `services.ts` collapses them to **ONE canonical incident right after `parseXaiRssIncidents`**, so EVERY downstream surface — dashboard list, Analyze modal, RSS/Slack `/feed`, Discord new+resolved alerts — sees a single incident. This SUPERSEDES the earlier per-surface merges (`mergeXaiRegionalAlerts` #686 on the Discord alert batch, `collapseXaiRegionalIncidents` #703 on the AI-analysis write loop), which were **cycle-local** — they only collapsed within one `*/5` cron batch, so regions that surfaced or resolved in *different* cycles leaked as duplicate cards/messages (observed 2026-07-08: 2 Discord "Resolved" + 3 Slack items + a 2-card Analyze modal for one 3-region event); those two helpers now receive an already-merged list → no-ops kept as cheap defense. Merge semantics: **id** = `xai-evt:<fnv1a(region-stripped title)>` (survives partial resolution + single→multi-region transition without re-keying, so no phantom mid-incident re-alert; two accepted re-key cases, each still far fewer alerts than the pre-#940 per-region behavior — an xAI incident already active at deploy re-keys once from its RSS guid (deploy while xAI is clean to avoid it), and an upstream **summary-text edit** changes the eventKey → one duplicate alert); **status** worst-of (`resolved` only when ALL regions resolved, else most-active stage); **impact** worst-of; **startedAt** earliest / **resolvedAt+duration** only when all resolved (latest resolvedAt); **title** single-region keeps its original `[API (<region>.api.x.ai)] …`, multi-region → **`[API] <eventKey> (regions: …)`** — the `[API]` marker is REQUIRED because the merge runs at the SOURCE (before `filterIncidents`), and xAI keeps an incident only when its title carries the `api` `incidentKeyword` (xAI incidents have no componentNames); dropping the prefix would silently filter out a real multi-region outage → service reads operational (the #940-review Critical); **timeline** union sorted oldest-first + deduped. Non-region-tagged + non-xAI incidents pass through untouched (safe no-op). Pure + unit-tested end-to-end through `filterIncidents` (`__tests__/xai-regions.test.ts`).

**Incident-history preview + collapse (display-only, #incident-history-collapse)**: on top of grouping, both incident-history surfaces show only the **first 5 grouped rows** and tuck the rest behind a "Show N more"/"Show less" toggle (so a busy provider like Claude — ~10+ rows/week — doesn't dominate). Dashboard `ServiceDetails.jsx` uses a React button (`historyExpanded` state, reset on `serviceId` change); the is-down Edge SSR (`api/_is-down/html-template.ts`) uses a **CSS-only checkbox-hack** (`.ih-toggle`/`.ih-rest`/`.ih-more-label`, no JS — CSP-clean) anchored at the bottom so overflow reveals **above** the toggle, with collapsed rows kept in the HTML (crawlable). The is-down incident-history **window was aligned 30d→7d** to match the dashboard's 7-day "Incident History" (the SERP meta's separate `thirtyDayIncidentCount` "(30d)" breadth figure is intentionally left at 30 days — it's a distinct, explicitly-labeled SEO signal, not the visible list).

**Crowd "Report an issue" — collect + GATED display (#575)**. Visitors report a problem (category + 80-char description) via a modal: the **Overview** floating button (service-select dropdown) and the **ServiceDetails** header button (service pre-selected) on the dashboard, plus the is-down page's own modal — all POST `/api/report-issue` (IP-hash per-UTC-day dedup, never a public count). The recent reports DISPLAY is **gated**: a service's `report:feed:*` surfaces ONLY when an INDEPENDENT signal corroborates a problem — official status not operational, a `partialCount` (#722), OR a `probeSpike` (active consecutive RTT spike, the "faster than official" early-warning) with the crowd clearing `REPORT_DISPLAY_MIN` (`shouldSurfaceReports`, pure + unit-tested). Crowd-alone (operational + clean probe) is **never shown** — the load-bearing constraint (at ~22 visitors/incident a raw "N reporting" banner would manufacture false signal). The worker centralizes the gate in `buildReportFeedMap` → the gated `reportFeed` map on `/api/status` (the dashboard reads it; the is-down Edge uses `/api/report-feed`). Surfaces: Overview "Recent user reports" panel (next to Recent Incidents, 5 + collapse), ServiceDetails section below the incident history (5 + collapse), is-down section. Descriptions sanitized on store + escaped on render (UGC). The earlier "Status Confidence" indicator idea was dropped as redundant with existing signals (partial pill / Unknown badge / the reports section itself); only `probeSpike` was kept, as the gate's cross-match signal.

**OnlineOrNot planned-maintenance filter (#894, `worker/src/parsers/onlineornot.ts`, openrouter/xai)**: OnlineOrNot's React-Router SSR loader data separates real incidents (`incidents`/`activeIncidents`) from planned maintenance (`scheduledMaintenance`), but a maintenance entry **reuses the same `title`/`started` `_N` key indices** as an incident (and carries no `impact`). The original flat-scan — which picks up any object with a `title`+`started` ref — therefore swept a `scheduledMaintenance` entry in as an active `investigating` incident (OpenRouter "Scheduled Database Maintenance" showed on the dashboard while `activeIncidents` was empty). `collectMaintenanceRefs` walks the `scheduledMaintenance` grouping (key string → the container's `_N` ref → its index array → those object refs) and the scan **skips those objects by reference identity**. Trusts the source's own grouping — the authoritative signal — so custom-titled *in-progress* maintenance is caught and real incidents are never dropped. **#896 (title backstop)**: once a maintenance window **ends**, OnlineOrNot relocates the completed entry OUT of `scheduledMaintenance` (the array goes empty) into a normal resolved-entry object, so the structural filter alone let a *completed* maintenance leak in as a resolved incident. The scan now ALSO skips any entry whose title matches betterstack's exported `MAINTENANCE_TITLE` — the exact belt-and-suspenders betterstack uses (structural `report_type='maintenance'` + `MAINTENANCE_TITLE`). Structural filter covers in-progress custom-titled maintenance; title backstop covers completed/relocated maintenance.

**General rule**: when adding a parser for a new status-page platform, confirm it maps the platform's severity/impact vocabulary onto `'minor' | 'major' | 'critical'` (reserve `null` for genuinely informational/maintenance entries) — otherwise the service's incidents won't count toward its score.

## Intermediate "Partial" display state + BetterStack threshold (#722)

BetterStack multi-monitor services (together/fireworks/huggingface/modal/luma) expose N per-model resources. When one goes down the official page shows **"Some services are down"**, but `parseBetterStackStatus` collapses the badge to `operational` when non-operational resources are below a fleet-ratio threshold (single-model churn ≠ service-level outage, #159). `parseBetterStackPartialCount` separately counts the affected (degraded+downtime) resources → `ServiceStatus.partialCount`.

- **Display — intermediate `partial` state**: a green pill understated the gap (peers StatusGator/IsDown both use an intermediate "warn"; BetterStack itself is worst-of). The shared `resolveStatusDisplay(status, partialCount, sourceDead, sourceUnknown)` (`src/utils/statusDisplay.js`) returns `'partial'` when `status === 'operational' && partialCount > 0` (and `'unknown'` for `sourceDead` (#689) or for `sourceUnknown` + `degraded` (#1004 — the fetch-failure fallback, see above)). `StatusPill` renders it as a **yellow** pill — the 4-step gradient is operational(green) → **partial(yellow)** → degraded(amber) → down(red); **#744** folds the affected-count into the single pill (`⚠ Partial · N`) instead of a separate `⚠ N affected` chip. **#744 also propagates the partial display to the two surfaces that previously read flat-green**: the **Overview card left border stripe** (was `status`-only → green; now `resolveStatusDisplay(...)==='partial'` → yellow, matching the badge on the same card) and the **is-down Edge SSR header** (a yellow 🟡 dot + a visible "Partial — {name} has N component(s) affected (operational overall)" answer line, replacing the old flat-green "No — operational" verdict + the now-removed separate note). The is-down `<title>` + meta description (the SEO/SERP answer) **stay on the raw `operational` status** — only the on-page visible header reflects partial, so the search answer ("Is X down? → No") doesn't flip. **It's a render-time relabel — never changes the `status` field**, so it can't itself escalate a service to `degraded` or fire a degraded alert (those key off `status`). It does NOT shield the Score/ranking from the real outage: that already flows in via uptime/incidents as usual (server-side, intended). The point is only to avoid mislabelling a single-model blip as a service-wide `degraded` (which WOULD churn alerts). Supersedes the #447 green-pill + tiny-chip treatment.
- **Threshold value — `BETTERSTACK_DEGRADE_THRESHOLD = 0.1`** (`betterstack.ts`): the collapse threshold governs only the operational↔degraded (Score-penalized) boundary. It was historically escalated 10%→15%→30% (#159→#162/#163) **chasing the wrong root cause** — the recurring false-degraded alerts were the Cloudflare Workers connection limit (#162: "root cause is NOT BetterStack aggregate_state sensitivity"; fixed in #164), and 30% was never re-validated post-#164. #722 returns it to the #159-justified ~10%, so a genuine **multi-model** outage (≥10%, e.g. 3/29) registers as `degraded` while a single model down (1/29 = 3.4%) stays `operational` + `partial` display. The `downtime` branch still escalates to `down` only when >50% of resources are down.
- **Provider roll-up gate (#731)**: `parseBetterStackPartialCount` returns **0 when `aggregate_state === 'operational'`** — i.e. when BetterStack's own page header is all-green (no incident). Because `/api/status` re-fetches live every 60s, a stray transient resource-level `degraded`/`downtime` monitor blip that the provider did **not** roll up into a non-operational aggregate otherwise produced `partialCount > 0` → a **phantom yellow Partial pill** that flapped in/out per poll while official showed all-green (Together AI, 2026-06-21). The intended #722 Partial case always has a non-operational aggregate, so it's preserved; only `operational` is gated. A `maintenance` aggregate deliberately falls through (a real degraded resource during a maintenance window is still a partial) — diverging from `parseBetterStackStatus`'s collapse-to-operational. Single chokepoint → covers both the live `/api/status` path and the cron-written `services:latest` (is-down SSR).

## No official uptime → no invented value (#713, supersedes the #653 estimate)

Services with **no official rolling uptime %** (`bedrock` — AWS Health events JSON; `azureopenai` — Azure RSS; incidents-only — plus the incident.io pages that publish no number, e.g. `stability`/`replicate`/`elevenlabs`) **show no uptime %**. AIWatch does **not** derive one. #713 removed `estimateUptimeFromIncidents` / `uptimeSource: 'estimate'` entirely (the prior #653 estimate, the #707 "No reliability incidents" wording, the 90-day `mergeIncidentsById` uptime merge, and the `score.ts` `assumedUptime = 36` fallback are all gone) — honoring the methodology's "official-first, no fabricated value" claim literally.

### incident.io uptime — the `$undefined` vs missing-config distinction (#857)

Two different reasons an incident.io service can end up with `uptime30d = null`, and only one of them is honest:

1. **The page publishes no number.** incident.io emits `"uptime":"$undefined"` in `component_uptimes` whenever the page runs `display_uptime_mode: 'chart_only'` (a 90-day chart, no percentage) — `stability`, `elevenlabs`, `replicate`. `parseIncidentIoUptime` returns null, and "No official uptime — incident-tracked" is the correct display. A `$undefined` component in a LIST is **skipped**, never read as `0`.
2. **We never looked.** `needsHtml` in `services.ts` fetches the status-page HTML only when a service sets `statusComponentId` **or** `incidentIoComponentId`. A service with neither never runs *either* uptime parser, so a published uptime is silently dropped. This is what happened to `turbopuffer`: its Statuspage-compatible `summary.json` made it look Atlassian, so it was configured with neither id — while the page (an incident.io page, `display_uptime_mode: 'chart_and_percentage'`) published uptime for all 15 region components the whole time. The score therefore ran on the `/60` no-uptime rescale (73/fair/medium) instead of `/100` (84/good/high).

**Telling the platforms apart** (a Statuspage-compatible `summary.json` does NOT mean Atlassian): Atlassian embeds `window.uptimeData = {…}` in the page HTML and uses 12-char component ids (`r7tngp2p3sjd`); incident.io embeds `component_uptimes` inside its `self.__next_f` RSC payload and uses ULIDs (`01K0Q5QSJV…`).

**Worst-of over a component list.** `parseIncidentIoUptime` accepts `string | string[]`; a list returns the **minimum** across the matched components, accumulated over every RSC chunk, mirroring the worst-of `statusComponentIds` badge (#379) and `parseIncidentIoComponentImpacts` (already list-capable). Used by `turbopuffer`, whose only components are per-region API endpoints with **no group aggregate** to read — a single region would report 100% while another region is down. Its `Dashboard` component is deliberately excluded from the list (not an API surface) — the same principle that keeps `langsmith`'s uptime on representative API surfaces only. The config type is `string | [string, ...string[]]`, so an empty roster (silently truthy, and therefore a silent uptime drop) is a compile error. Pinned by `turbopuffer-uptime.test.ts`.

**Rotation guard.** A list is a roster we expect to find whole, but incident.io ULIDs are not guaranteed stable — a rotated id simply stops matching on a **200-OK page**, so neither the source-liveness check (keyed on 4xx/5xx) nor the #135 component-miss alert (keyed on `statusComponentId`, which a list-configured service does not set) fires. A partial rotation would quietly shrink the worst-of to the surviving regions and could report a healthy 100% while a vanished region is down. `parseIncidentIoUptime` therefore **warns** when a configured id resolves to nothing (list configs only — a single unmatched id is the ordinary "no such component" case). That warn only reaches Workers logs; routing it to the operator, and detecting the broader `uptime30d` non-null → null transition across all services, are tracked in **#957**.

### The monthly archive's `officialUptime` must agree with the Score (#951)

The archive carries three uptime-ish fields and they answer different questions, which is how the report came to print **"Official · 100.00% uptime"** beside a Score that had been rescaled over `/60` as if no uptime existed:

| field | source | window |
|---|---|---|
| `uptime` | AIWatch's own daily `ok/total` counters | the month |
| `officialUptime` | `computeMonthlyOfficialUptime` — a daily snapshot of `ServiceStatus.uptime30d` | *was* **any** day in the month; now the final days |
| `score` | snapshot of the **live** 30-day Score at build time (the 1st of the next month) | build day |

Two ways the display and the score drifted apart, both real:

1. **Pre-#713 estimate residue.** The daily counter stores `uptime30d` **without its `uptimeSource`**, so the incident-derived estimate that #713 removed (merged 2026-06-19) is indistinguishable from an official % in the snapshot. `computeMonthlyOfficialUptime` kept the **last non-null** value over the whole month — despite its docstring saying "as of the LATEST day" — so one pre-#713 day stamped a fabricated "official" figure on all of June 2026: Stability 100%, Replicate 99.34%, ElevenLabs 99.18%. The build-time Score, computed after #713, had already dropped uptime.
2. **A source that dies mid-window.** Character.AI's Statuspage was deactivated (#689/#800), leaving a real-but-dead 99.58% behind the same way.

The fix is two layers, because they answer different questions:

- **`computeMonthlyOfficialUptime` now means what it said** — only the final `OFFICIAL_UPTIME_TAIL_DAYS` (3) days with data may supply the value. A figure last seen on the 17th is residue, not month-end data. Three days tolerates a transient status-page failure on the last day (the snapshot is that day's last cron cycle) without tolerating a source that went away mid-month. This removes both contaminations at their origin.
- **`resolveArchiveOfficialUptime` then requires the Score to have consumed it** (`scoreConfidence === 'high'` ⟺ `score.ts` `hasUptime`), so display and score cannot contradict each other. The archive also persists `scoreConfidence`, so the report labels the uptime source from data rather than a hand-maintained service list.
- **#1016 — the display value is the month-end daily snapshot ONLY; there is no live `services:latest` fallback.** It used to fall back to the build-time `uptime30d` when no daily snapshot existed, which meant `/api/admin/rebuild-archive` re-snapshotting a frozen month injected *today's* uptime into it — "Official · 100%" beside a `monthlyScore` that had dropped the uptime component (openrouter, June 2026: gained an incident.io uptime only after #1006 deployed, so its June snapshot is null but the rebuild read today's 100%). A month with no daily snapshot now reads `null`, which is what a no-official-uptime service should show. (The rebuild still re-snapshots `score`/`scoreConfidence` from live — that separate staleness is why a stale month should be patched in KV, not rebuilt.)

Two deliberate non-obvious behaviours in that gate:

- Withholding a month-end value the Score didn't consume **warns**. It is reachable without any contamination: `scoreConfidence` comes from ONE read of `services:latest` on build day, so a status-page fetch that fails on that read makes a service which published uptime all month read `medium` and lose its figure. The number is still withheld (a displayed uptime beside a `/60` score is the contradiction this issue exists to remove — and that archived score is wrong too), but discarding a month-observed figure silently would be the very defect being fixed.
- **No score data at all → keep the month-end value.** `scoreSvc === undefined` means `services:latest` was unreadable; the daily snapshots stand on their own and there is no score to contradict. Tying `officialUptime` to `scoreData` would let one parse failure erase every service's uptime from an archive the cron never rebuilds (it only builds when the entry is absent).

**Archives written before this shipped keep the contaminated values and are corrected out-of-band — do not reach for `/api/admin/rebuild-archive`.** It is not idempotent: it rebuilds `scoreData` from the **current** `services:latest`, so a historical month's scores are overwritten with today's. And because the gate above reads that same current `scoreConfidence`, rebuilding a month whose service has *since* lost its source (Character.AI) also withholds the uptime it genuinely published back then. Patch the `archive:{period}` KV entry directly instead.

Concretely:
- **Worker** (`services.ts`): when no official uptime is found, leave `uptime30d` null and set no `uptimeSource`. The card incident COUNT + Incident History stay the live `filtered` set.
- **Score** (`score.ts`): computed on the **AVAILABLE components only, rescaled to 100** — `(uptime? 40) + incidents 25 + recovery 15 + (probe? 20)` over the available max. A no-official-uptime service drops the 40-pt uptime component (no assumed value) and is scored on incidents + recovery (+ probe if any); `confidence` = `hasUptime ? 'high' : probe ? 'medium' : 'low'`. Backward-compatible (uptime+probe → /100 unchanged; no-probe → /80 = ×1.25 unchanged).
- **Display / ranking** (`src/utils/serviceReliability.js`, mirrored in `api/is-down.ts`): `noOfficialUptime(s) = uptime30d == null && !incidentSourceStale` → uptime card reads **"No official uptime — incident-tracked"** (`uptime.noOfficial`); `isUnreliableUptime = uptime30d == null || stale` blanks the uptime + excludes from the Uptime ranking; **`hasReliableScoreData = !stale && scoreConfidence !== 'low'`** for the **Score** ranking — a service is ranked when it has at least one substantial measured signal: confidence `high` (official uptime) or `medium` (no uptime but a real probe, e.g. Gemini/xAI/OpenRouter) stay ranked; only `low` (NEITHER uptime nor probe — Bedrock/Azure, scored on just incidents+recovery → over-scores under the rescale) is dropped (still shown on its detail page). `incidentSourceStale` (#591 frozen feed) is the separate "unknown, not just unmeasured" case and keeps the "Not provided" wording. The Score CARD (detail page + Overview) gates on `aiwatchScore != null && !incidentSourceStale` — NOT on `isUnreliableUptime` — so a probed no-uptime service (Gemini/xAI, score present) shows its score on every surface it's ranked on; only the *uptime %* display is blanked. #713 also deleted the dead estimate machinery entirely: `computeUptimeFromIncidents` + `resolveImpactWeight` (incident-io.ts) and `readArchivedIncidentsForService` (monthly-archive.ts) had no callers left once the estimate path was removed.
  - **#802/#870 — the not-ranked bucket is split by REASON** (`src/pages/Ranking.jsx` via `serviceReliability.isRecentlyAdded`): **"Recently Added"** (`ranks in Nd`) when a `<MIN_COVERAGE_DAYS` (30) service is either already scorable (just the coverage gate) OR its only gap is a **warming probe** — `isProbeWarming(s) = scoreBreakdown.responsivenessStatus === 'insufficient'` (a new probe target with <7d of samples, e.g. turbopuffer days 1-7: no official uptime by design + a probe that reaches `available` at ~7d → it WILL rank). **"Insufficient Data"** stays for genuinely un-measurable services — `responsivenessStatus: 'unsupported'` (no probe target ever + no uptime: Bedrock/Azure/apps/agents) or a stale feed. The distinguishing signal `responsivenessStatus` (= score.ts `ProbeContext.kind`, on `scoreBreakdown`) is exposed even when the score is withheld, so this is a frontend-only classification. `'unavailable'` (transient global probe-KV read failure) is intentionally NOT treated as warming.

### Uptime window label is source-neutral (#654)
The `uptime30d` field holds figures over **different windows by source**: `official` = the status page's published % over **its own (varying) window** (Anthropic status.claude.com = "past 60 days"; other incident.io/statuspage pages = 30/90), `platform_avg` = the **upstream platform's** window (BetterStack avg-of-resources / OnlineOrNot — not AIWatch-controlled). The official parsers read only the *percentage*, not the page's "past N days" window. So no surface claims a specific window: the card title is the neutral **"Uptime"** (`svc.uptime30d`) or the source-specific label ("Official Uptime" / "Platform Average"), the Uptime-page basis label is "reported uptime" (`uptime.basis`), and the is-down SEO meta/narrative say "Uptime: X%" (the "30-day"/"(30d)" qualifier was dropped). The **Score** keeps its "30-day" framing (`aboutScore.intro`, Ranking "30d basis") — `score.ts` genuinely computes over a 30-day window (`incidents30d` + daily counters), so that claim is accurate and is intentionally NOT changed.

## Supply-chain correlation banner (#574, Phase 1: AWS)

A LIVE banner correlating a cloud-region issue with dependent AI services — surfaced ONLY when an
**AWS infrastructure region is degraded AND ≥1 AWS-dependent AI service is degraded AND names THAT SAME
degraded region in its own incident** (#1000). Differentiator vs AIDown.io's *static* dependency map
(always shown, no live correlation) and vs a naive timing correlation (over-alarmist).

- **AWS region health** (`parseAwsRegionHealth`, `parsers/aws.ts`): derived from the SAME AWS Health
  public-events JSON the Bedrock fetch already pulls (`health.aws.amazon.com/public/events`, all AWS
  services) — **no extra subrequest**. Currently-active (unresolved) events per region, via the shared
  `awsHealthImpact` (so a #707 non-reliability advisory is excluded). **`BEDROCK` is excluded** from
  this signal (`AWS_REGION_HEALTH_EXCLUDE`) — it's an AI service we track separately, so counting it
  would make a Bedrock-only outage circularly read as "AWS down → may affect Bedrock". Attached to the
  bedrock `ServiceStatus.awsRegionHealth` (rides in `services:latest` → live + cached both have it).
- **Dependency map** (`SUPPLY_CHAIN_AWS_DEPS`, `supply-chain.ts`): curated AWS-dependent monitored
  services + confidence — bedrock (certain), Anthropic claude/claudeai/claudecode (high — public $100B+
  AWS Trainium/Bedrock commitment), huggingface + pinecone (medium). **Together was removed** (runs its
  own AI-native GPU cloud, not AWS — AIDown's 60% was wrong). Worker-side only (no client sync).
- **Attribution cross-check** (`buildSupplyChainBanner`, StatusGator-style) — **region-aware since
  #1000**: a degraded dependent is **`affectedNow` only if its OWN active incident (title +
  `componentNames` + timeline) names an AWS region that AWS ITSELF currently reports as degraded**
  (`awsRegionsNamedByService` ∩ the `awsRegionHealth` keys — a plain set intersection, no key is
  special-cased). Region tokens are matched by shape (`AWS_REGION_RE`: `<area>-<direction>-<n>`, with the `<direction>`
  vocabulary enumerated), not by a hand-kept list of full region names — the token is AWS-specific by
  construction (GCP writes `us-east1`, Azure `eastus`), so naming one IS the attribution. Incidents
  with `impact: null` are skipped (the provider itself claims no availability impact → it cannot be
  the cause), mirroring the AWS side where `awsHealthImpact` drops #707 advisories. An AZ suffix
  (`us-east-1a`) folds to its region. Verified empirically at #574 design time (2026-06): Pinecone
  tags `[AWS][us-east-1]` in 29/50 incidents (region-matchable), Anthropic 0/50 (so Claude only ever
  appears under `mayBeAffected`, never confirmed — correct). Healthy map members → `mayBeAffected`
  ("AWS-dependent · may be affected", hedged). **Gate**: ≥1 `affectedNow`, else null.
  - **Extraction reads the incident BODY, not just the title** — load-bearing, verified 2026-07-13.
    Hugging Face titles a real incident `Elevated error rate – AWS CDN (Singapore)` — a human place
    name, no token — and names the region only in the update body ("…in the Asia-Pacific (Singapore /
    `ap-southeast-1`) region"). Title-only extraction would leave HF permanently unattributable even
    though it explicitly blames AWS. Pinecone is the opposite, front-loading `[AWS][us-east-1]` into
    the title. Both shapes are covered because the extractor reads title + `componentNames` + timeline;
    the HF incident is pinned as a test fixture.
  - **Why region-aware** (#1000): the original gate only asked *"does the incident mention AWS at
    all?"*, which let the banner's two halves disagree. On 2026-07-13 prod rendered "AWS infrastructure
    issue — me-central-1, me-south-1 · AWS-attributed: Pinecone" while Pinecone's only incident was
    `[Serverless][AWS][us-east-1] …` and us-east-1 had **no** AWS event — the regex matched on the
    bare word `aws`. That is exactly the "both degraded at once" coincidence the cross-check exists to
    eliminate. Its region list had also gone stale (no `me-`/`ca-`/`sa-`/`af-`/`il-`/`cn-`/`mx-`/
    `us-gov-`/`ap-east-`/`eu-north-`/`eu-south-`), though that alone was mostly harmless — the bare
    `aws` alternative caught those incidents anyway. Shape-matching just removes the upkeep.
  - **Bedrock has no special case** (removed in #1000). It is AWS-native and its incidents come from
    the AWS Health feed with `componentNames: [region]`, so its regions parse out like anyone else's.
    The old `id === 'bedrock' → always attributed` shortcut would have preserved this very bug for
    Bedrock (an outage in one region rendering under an unrelated region's infra event).
  - **Region-less attribution is fail-closed**: an incident that blames AWS with no region ("our
    upstream provider is having issues") is NOT attributed. The banner's headline is region-scoped, so
    listing a service under regions its own status page never mentions would re-create the claim this
    gate removes. We under-claim rather than assert an unverifiable cause.
  - **`global` events deliberately do NOT correlate.** AWS files its region-less services (Route 53 /
    IAM / CloudFront / STS) under `region: "global"`, which `parseAwsRegionHealth` passes through as a
    key — but `awsRegionsNamedByService` only emits `<area>-<direction>-<n>` tokens, so `global` can
    never enter the intersection whatever an incident says: a global-only event never joins and the
    banner stays silent. Treating it as a wildcard ("degraded everywhere → it cannot contradict
    anyone") was implemented and **reverted**: non-contradiction is not corroboration. It let an active
    CloudFront advisory attribute Pinecone's routine `[AWS][us-east-1]` freshness lag — #1000's
    headline again with `global` in place of `me-central-1`. The AWS outages that actually move
    dependents are filed per-region, so the regional path covers them; we under-claim instead.
  - `regions` is **narrowed to the correlated regions only** — a degraded AWS region that no affected
    service named is not part of the story, does not appear in the headline, and does not feed
    `severity` (an uncorrelated `down` region must not inflate a `degraded` banner to red).
  - The `<direction>` vocabulary in the regex is enumerated, so a bare `[a-z]+` cannot pull a cert id
    or DNS record (`ca-cert-1`, `mx-record-1`) in as a "region". The `∩ awsRegionHealth` join already
    makes such a token inert — this is defence in depth, and it costs nothing since every real AWS
    region reuses the same vocabulary.
- **Surfaces**: `/api/status`(+cached) `supplyChainBanner` field → dashboard `<SupplyChainBanner>`
  (Overview, above the summary cards) + an is-down per-service note (`affectedNow` → "attributes it to
  an AWS/upstream issue"; `mayBeAffected` → "runs on AWS and may be affected"). is-down SEO title/verdict unchanged.
- **Verify**: rare-but-accurate by design (fires only on a real AWS event where a dependent
  self-attributes **in that region**). The #574 signal first fired 2026-07-13 and was a false positive
  — hence #1000. Tune `AWS_REGION_RE` against observed phrasings if a real region token is ever missed.
