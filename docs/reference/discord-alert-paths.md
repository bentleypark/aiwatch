# Discord Alert Delivery Paths

> Extracted from CLAUDE.md to keep the auto-loaded project file lean. CLAUDE.md links here; this is the canonical reference for how Discord alerts reach the operator and per-user webhooks.

## Two Discord alert paths (#467, #475, #486)

1. **Operator** — the `*/5` cron posts to the single `env.DISCORD_WEBHOOK_URL` secret (always on for the operator).
2. **Per-user** — a visitor's own Discord webhook (Settings → Alerts), delivered **server-side** by the same cron via `deliverToSubscribers` (`worker/src/webhook-subscriptions.ts`) — tab-independent (#486 PR3 replaced the old browser relay).

### Operator phone-push side-channel (#778)
Independent of Discord, immediately after the operator Discord send the cron fires an **ntfy.sh phone push** (`sendPushAlert`) when `pushTargetFor(alert, scored)` returns a target — gated to a **NEW** (`alerted:new`) **down/degraded** (incident impact non-null, never informational) **non-advisory** (the shared `isNonOutageAlert` predicate, #1184) incident on a **PUSH_SCOPE** service (`claude`/`openai`/`gemini`/`chatgpt`/`claudeai` — deliberately narrower than the #777 search scope; `claudecode`/`codex` excluded as low-virality). Purpose: the operator Discord buries a real Tier-1 outage under every other monitored service's noise + daily/changelog/security reports, and the Twitter-reply window is short (~1–2h) — a `Priority: urgent` push that fires *only* for the high-value moment cuts through. The ntfy `Click:` header is the #777 `buildTweetSearchUrl` Top-search URL, so **push → tap → viral "is X down" tweets to reply to**. Config: `NTFY_TOPIC` secret (bare topic name or full `https://ntfy.sh/<topic>` URL); absent → **fail-soft skip** (the Discord alert is unaffected). The push is in its own try-guard isolated from the operator send, ntfy headers are ASCII-only (no emoji in title/body), per-incident dedup is inherited from the `alerted:new` roster (one push per incident), and v1 is new-incidents-only (no recovery push). Operator-only — never reaches the per-user path.

### Reddit engagement links (#1182) — operator-only block on the incident embed
Appended after the #777 X-search block by `appendRedditSection`, from `buildRedditEngageTargets(alert, scored)` (`worker/src/alerts.ts`). Same operator-only boundary as the tweet draft — it is added to `operatorDescription` only, never to the per-user feed entry, pinned at source level by `reddit-engage-wiring.test.ts` (`reddit-engage.test.ts` deliberately does not — a literal-vs-literal assertion there could not fail). Build **and** render sit inside one try/catch: the dedup keys are written long before the send, so a throw here would lose the alert permanently and skip every remaining alert in the cycle.

**It performs no Reddit request.** That is the whole design. #1138 wants the *Worker* to search Reddit and pick the threads; measured from the Cloudflare edge, the Worker cannot — the unauthenticated listing feeds mostly return Reddit's per-IP 429 and `search.json` is a flat 403. The egress IP is shared with other Cloudflare tenants, so the limit is not ours to back off from. The run, with its dates and denominators, is in [marketing-playbook.md §Reddit](../marketing-playbook.md#reddit). A link the **operator** opens in a browser is subject to none of this, so the block is pure string-building and is unaffected by #820's pending Data API approval.

Per in-scope service the alert covers, the block renders scoped in-sub searches (`sort=new&t=day`), an **all-of-Reddit** search, and the `?utm_source=reddit` is-down reply link (same `appendStatusHint` + `appendUtm` construction as `formatRedditAlert`, so both Reddit surfaces attribute identically). The all-Reddit link is not redundant: most subreddits carrying outage posts contributed only one or two, from communities no fixed list would carry, so the sub list alone cannot reach the tail. The playbook's posting caps render with the block.

Scope is `REDDIT_ENGAGE_SUBS`, whose keys are pinned equal to `TWEET_SEARCH_TERMS`' keys (`reddit-engage.test.ts`) so the Reddit and X channels cannot drift apart — the builder needs both a sub list and a search phrase, so a key in one map and not the other would silently render nothing.

**Gated by `isNonOutageAlert`**, exactly like the tweet draft, X-search and reply draft: an advisory (#1021) or a withdrawal (#1106) renders no block at all. Handing the operator "go find the outage threads" links when AIWatch is not claiming a live outage invites confirming one that is not happening.

**Two limits it does not solve**, stated because silence would read as coverage: a sub's own rules may remove the very threads these links search for (r/ChatGPT Rule 2 names "Is ChatGPT down?" posts) — a removed post drops out of the listings, and whether it also drops out of search results is unmeasured, so an F5Bot alert remains the primary entry; and a service in neither scope map renders nothing forever with no signal, since the parity test passes when both maps are equally wrong.

Length-guarded against the 4096-char embed cap. When the section is dropped for space the cron logs a scoped `#1182 reddit section dropped (embed cap)` warn — otherwise that outcome is byte-identical to "no targets" and unanswerable from the logs later.

### New status-page component detection (#992) — operator ops alert
A cron-only operator alert (webhook only, never per-user), sibling to the #135 component-**miss** alert but the **inverse direction**: #135 fires when a *configured* id disappears (migration); this fires when an *unseen* id **appears** (a provider added a component AIWatch should decide whether to track). Data is free — `fetchAllServices` returns `pageComponents` (apiUrl → `{id,name}[]`, built by `buildPageComponents`) harvested from the live prefetch; the cron diffs each page against the durable `component-seen:{apiUrl}` KV snapshot (`diffPageComponents`).

**#1125 — what "this page's components" means, and who gets asked about them.** The list resolves through `pickBreakdownComponents`, the same precedence the badge/breakdown uses (`componentsUrl`'s components.json when readable, else summary.json). It previously read summary.json alone, which on `status.openai.com` serves only part of the page and rotates which part — so a component AIWatch already tracked false-alerted as new when it rotated in (`Images`, `Sora`), while one that never entered that window could not alert at all. The first-seen set is then split by `partitionFirstSeen` against `TRACKED_COMPONENT_IDS` (the ids named by `statusComponentId`/`statusComponentIds`/`displayComponentIds`/`incidentIoComponentId`/`incidentIoGroupId` plus the #1072 upstream feeds), and only the unrecognised half is alerted on, because *"decide whether to track it"* has no answer for something we already read; a page that tracks components without NAMING ids (`displayAllComponents`, or a name-matched `statusComponent`) contributes none and still alerts. That filter is what makes a narrower list harmless: if components.json is unreadable and the fallback list is short, the cost is DELAY — whatever it later reports as new is by construction untracked, i.e. a correct alert arriving when the component rotates into view. The one thing `buildPageComponents` will not do is record an entry without a string `id` (it drops it, and names it in a warn): `JSON.stringify` writes an `undefined` id as `null`, which no later `seen.has()` can match, so recording one would turn the once-ever alert into one every cron tick, naming `undefined`. The filter governs only what is **said** — `component-seen` still unions every current id, so a silently-recorded component can never come back as an alert later. **First sight of a page bootstraps silently** (records ids, alerts nothing) so a rich shared page (status.openai.com) never dumps its existing components as "new"; thereafter each genuinely-new id → **one** 🆕 heads-up, ever (the snapshot unions it, so it never re-fires; a removed-then-re-added component stays silent). The body (`formatNewComponentAlert`) lists the new component name+id and the AIWatch services on that page; for a `displayAllComponents` page (cerebras) it says *already auto-tracked — heads-up only*, otherwise it points to the `statusComponentIds`/`displayComponentIds` config to edit. The snapshot is persisted **only after a successful send**, so a Discord failure retries next cron rather than dropping the one-shot alert — except on the all-already-tracked path, which has nothing to send: it persists first and logs only if that write succeeded (otherwise the same set would be re-evaluated every cycle). A fresh-cache cron cycle (no live fetch) leaves `pageComponents` empty and simply skips — detection runs on the next stale-triggered fetch. Pure `diffPageComponents` + `formatNewComponentAlert` unit-tested in `utils.test.ts`; `buildPageComponents` + `partitionFirstSeen` + their cron wiring in `page-components-source.test.ts`.

### Partial component resolve (#1179) — operator ops alert
The third member of the component-drift family, and the one the other two could not see. #135 fires when the **primary** `statusComponentId` disappears; #992 fires when an **unseen** id appears; this fires when a service's badge is resolved from **some but not all** of its `statusComponentIds`. `resolveSvcStatus` drops the ids it cannot find and returns a worst-of over the survivors, so its value cannot say that it judged only some of them — and an outage on any of the rest reads as `operational`. Before this, the secondary ids were a `console.warn` with no operator path.

**Scope: the partial case only.** When *no* configured id resolves, `resolveSvcStatus` returns the page's overall indicator rather than a worst-of, so there is no narrowed badge for this alert to describe and `fetchService` raises nothing. `anyResolved` is therefore computed over the **full** id list, primary included — that is the condition `resolveSvcStatus` itself branches on, and `missing` cannot stand in for it because it omits the primary. The `console.warn` enumerating the unresolved ids is deliberately *not* behind that gate: for most of the roster it is the only enumeration there is. Note a page that serves no `components` key at all lands here too, and #135's own check is likewise guarded on having a component list — so an absent array is covered by neither alert.

**Why it is not an extension of #135.** Two properties are load-bearing. It uses its own KV key (`component-partial:{svcId}`), because reusing `component-missing:` would interleave with the primary path's `resetComponentMiss` inside a single cycle and the #135 body names `statusComponentId` — the wrong id here. And it is **time-based, not count-based**: `fetchAllServices` runs on every `/api/status` request (60s browser polling), as well as the cron when its snapshot is stale, so #135's 3-consecutive-miss threshold is minutes of wall clock under live traffic, and `status.openai.com`'s rotating `summary.json` window (#1125) would page on a single rotation.

**Report-and-expire, not track-and-clear.** `trackPartialResolve` is a *report* of a live partial resolve: a clean cycle calls nothing, does not read, and does not write, and **nothing ever deletes the record** — it retires when its TTL lapses because reports stopped. An earlier revision cleared it on the first clean cycle instead, which on a flapping `components.json` reset the clock every poll and could not fire at all. Alerting needs both halves of the record — `since` at least 6h old (`PARTIAL_RESOLVE_THRESHOLD_MS`, via the shared `elapsedAtLeast` primitive that also backs the #500 persistent-failure alert) and `updatedAt` newer than `PARTIAL_RESOLVE_STALE_MS`, which is what makes "and it is *still* happening" decidable rather than assumed. A status page that cannot be fetched at all reports nothing either way; that is #500's alert, not this one.

**The horizons.** Reports further apart than `PARTIAL_RESOLVE_TTL_S` never join — the record expires between them and `since` restarts. That cuts both ways: below the 6h threshold, a real-but-sparse drift could never reach it at any duration; far above, two isolated blips hours apart would merge into one reported span. The TTL therefore sits just above the threshold, not comfortably above. And because `updatedAt` may lag the last observation by up to the refresh throttle, a drift that stopped within roughly `PARTIAL_RESOLVE_STALE_MS` can still page once. The constants' ordering is asserted in `partial-component-resolve.test.ts` so a later tightening of any one of them cannot silently reopen a horizon.

**Writes.** Refreshes are throttled to `PARTIAL_RESOLVE_REFRESH_MS`, so a drift does not write on every poll, and a steady state with every id resolving costs nothing at all. `missing` is stored as the **union** of every id seen unresolved since `since`, and `viaSummary` latches on rather than flapping, so neither a rotating window nor an intermittent `components.json` turns an observation into a per-poll rewrite. Both latch, which is why the alert body scopes its claims to the window rather than asserting a present-tense blind spot for every id it lists. `trackPartialResolve` **fails closed on a KV read fault** — reading a rejected `get` as "no record" would rewrite `since` to now every failing cycle, so the clock could never mature (same hazard and same posture as the #992 detector's `component-seen` read). `detectPartialResolves` takes the opposite posture on each of its two reads, deliberately: a fault on the *record* read skips that service (silently reading it as "no drift" would disarm the alert itself), while a fault on the *dedup* read re-pages rather than dropping the page. Both are logged.

**Coverage and body.** The roster (`PARTIAL_COMPONENT_SERVICES`) is derived from `SERVICES`, so any service configuring a non-empty `statusComponentIds` enrolls itself — both the `componentsUrl` group and the group resolving against `summary.json`. `formatPartialResolveAlert` names the ids that did not resolve, because the badge value cannot. It claims **#1175 has reverted** only when the resolve was *observed* falling back to the summary window (`viaSummary`, recorded by `fetchService`) — not from the mere presence of a `componentsUrl` in config, since a provider deleting one id from a perfectly readable `components.json` produces the same missing set and would send the operator to debug a working fetch. The Discord send gates its 24h dedup key on success (`sendDiscordAlert` returns `false` rather than throwing, so an unconditional write would swallow the page on a 429), matching #500/#992. Pure fns + the `fetchService`/cron wiring are unit-tested in `partial-component-resolve.test.ts` — including an end-to-end flap simulation, since "an intermittent drift still pages" is the property this mechanism was rebuilt around and no unit of it demonstrates that alone. The degraded path itself stays pinned in `page-components-source.test.ts`.

### Single source of truth (#475)
The cron appends every embed it sends the operator to a rolling KV feed (`alert:feed:recent`, built in `worker/src/alert-feed.ts`), surfaced as the `alertFeed` field on `/api/status` (+`/cached`) for external readers. In the same cron cycle it fans those exact entries out to confirmed subscribers, so operator/user alerts are **byte-identical** (Detection Lead, AI analysis, grouping, fallback, region all included) and duplicate suppression — incl. the #473 cross-poll status↔incident race — lives server-side.

Consequence: user alerts fire at **cron cadence (≤~5min, same time as the operator)** whether or not a tab is open. The two target *different* webhooks (no cross-source dupe).

- Per-subscriber delivery is isolated (`Promise.allSettled`) — one dead webhook never blocks the rest. Dead webhooks (Discord 410/404, or `MAX_FAIL_COUNT` consecutive failures) are pruned. Per-sub per-alert dedup via `webhook:sent:{hash}:{alertKey}` (2h).
- `postEmbed` re-validates the decrypted URL with `isAllowedAlertWebhook` (defense in depth) before POSTing.
- `/api/alert` is a CORS/SSRF-guarded Discord proxy (Discord hosts only, #468) — still used by the Settings "Send test alert" button.
- Slack subscriptions use Slack's native `/feed` RSS app (no webhook stored). **#724 — the `/feed` item structure is aligned with the Discord operator embed**: it carries the 🤖 AI analysis summary (the `/feed` handler reads `ai:analysis:*` for active incidents → `RssAiAnalysisMap`), uses a **provider-grouped title** for shared incidents (mirroring "Anthropic (Claude API, claude.ai, Claude Code)"), and ranks "Try instead" identically (the handler attaches `aiwatchScore` to `services:latest` via `scoreFor` first, since `getFallbacks` needs it). The feed is **public**, so the operator-only 🐦 tweet draft — and its #777 companion `🔎 FIND TWEETS TO REPLY TO` block (an `is {service} down` Top-tab X-search link to find the viral outage tweet, plus ONE casual copy-paste reply for replying to it) — are deliberately never emitted there (Discord operator embed only, appended after the per-user feed entry is built). **#936** — the reply is no longer an in-embed ``` code block (one-click copy on Discord DESKTOP only; mobile long-press copies the whole embed). The embed now shows a one-line pointer (`💬 REPLY DRAFT in the message below ↓`) and the cron sends the reply text as its **own plain-text operator message** right after the embed (`sendDiscordMessage`, `flags:4` SUPPRESS_EMBEDS), so mobile "Copy Text" grabs exactly the reply. Operator channel only; isolated try-guard (a send failure never affects the alert). `buildReplyDraft` also now leads the reply with a status circle (🔴/🟠/🟢). Delivery model still differs: Discord is real-time cron push; Slack `/feed` polls on its own cadence. **#759/#768 — Slack /feed dedup hardening**: Slack dedups by guid but re-notifies on item *content* change, and historically posted a freshly-detected incident BEFORE its AI analysis landed, then re-posted it on each status transition. #759 **holds** an AI-less active item (≤6 min) so the first post carries AI; #768 makes the active item's description **status-invariant** (severity + impact label + AI + fallback only — no status word / running duration / per-update timeline text, which now render on the resolved item only) so investigating→identified no longer re-posts. Net per incident: 1 active post (with AI) + an optional monitoring re-post (AI dropped by #724) + 1 resolved post.
- Per-user filter honors `alertCondition` (`down`/`all`, #470) + `alertTarget` (`all`/`custom` picker) + `alertIncidents` (default on); the filter (`shouldDeliver`) is byte-parity with the former client `shouldRelay`.
- **Per-user link target (#726)** — a deliberate exception to byte-identical (alongside the operator-only tweet draft): the stored embed's "View on AIWatch" link is the **operator dashboard** (`ai-watch.dev/#{svc}`), correct for the operator; the per-user relay rewrites it to the **is-down page** (`ai-watch.dev/is-{slug}-down`) via `toPerUserEntry` before `postEmbed`, since general subscribers want the friendlier public page (matching Slack `/feed`). The is-down URL comes from the shared `isDownUrl` (rss.ts, single source of truth); `NO_IS_DOWN_PAGE` services (bedrock/azureopenai) keep the dashboard hash. **#936** — both the operator link and the rewritten per-user link are UTM-tagged (`utm_source=discord&utm_medium=notification&utm_campaign=outage`, via `appendUtm`) so alert clicks attribute to the notification channel instead of `(direct)`; the tag's query goes before the `#` on the dashboard hash link, and `toPerUserEntry`'s regex tolerates that query. Operator delivery is a direct cron post (not via `deliverToSubscribers`), so its link is unchanged.

- **Auto-monitor repeat bursts — the `autoMonitor` tag (#983)** — a provider whose Statuspage auto-monitor opens a **brand-new incident per blip** (same title, minutes long) defeats both existing suppressors: `flapSuppression` matches only the BetterStack `— down`/`— recovered` title shape, and `holdShortIncidents` bails on `impact === 'major'` — which Statuspage assigns whenever ONE sub-component reads `major_outage`. Twelve Labs published four such incidents in 7 hours on 2026-07-09 → **4 New + 4 Resolved** operator messages. The fix tags the incident at the source (`ServiceConfig.autoMonitorTitles` → `Incident.autoMonitor`, see [status-determination.md](status-determination.md)); on the alert path the tag makes the incident **hold-eligible and flap-suppressible regardless of `impact`**. Net for that burst: the sub-`FLAP_HOLD_MS` (9min) blip is swallowed entirely (neither New nor Resolved — the #835/#792 accepted symmetry), and a repeat inside the 60-min `alerted:flap:` window is deduped, leaving ~2 alert pairs instead of 4. **`critical` and Tier-1 are never held**, tagged or not.
  - **`FLAP_SUPPRESSION_ESCAPE_MS` (30min) — a flap is SHORT by definition.** Tagging a service's `major` incidents as flap-suppressible created a new exposure: flap suppression silences **both** halves (New *and* Resolved) of any same-titled incident inside the 60-min window, so a genuine sustained outage that reused the machine title minutes after a blip could have been muted for up to an hour. `isFlapSuppressible` now **escapes** any incident whose *run length* (`incidentRunMs` — `startedAt`→`resolvedAt`, or →now while ongoing) reaches 30 min, which is comfortably past every auto-monitor blip observed on either platform (5–16m). The escape is symmetric across the ongoing and resolved halves, so an escaped incident that alerted New can never lose its Resolved and strand an "ongoing" card. It **generalizes** to the pre-existing BetterStack flap services (modal/together/huggingface/luma/helicone; fireworks left this group in #1198 — migrated to incident.io, opted into `holdShortIncidents` instead since its titles no longer carry the "— down/recovered" suffix `isFlapNotice` matches on): a 3-hour `— down` is no longer treated as a flap there either, and a first sight of an already->30min incident on those services now alerts instead of being held. Because this feeds a *suppression* guard it **fails open**: an unparseable `startedAt` returns `Infinity` (→ escapes → the alert ships) plus a `console.warn`, since returning 0 would pin a real outage below the threshold on every cron cycle and mute it for the whole window; an unparseable `resolvedAt` degrades to measuring against now; only a *future* `startedAt` (clock skew) clamps to 0, and it self-corrects as `nowMs` advances. `nowMs` is a **required** parameter, not optional — an optional clock would let a call site silently keep the old always-suppressible behavior and reproduce the exact silent drop the guard exists to prevent (#970).
  - **Suppression is logged.** The cron emits `[cron] #283/#983 flap-suppressed (same-title window active): <svc> <incId> autoMonitor=<bool> "<title>"` whenever it drops an incident into `suppressedIncIds` via the flap window. Dropping there kills BOTH the New and the Resolved alert, so without the line a post-incident triage cannot distinguish *"AIWatch suppressed it"* from *"AIWatch never saw it"* — the exact forensics gap #970 hit.

- **Discord and Slack DISAGREE on sub-poll-interval incidents, by design (#983)** — expect this and do not chase it as a dedup bug. Discord is a **cron push**: the `*/5` handler sees every incident that exists at any tick, so a burst of four 5–16m incidents produces four alerts. Slack `/feed` is a **poll**: the `active` item exists only while the incident is live, and #793's orphan-resolution guard suppresses a `resolved` item whose `active` was never served (no `feed:active-emitted:{incId}` marker). Slack's RSS poller backs off to a long cadence (#860, a Slack-side behavior AIWatch cannot influence), so during the Twelve Labs burst it missed three of the four live windows entirely and emitted **one** item — the fourth incident's resolution. Symptom to recognize: *"Discord alerted N times, Slack once and late."* Both surfaces are behaving correctly; only the Discord side is worth suppressing (which #983 does).

- **Service-status edge alerts are a Tier-1-only safety net (#767)** — `buildServiceAlerts` (🔴 Service Down / 🟠 Partially Degraded / 🟢 Service Recovered, which fire only in the incident-less gap `!hasOngoingIncident`) is emitted **only for claude/openai/gemini** (`API_TIER[id]===1`). Non-Tier-1 services rely on the canonical incident alerts (`buildIncidentAlerts`) alone — the status-edge alert otherwise produced a redundant second message when the provider flipped its status indicator one cron cycle before publishing the incident object (the #759 AssemblyAI "Service Down" 6:18 → "New Incident" 6:23 double). Tier-1 keeps it so a Tier-1 hard-down with NO parseable incident still pages.

- **Informational (`impact: none`) incidents DO alert, and look different (#970)** — a provider can open an incident that degrades no component (Statuspage `impact: none`), e.g. Runway's 2026-07-08 "Aleph 2.0 delayed generations". These used to reach **no channel at all**: `filterByComponentStatus` dropped the ACTIVE incident because the service's own component was still `operational` (see [status-determination.md](status-determination.md) rule 6), so `buildIncidentAlerts` never saw it — and the resolved path needs a prior `alerted:new:` roster entry, so the 🟢 Resolved alert stayed silent too; the incident only appeared on the dashboard once it resolved. Now such an incident alerts when it names a component in the service's badge group. Consequences to expect in the operator channel: the embed is the normal `🔴 {service} — New Incident`, but (a) the **service badge stays `operational`** (correct — the provider degraded nothing), so `buildIncidentAlerts` attaches **no "Try instead" fallback block** (it gates on `firstSvc.status !== 'operational'`), and (b) the **#767/#778 phone push never fires** (`pushTargetFor` requires `inc.impact != null` — informational incidents are explicitly out of scope). Slack `/feed` emits the active item as usual. So an `impact: none` alert is a *notification*, not a page.

- **Non-reliability ADVISORIES alert informational, not as a red outage (#1021)** — a usage-limits / quota / billing / deprecation notice a provider posts as a status-page "incident" (the live case: Codex's "Usage Limits Depleting Faster Than Expected") is NOT an availability outage — `downclassifyAdvisoryIncidents` down-classifies it to `impact: null` at the `fetchAllServices` choke point (see [status-determination.md](status-determination.md)). On the alert path `buildIncidentAlerts` then **reframes it** (keyed on `isNonReliabilityAdvisory(inc.title)`, the same title classifier, NOT on `impact == null` — so a mis-parsed null-impact REAL incident keeps the outage alert): the embed is **`ℹ️ {service} — Advisory`** in **blurple `0x5865F2`** (vs `🔴 … — New Incident` red), carries **no "Try instead" fallback** and **no region-switch hint**, and the resolved counterpart is **`ℹ️ {service} — Advisory cleared`** with **no duration** (an advisory's up-time is not downtime). The alert carries an **`advisory: true`** flag, and the **entire #777 operator viral-reply toolkit skips it** through the shared **`isNonOutageAlert`** predicate (for an advisory that leaves the service `operational`, a reply draft would otherwise emit a factually-FALSE "🔴 yes — {name} is down right now"). The **#778 phone push** is silent too, and was before #1184: `pushTargetFor` requires `impact != null`, which the down-classification above already guarantees an advisory fails. **#1184** added the shared predicate to it as well, changing no outcome — so the silence is `pushTargetFor`'s own stated rule instead of a consequence of `downclassifyAdvisoryIncidents` in another module. It is not a second defense against advisory *misclassification*: both gates read the one `isNonReliabilityAdvisory` predicate, so if that stops matching a title they open together. The dedup `key` is unchanged, so the paired resolved alert still matches. The Slack **Discord `/feed`** + #486 user webhooks inherit the reframed alert object, so they reframe too; the public **RSS `/feed.xml`** `severityEmoji` also returns **ℹ️** for an advisory-titled incident (instead of 🟡/🟢). Net: the operator/subscribers still learn a quota notice was posted, but it never masquerades as an outage on any surface. (Complements #1021's other half — the advisory is also excluded from `totalDowntimeMin` / the Score.)

- **A `monitoring` incident never fires a NEW alert (#1039)** — Statuspage `monitoring` denotes that the provider **applied a fix and is watching it** — the predicate the display/projection surfaces read as recovered. (That denotation is what the branch keys on; it is NOT by itself the justification for staying silent — see the interrupt-cost sub-bullet below.) `buildIncidentAlerts` gated its new branch on `inc.status !== 'resolved'` **alone**, and shipped a real **`🔴 OpenAI API — New Incident`** for an already-recovering incident on **2026-07-16**. The branch now also excludes `monitoring`, matching the predicate the **display/projection** surfaces already use (`incident-history.ts`, `statusline.ts`, `ext-claude.ts`, and several `index.ts` sites — one commenting it outright, *"monitoring = recovery confirmed"*).
  - **Not unanimous, and the exception is the mitigation.** `rss.ts` is the counter-example: only `status === 'resolved'` branches to a resolved item, so a `monitoring` incident emits a **live `active` item** on the public `/feed.xml` + Slack `/feed`, and `isActiveItemHeld` returns `false` for `monitoring` *specifically so it is never held* (#724 strips only the AI block, not the item). So the surfaces genuinely disagree: display treats `monitoring` as recovered, the feed treats it as active.
    - **The split is justified by interrupt cost, NOT by a reading of `monitoring` (#1091).** An earlier version of this doc argued the semantic case — Discord sides with the display surfaces because `monitoring` means recovered — and then justified that silence by pointing at the feed, which carries the same incident precisely because it reads `monitoring` as still-active. That is inconsistent: the silence was justified by reading `monitoring` as recovered, then mitigated by pointing at a surface that carries the incident only because it reads `monitoring` the opposite way. The defensible argument is asymmetry of **interrupt cost**, not of meaning. Discord/push is a **notification** channel (it arrives; at its sharpest it carries the #778 phone push, though `PUSH_SCOPE` is only claude/openai/gemini/chatgpt/claudeai — 5 services, a small fixed slice of everything else AIWatch monitors); `/feed` is **polled**, and that contrast holds for every service. Under genuine uncertainty about whether a `monitoring` incident still impairs users, a higher bar for the interrupting channel and a lower one for the polled channel is ordinary design. That justifies the higher bar — no more. Which FORM the bar takes is decided by the *Silence, deliberately* bullet: silence rather than a down-classed alert. The collateral loss of the resolved-surface markers is not a choice of form at all — it is a coupling in the roster (*Withheld*: `alerted:res:` also gates `markIncidentResolved`), accepted on the #633/#283/#929 precedent. Neither is entailed by interrupt cost. The feed carrying it is therefore a real mitigation of the residual risk below (`feed:active-emitted` is stamped, so the #793 resolved item still fires), but it is **not the reason** Discord is silent: it falls out of `rss.ts`'s own reading of `monitoring`, which predates #1039, and merely happens to land on the same side as a lower bar for a polled channel.
    - **Why not gate on the service's own status instead (#1091 option (b), REJECTED).** The obvious refinement — alert when the incident is `monitoring` but our component is NOT operational, i.e. "the provider says fixed, we say still broken" — is not a signal this gate can be built on, and the one real case does not settle it either way. On **2026-07-16**, `status-determination.md` records openai's badge as `degraded` off its own API-group Login component during this event, and the *Reachable without a joiner* bullet below records openai joining the incident only after the #1032 deploy changed its attribution — by which time the incident was `monitoring`. **Those two records do not share a timestamp**, and per-incident component status is not retained, so the conjunction cannot be confirmed exactly; the deploy sits between them by construction. Whether the component was still impaired at the `monitoring` transition is therefore **unresolvable from the record** — and a component returning to `operational` at `monitoring` is consistent with what that status denotes. So 07-16 does not settle the gate either way. **The rejection does not rest on it.** The flaw is that `svc.status` is **service-scoped**: with several incidents in flight it reports "something is wrong with us", never "THIS incident is still hitting us". The missing piece is a per-incident signal — the provider's per-component impact status — which no parser attaches to an incident per component: where a feed even carries one, the parser folds it into a single worst-of incident-level `impact` (#1093). A status-aware gate therefore depends on retaining that signal per incident, which #1093 tracks — a follow-up, not an alternative to this one.
  - **Reachable without a joiner.** The condition is only "first alert for this (incident, service) pair while the status is `monitoring`": a provider that posts an incident **after** mitigating, the `*/5` cron missing the earlier states on a short incident, a **#929/#835 or #882 hold releasing onto a now-`monitoring` incident** (`shouldHoldNewIncident` excludes only `resolved` — verified in code), or a **#545 joiner** (the 2026-07-16 path: the #1032 deploy changed openai's attribution mid-incident, so openai joined an incident chatgpt had already alerted, by then `monitoring`).

Emitting one only when we happen to FIRST see an incident at `monitoring` would invent an alert type that exists solely in the edge case — trading one inconsistency for another. And for the hold-release case there is no *good* alert available: firing would ship the `🔴 New Incident` framing this issue exists to remove.
  - **Withheld: the alert, the push, and — for a never-rostered incident — the resolved-surface markers.** The incident itself stays in `svc.incidents`: it still renders on the dashboard card + is-down and still counts toward the Score. That is the same set the #633/#283/#929 holds already forgo — `recovery-mark.ts` names this class explicitly (*"its surfaces stay dark. That is intended"*). Withholding the `new` candidate also drops the **#778 phone push for free** (`pushTargetFor` reads only `new`-keyed candidates), closing a leak the `impact != null` gate did not: a `monitoring` incident with `impact: 'minor'` used to page.

Only a service never rostered for that incident (i.e. the monitoring-first one) alerts on a reopen. The **resolved pairing is untouched**: `alerted:res:` is `alertedNewMap.has(incId)`-gated at the *incident* level, so a silent joiner still appears in the grouped 🟢 Resolved alert — accurate, since the incident did affect it. **Known wrinkle — introduced by #1039, tracked in [#1043](https://github.com/bentleypark/aiwatch/issues/1043):** the #486 per-user relay scopes by `svcIds` (`AlertFeedEntry.svcIds` → `deliverToSubscribers` → `shouldDeliver`), and the resolved branch groups **every** service holding the incident, so an openai-only subscriber in that joiner scenario receives a lone 🟢 Resolved with no prior New — a #793-shaped orphan on the relay (`/feed` has the `feed:active-emitted` guard for exactly this; the relay has no equivalent). Only the joiner path: without one, a monitoring-first incident is never rostered ⇒ no resolved alert either ⇒ no orphan. Accepted for now — it replaces a phantom red alert, so the current state still beats pre-#1039 — and NOT fixed by the obvious per-subscriber guard: `webhook:sent:{hash}:{alertKey}` has `SENT_TTL_S = 2h`, shorter than plenty of real incidents (the 2026-07-16 SSO one ran 3h+), so keying the resolved on "did this subscriber get the New?" would trade the orphan for a genuine silent drop. The roster (`alerted:new:{incId}`, 7d) is the right source; see #1043 for the `svcIds`-consumer trace that has to precede the change.
  - **Residual risk, accepted + observable:** an incident **first observed** at `monitoring` that is still impairing users is never announced on Discord/push (the normal path has no such gap — it alerted at `investigating`); `/feed` still carries it. Every withheld alert **logs** (`[alerts] #1039 …`), per the #970/#983 rule that a judgement drop must never be quiet, so triage can tell "AIWatch withheld it" from "AIWatch never saw it". The line describes a **state**, not an event — `buildIncidentAlerts` is stateless and a withheld alert is never rostered, so it reprints every cycle the incident sits in `monitoring` (same cadence as the #283/#983 flap line). **Line count is therefore not a frequency** (it is withheld-incidents × cycles-in-monitoring); count **distinct incident ids** to measure how often this actually fires. Taking the other side — "`monitoring` may still impair, so alert" — can attack either the denotation at the top of this section or the interrupting channel's bar, and the interrupt-cost sub-bullet above argues the bar the other way. An independent reason survives both: the consistency argument in *Silence, deliberately* — emitting only on a first-sight-at-`monitoring` would invent an alert type reachable solely from the edge case, which rests on roster mechanics, not on what `monitoring` means. (That bullet's OTHER argument — that firing would ship the `🔴 New Incident` framing — does rest on the denotation, and falls with it.)

- **New-incident AI-hold — hold-eligible services only (#882/#1148)** — the cron runs a new incident's AI analysis **inline with a cancellable 15s budget** (`INLINE_ANALYSIS_BUDGET_MS`; an uncancellable 8s `Promise.race` until #955) so it can merge into the embed. When that call overruns, the alert historically shipped **AI-less on BOTH surfaces** (operator embed + per-user relay are built from the same `description`), and since the send is fire-and-forget (no message ID captured) neither could be patched once the end-of-cron `refreshOrReanalyze` backfilled `ai:analysis` — so the alert permanently disagreed with the dashboard modal (which reads the backfilled KV). #882 applies the **#759 publish-before-analysis hold to the Discord push path**: on a fresh `alerted:new:` whose AI isn't ready, an incident on a service outside `NEVER_AI_HELD` is **HELD** (the send loop `continue`s before the roster write / feed append / send / push, stamping a write-once `pending:ai:{incId}` first-seen marker) instead of shipping AI-less. The next cron cycle's `refreshOrReanalyze` backfills the analysis; a later cycle's **KV-first read** (`ai:analysis` preferred over a fresh inline call — `formatAnalysisEmbedSection` renders both identically) then releases the alert WITH the AI section. Decision is the pure `shouldHoldForAiAnalysis` (`alerts.ts`): holds only when AI is genuinely pending (not `merged`/`no-model`/`generic` — those never get AI) and only within the bounded window (`AI_HOLD_MS = 10min ≈ 2 cron cycles); **past the window it fail-opens** (ships AI-less so an alert is never lost), and a KV-read error (`firstSeenMs=0`) also fail-opens. **A `NEVER_AI_HELD` service is NEVER held** — its alert ships at cron cadence. #1148 moved the exemption off `TIER1_IDS` into its own set, a SUPERSET of `PUSH_SCOPE`: the consumer apps were already push-worthy (#778), yet the hold `continue`s before BOTH the send and the push, so it delayed the phone alert that set exists to fire — the live 2026-07-23 ChatGPT alert landed ~17min behind the provider's post, far more than the ≤5min cron floor accounts for. It also adds four coding agents (`claudecode`/`codex`/`cursor`/`copilot`), where a late alert costs more than a missing AI paragraph the dashboard modal carries anyway; `windsurf`/`junie` and everything else stay hold-eligible. Push scope is unchanged — the two sets answer different questions ("wake the phone" vs "must be fast"). Held keys are excluded from the `alert:count:{date}` daily tally (they weren't sent). Net delay: **~5min typical** (only on a cycle where the inline budget actually overran — no hold when Gemma answers in time), **~10min worst-case then AI-less**; the dashboard/modal show the incident live throughout, so only the Discord alert is delayed. Distinct from the #633/#835 flap hold (`pending:new:`, which suppresses a *phantom* short/flap alert) — this holds a *real* alert briefly for completeness; the two markers never clobber (`pending:ai:` vs `pending:new:`). Slack `/feed`'s counterpart is the #759 `AI_HOLD_MS=6min` hold in `rss.ts` — which has **no service exemption at all** (`isActiveItemHeld` takes no service id), deliberately: a polled item cannot be edited without re-notifying Slack, so completeness beats speed there.
  - **Efficiency/safety details**: the inline AI call fires **only on the incident's first sighting** — a held incident on a later cycle relies on the KV-first `ai:analysis` read + `refreshOrReanalyze`'s backfill, so a hold doesn't burn a second Gemma/Sonnet call every cycle. And because the fail-open window can only elapse if the `pending:ai` marker persists, a **failed first-sight marker write fail-opens immediately** (ships AI-less) rather than risk an unbounded hold (a re-stamped first-sight window would never advance if the write kept failing AND AI never landed).
  - **Accepted tradeoff — a sub-cycle flash incident held then resolved emits nothing on Discord/feed** (code-review #882): a held incident whose roster (`alerted:new:`) was never written, if it **resolves within the hold window** (~one cron cycle, before `refreshOrReanalyze` backfills AI), fires **neither New nor Resolved** (the resolved branch is `alertedNewMap.has`-gated, which cleanly avoids a #793-style orphan "Resolved" but means the incident is silent on the alert surfaces). This is **symmetric with the already-accepted #835/#792 flap-hold** behavior (a held blip that self-recovers emits neither), now extended to any hold-eligible service. It requires BOTH an inline-AI overrun AND a sub-~5min resolution, the dashboard shows the incident live throughout, and such a brief outage is typically over before an alert would be read — so it's accepted, not fixed. (A `NEVER_AI_HELD` service is never held, so its flash incident still alerts immediately.)

- **🎯 recovery-prediction line — two placements (#827 F4 + #846)** — the "how our AI estimate held up" line (`🎯 AI prediction: 45m (within ~45m est.)`, from `predictedVsActualText`) appears on BOTH resolution surfaces, but was built in different places. Slack `/feed` renders it for **every** resolved incident carrying a numeric estimate (`rss.ts` `descHtml`, tier-agnostic). Discord originally attached it (`recoverySection`) **only** to the Tier-1 status-edge `alerted:recovered:` path (#827 F4) — which fires rarely (incident-less gap only) — so the canonical **`alerted:res:` "Incident Resolved" embed** (the resolution path for ALL services) showed no prediction, and Discord effectively never displayed it while Slack did. **#846** attaches the SAME single-line wording to the `alerted:res:` embed, computed live from the still-warm `ai:analysis:{svcId}:{incId}` estimate + the resolved incident's actual duration. The two surfaces now share `resolvedAtOf` + the `estimatedRecoveryHours == null → omit` gate (both in `incident-history.ts`) so wording and actual-duration derivation are identical; a missing/`N/A` estimate omits the line on both. The Discord block is best-effort (a KV/parse failure logs + omits, never aborts the send) and `!recoverySection`-guarded so it never double-emits alongside the Tier-1 path.
  - **#847 — corpus accrual fix**: the same `alerted:res:` block now ALSO writes the durable **#827 incident-history record** (`buildHistoryRecord` → `appendIncidentHistoryBatch`) for **each affected service**, so the corpus accrues on normal incident resolutions. It was previously written ONLY in the `alerted:recovered:` block (Tier-1 status-edge, incident-less gap) → normal resolutions recorded nothing, starving the accuracy ledger (F1/F3) + RAG corpus (F2). Idempotent (dedups by incId, so the two alert paths can't double-record); a grouped incident records once per surface (each surface's own RAG corpus grows), and `summarizeAccuracy` **dedups by incId** so the shared prediction is counted once — per INCIDENT, not per affected surface — in the accuracy metric.

- **⚪ Incident Withdrawn — the third terminal alert kind (#1106)** — a provider sometimes **deletes** an incident from its own status page instead of resolving it. Observed live on Mistral: `🔴 Mistral API — New Incident / Audio API Degraded` went to every channel on 2026-07-17, the incident was removed upstream ~4 days later, and **nothing ever closed the thread** — no Discord Resolved, no Slack/RSS resolution item, and the accumulator row was pruned. The resolved branch of `buildIncidentAlerts` requires the incident to be **present in the live list with `status === 'resolved'`**, which a deleted incident can never be again, so that branch is *structurally unreachable* here — this is not a bug in the resolved path but a case it cannot express. `buildWithdrawalAlerts` (`alerts.ts`) fills it, sourcing the `withdrawn.ts` tombstone the #975 prune leaves behind (the prune is the last moment the title + start time exist anywhere). Concatenated into the same `allAlerts` list the ordinary send loop drains, so operator + relay fan out unchanged; `alerted:wd:{incId}` is its dedup key, `AlertKind` gains `'withdrawn'` so `buildFeedEntry` carries it, and `'withdrawn'` is added to `INCIDENT_KINDS` in `webhook-subscriptions.ts` so the #486 per-user subscribers — the party actually holding an unclosed 🔴 — receive it under their existing `alertIncidents` filter. That last one is **not** free plumbing: `shouldDeliver` ends in `return false`, so a kind in neither set is silently dropped for every subscriber. Withdrawals are ordered **last**, because the send loop caps at 5 alerts per cycle and a retraction of a days-old incident must never evict a live `down` alert (a capped-out withdrawal simply retries next cycle — no dedup key is written for an unsent alert, and the tombstone lives 48h). Ordering `allAlerts` is **not sufficient on its own**: the array the cap actually slices is `mergedToSend`, and both merge fns return `[...rest, ...merged]`, so a collapsed live Together/xAI alert would land *behind* the ⚪ retractions that rode through in `rest`. They are therefore re-sunk to the tail after merging, and the test pins that array rather than `allAlerts`.
  - **Gated on `alerted:new:{incId}`** — only an incident AIWatch actually announced produces a withdrawal notice. Without that gate a withdrawal of an unannounced incident is a closing message for an event the subscriber never saw — the Discord twin of #793's orphan-resolution rule (the RSS half reuses `feed:active-emitted:{incId}` for the same reason). **The two halves fail in OPPOSITE directions, deliberately**: on a KV read failure Discord counts the incident as *not announced* and stays silent (a blip must not invent the premise that an announcement preceded this; the tombstone lives 48h, so the next cycle retries), while the RSS half fails **open** and emits, inheriting #793's documented trade that dropping a legitimate closing notice is worse than letting one orphan through. Note the marker's 7d TTL is a ceiling: an incident announced more than a week before the provider deletes it reads as never-announced. Every drop logs, and the log distinguishes a clean miss from a read error, so that case is diagnosable rather than invisible.
  - **Withheld unless the service is cleanly operational and readable** — `withdrawalHold`, applied by both channels (each to its own view of the live list: the cron's freshly-fetched `scored`, the feed's `services:latest` cache — the *rule* is shared, the input is per-channel). It returns a reason rather than a boolean, because the three mean different things to an operator: `republished-same-id` (the provider undid it — checked across **every** service, not just the tombstone's own, since one id routinely spans surfaces and a provider re-listing it on only some of them would otherwise put the same id in the feed as live *and* retracted at once, with the retraction borrowing the live surface's name through the provider-grouped title), `incident-running` (an unresolved incident is live, or the service is degraded/down), `source-unreadable` (`sourceDead`/`sourceUnknown`, or the service missing from this cycle entirely). Why each is needed: `incident-running` covers the #975 prune's *own* motivating shape — Pinecone deleted `xqp5fkvlyg6t` and re-published the same outage as `m3wrr6csl9jm` with a reworded title and a backdated start, so the old id is pruned and a naive reading would announce "withdrawn" while the outage runs on under a new id, which we cannot tell from a genuine withdrawal (differing ids, reworded titles — the reason #975 exists). Note the prune's guard 3 already requires a strictly-earlier live incident, so *"an earlier live incident exists"* is true on every prune and cannot discriminate — its **resolution status** can, since guard 3 is satisfied by resolved incidents too. The status half additionally covers the prune's OTHER documented residual (a still-open incident retitled out of `filterIncidents` attribution is absent from the incident list by definition, but leaves the service visibly impaired). `source-unreadable` exists because a failed fetch yields an EMPTY incident list, indistinguishable from "nothing is running" — without it the retraction would publish on exactly the cycle we could not read the page, and the other two tests would silently stop discriminating (same posture as #1004's `unknown` OG card: when blind, do not assert). In the evidencing Mistral case the service was operational with every surviving incident resolved, so the notice still ships. A hold is a **delay, not a loss** (48h roster × 5-min cron); it becomes a loss only if the state outlasts the roster, which the cron logs — both the hold (with its reason, every cycle, so read it as a state not a frequency) and the eventual expiry.
  - **Known reachability limit**: the whole feature is downstream of the #975 prune firing. A provider that deletes its *only* incident, or its *oldest* one, fails prune guard 3 (no strictly-earlier live incident) and produces no tombstone, no notice, and no line explaining why — so "the thread still didn't close" is not automatically this feature regressing.
  - **Carries no outage-promotion tooling.** That tooling says "this outage is happening, post it" and a retraction is the opposite claim, so producing any of it would be factually false at the moment it is posted. The shared `isNonOutageAlert` predicate gates every such builder, keyed on the alert's **kind** (`alerted:wd:` → `'withdrawn'`) rather than on a flag: the key already states the fact, `kindFromKey` is what every other consumer reads, and a parallel boolean would admit `advisory && withdrawn` — a state that cannot exist. `advisory` (#1021) stays a flag because an advisory's key is an ordinary `alerted:new:`, so nothing in it distinguishes one. The #778 phone push is already `alerted:new:`-only, so a withdrawal never reaches its non-outage check at all.
  - **Copy says withdrawn, never recovered** (`WITHDRAWN_NOTE`, one shared constant imported by `rss.ts` so the two channels cannot drift): *"The provider removed this incident from its status page without ever posting a resolution we could record. AIWatch has no recovery record — the report was withdrawn at the source, not confirmed fixed."* We do not know the service recovered; we know the record was removed, and claiming recovery from a deletion would invent an outcome the evidence never had. The "…without ever posting a resolution **we could record**" hedge is load-bearing: a provider that marks an incident resolved AND deletes it inside one 5-min cron window leaves no `resolved` snapshot and fires no `alerted:res:`, so the thread genuinely is unclosed — but a flat "without resolving it" would be false in exactly that branch. Colour is neutral grey — neither outage-red nor recovery-green, since either would make a skimming subscriber read the wrong event.
  - **Slack/RSS half**: a `withdrawn` `ItemKind` with a distinct guid (`aiwatch:{svcId}:{incId}:withdrawn`) so guid-dedup lets the retraction through as a new message. Its `pubDate` is the tombstone's `prunedAt`, **not** `now` — `weakFeedEtag` hashes the body and `<lastBuildDate>` derives from the newest item's pubDate, so a wall-clock value would change the bytes on every poll, defeat the #860 304, and re-notify Slack on every content change. `prunedAt` is still later than the active item's pubDate, which is what makes a reader treat it as new. No duration, no timeline, no AI block, no "Try instead": each would re-assert something about an outage whose only remaining fact is that the claim was withdrawn. The item's link carries `?e=withdrawn`, which **must** be registered in `HINT_TO_OG_STATUS` (`api/_is-down/html-template.ts`) — an unlisted token is silently ignored, which un-pins `og:url` and falls the card back to the LIVE status, i.e. a green "Operational" unfurl beside a message saying we have no recovery record. It maps to the grey `unknown` og style, and a lockstep test pins that exact value AND that `og.ts` really carries the style (a token mapped to a value `og.ts` does not know falls through to a green "Operational" image under a "Down Right Now" title). The tombstones are also folded into `buildIncidentServiceMap`, so a multi-surface retraction keeps the provider-grouped title its 🔴 had — that map is built from LIVE incidents, and a withdrawn incident is in nobody's live list, so without it Slack would show `⚪ Claude API: Withdrawn — …` where the original read `Anthropic (Claude API, claude.ai, Claude Code)` and where Discord's withdrawal alert still names all three. Withdrawal items are additionally capped per render (`MAX_WITHDRAWAL_ITEMS`): their `prunedAt` pubDate sorts them ABOVE every live active item and `WITHDRAWN_MAX` equals `MAX_ITEMS`, so without a cap a burst of retractions could push every running outage out of the feed — the RSS counterpart of ordering withdrawals last on Discord.

## #955 — why the AI section went missing (silent analysis failures)

The #882 hold assumes `refreshOrReanalyze` will backfill `ai:analysis` on a later cron cycle. Four
independent defects broke that assumption, and each was invisible on its own. Symptom: `ai:usage`
showed 7 of 16 calls `failed` on 2026-07-08 with **zero Sonnet successes on any day**, while
`ANTHROPIC_API_KEY` was set and correctly threaded to `refreshOrReanalyze`.

| # | Defect | Effect |
|---|--------|--------|
| 1 | `claude-sonnet-4-20250514` hardcoded in `ai-analysis.ts` **and** `monthly-narrative.ts` (pinned #21, 2026-03-26) reached its **2026-06-15 retirement** | Every Sonnet call 404'd. `analyzeWithSonnet` swallowed it (`if (!res.ok) return null`), so the fallback was dead for weeks |
| 2 | The cron's inline analysis was `Promise.race([analyzeIncident, 8s])`, but `analyzeWithSonnet` carried its own 10s `AbortSignal.timeout` | Sonnet only ever got the budget Gemma hadn't already spent, and the race **cancelled nothing** — a response landing at 9s was paid for, discarded, and booked as `failed` |
| 3 | No retry anywhere in the AI path. `analyzeWithSonnet` returned `null` on *any* `!res.ok` | A 429/500/529 (exactly the retryable classes) was treated identically to a permanent 404 |
| 4 | On failure, `refreshOrReanalyze` wrote `ai:reanalysis-skip:{svcId}:{incId}` with a flat **1800s** TTL | The five-minute cron skipped the next six cycles. The lock is per-INCIDENT, so one transient Gemma parse failure froze the incident for 30min. It outlived `AI_HOLD_MS` (~10min), so the held alert was *guaranteed* to ship AI-less |

Observed timeline before the fix — a non-Tier-1 incident could never get its AI section:

| t | what happened |
|---|---|
| 0 | first sight → inline 8s race → Gemma fails → Sonnet cannot finish → `null` → `failed++`, #882 hold starts |
| 5m | `firstSight=false` → no inline call (#882 avoids double-spend) → `refreshOrReanalyze` tries → Sonnet 404 → `null` → **30min lock written** |
| 10m | `AI_HOLD_MS` expires → alert ships **AI-less** (fail-open) |
| 10–40m | lock active → `result.skipped`; nothing runs |
| 40m | retry → same 404 |

Fixes, in the same order: the model id + request shape moved into `anthropic.ts` (one place, pinned by
test — Sonnet 5 also gets an explicit `thinking:{type:'disabled'}`, since omitting it selects adaptive
thinking whose tokens come out of `max_tokens`; a determinism guard, not a fix for an observed
truncation — see the verification note below); the inline race became a real `AbortController` budget (`INLINE_ANALYSIS_BUDGET_MS`
= 15s) propagated into the fetch; `callAnthropicMessages` classifies each HTTP status and retries the
transient ones once, honouring `retry-after`; and `reanalysisLockTtlSec` scales the cooldown by failure
kind — **only `permanent` earns 30min**, `transient`/`aborted` write no lock at all so the very next cron
cycle retries *inside* the hold window.

Two supporting changes make the next regression visible instead of silent. `wrangler.toml` gained an
`[observability]` block — `console.error` was previously emitted and immediately lost, which is why a
404 loop left no trace. And `ai:usage` now records **attempts** per model, not just successes: a
fallback that is always reached and never succeeds reads `Sonnet: 0/7` and raises a `⚠️ Sonnet fallback:
7 attempts, 0 successes` line in the daily summary, whereas the old counters printed a bare `Sonnet: 0`
whether the fallback was broken or simply never needed. `calls` is also booked from the returned
attempt on *every* path now, including the throw path: the old `usage.calls++` sat after the `await`
inside the `try`, so a thrown error incremented neither `calls` nor `failed` and vanished from the
ledger entirely.

### Verification (2026-07-09, pre-merge)

Root cause was **confirmed against the production Cloudflare AI Gateway route with a real Anthropic
key** before the fix shipped, rather than inferred from the counters:

| Probe | Result |
|---|---|
| `claude-sonnet-4-20250514` (what production had been sending since #21) | `HTTP 404 not_found_error — model: claude-sonnet-4-20250514` |
| `claude-sonnet-5` + `thinking:{type:'disabled'}` (what this PR ships) | `HTTP 200` |
| `analyzeWithSonnetDetailed` end-to-end on a realistic incident prompt | `outcome.kind === 'ok'`, parseable `AIAnalysisResult` (`estimatedRecovery: "1–3h"`, 134 output tokens of a 600 budget) |

One expectation did **not** hold and is recorded here so it isn't re-asserted: omitting `thinking`
did **not** truncate. On the same prompt at `max_tokens: 600`, Sonnet 5 emitted no thinking block in
either configuration (134 vs 149 output tokens, both parsed). Adaptive thinking is the model's own
per-request choice, so `thinking:{type:'disabled'}` remains the right call — it makes the output
budget deterministic on a harder incident — but it is a **guard, not a repair**.

### Two things the verification disproved

Both were plausible, both were wrong, and both are recorded so nobody re-asserts them.

**1. `thinking: {type:'disabled'}` does not fix an observed truncation.** On the same incident prompt
at `max_tokens: 600`, Sonnet 5 emitted no thinking block whether or not `thinking` was sent (134 vs
149 output tokens, both parsed). Adaptive thinking is the model's own per-request choice. Disabling
it makes the output budget deterministic on a harder incident — a guard, not a repair.

**2. Wrapping `ai.run()` does not hang it.** An intermediate revision of this fix raced the Gemma
leg's I/O promise inside a hand-rolled `new Promise(...)`, saw every inline analysis abort at the
full budget, and concluded the wrapper broke the Workers-AI subrequest. It did not. Measured against
the real binding through `wrangler dev --remote`, `env.AI.run()` latency is simply enormous and
wildly variable:

| | run 1 | run 2 | run 3 |
|---|---|---|---|
| awaited directly | 110.7s | 61.2s | >115s (timeout) |
| wrapped in `new Promise` + `.then()` | 0.76s | 0.32s | 60.5s |

The wrapped calls were *faster*. The 15s aborts were Gemma being slow, not the wrapper hanging. The
wrapper was still removed — it only bounded how long we wait, which `analyzeIncidentWithBudget`
already does one level up by racing an ordinary promise, and it left an orphaned `ai.run()` whose
eventual rejection had no handler. **Race the analysis's ordinary promise; await the Workers-AI
subrequest plainly.**

The consequence for tuning: `INLINE_ANALYSIS_BUDGET_MS` cannot be set from first principles, because
Gemma sometimes takes minutes. Some inline calls will always overrun. That is now cheap — an overrun
books `timedOut` (not `failed`), writes no re-analysis lock, and the next cron cycle retries inside
the #882 hold window. The `timedOut` counter in the daily summary is the only legitimate input to
changing that number.

Note the measurements above come from `wrangler dev --remote`, which proxies each subrequest through
a preview tunnel; production latency may be lower. That is precisely why the counter exists.
