# Worker HTTP Endpoints

> Extracted from CLAUDE.md to keep the auto-loaded project file lean (#525). CLAUDE.md links here; this is the canonical per-endpoint reference for `worker/src/index.ts` routing.

All served by the Cloudflare Worker (`aiwatch-worker`, domain `aiwatch-worker.p2c2kbf.workers.dev`). CORS, KV, routing, and the `*/5` cron live in `worker/src/index.ts`.

## Status

| Endpoint | Notes |
|---|---|
| `GET /api/status` | Live parallel fetch of every monitored service (`SERVICES`), normalize, KV write, platform/probe cross-validation. Multi-component services carry a `components: {id,name,status,group?}[]` snapshot for the per-component breakdown — from `statusComponentIds` (#604: cerebras/cursor/runway/langsmith/copilot/windsurf), `displayComponentIds` (#606: elevenlabs/replicate), or dynamic `displayAllComponents` with a `group:'Models'` tag (#606: cohere/groq); absent otherwise. **#575 Phase B**: also carries a gated `reportFeed: {svcId: {cat,desc,ts}[]}` map (`buildReportFeedMap`) — recent crowd reports, ONLY for services where an independent signal corroborates (status not operational, or a probe spike + crowd ≥ baseline; `shouldSurfaceReports`). The dashboard Overview panel + ServiceDetails section render from it. Each service also carries `probeSpike?` (active consecutive RTT spike, the cross-match signal). Absent (omitted) when no service qualifies — so it never contradicts an operational board. **#574**: also a `supplyChainBanner` object (`{cloud,severity,regions,affectedNow,mayBeAffected}`) when an AWS infra region is degraded AND a dependent AI service is degraded AND — **#1000** — its own incident names **that same degraded region** (`buildSupplyChainBanner`, region-aware StatusGator cross-check; a service naming a different region, or none, is omitted → often no banner at all, and an AWS `global`-only event never correlates by design); omitted otherwise. `regions` lists only the CORRELATED regions, not every degraded AWS region. bedrock carries `awsRegionHealth` (AWS infra region health ex-BEDROCK, from the same AWS Health fetch) |
| `GET /api/statusline/down` | **#920 — parseable UNCAPPED down-list** (text/plain) for the plugin monitor's transition tracking. One `status<TAB>name` line per non-operational service (cache order), empty when all operational (`renderStatuslineDownList`, lite cache only — no scoring/incident reads). **#1238 — this wire publishes the honest status word, `unknown` included.** The #1233 carve-out that emitted `degraded` for an unreadable source is gone, and with it the contradiction it caused: the monitor said `🔴 … is degraded` while `/aiwatch` said `⚪ Status source unreadable`, about the same service in the same terminal. What changed is the WORD, not the filter — an unreadable source was already listed here, as `degraded`. `aiwatch-monitor.sh` also keeps the set of outages it still OWES a `✅` for, so a service that never got a `🔴` can never produce one. **What this endpoint owes that consumer**: every listed service is one AIWatch cannot call healthy, and a service's ABSENCE is the only claim of health published here. `unknown` ⇔ unreadable is TOTAL here — the renderer normalises any unreadable value through `isUnreadableStatus`, including one outside the union. Adding another AFFECTED word is safe (the monitor announces an unfamiliar word rather than discarding it); adding a second UNREADABLE one is not, since the script special-cases the literal `unknown`. Its transitions are pinned against the REAL script by `scripts/plugin-monitor.test.mjs` (stub-`curl` harness, run under each installed shell, gated in `test:scripts`). Already-installed plugin copies print `🔴 <name> is unknown` until they are updated — the same false-outage class they already emitted as `degraded`. Distinct from the emoji presets, which are display strings; `bin/aiwatch-monitor.sh` reads it with `comm` to emit explicit `🔴 <name> is <status>` / `✅ <name> has recovered`. WAE-tagged **`aiwatch-monitor`** (NOT `statusline-*`, so continuous monitor polling doesn't pollute the #918 preset-adoption read-back). `max-age=30`, CORS `*`. Routed before the generic `:preset` route. **#1227 — an unusable snapshot returns `503` + `no-store`, NOT the empty 200 that means "all clear"**: an empty body is the wire encoding of "nothing is down", so an unusable snapshot used to fire a false `✅ recovered` for every service that was actually still down (captured in production 2026-08-13). A 503 fails the monitor's `curl -sf`, which takes its existing fail-silent path. The empty 200 stays meaningful — a real all-operational snapshot still returns zero bytes. |
| `GET /api/statusline/brief` | **#920 — compact incident briefing** (text/plain) for the Claude Code plugin's `/aiwatch` command. For each AFFECTED service (#1233 — an unreadable source is not one; `/statusline/brief` discloses it on its own line instead, and it also disqualifies the "all monitored AI services operational ✅" all-clear; `/statusline/down` above publishes the same neutral state since #1238): its active official incident (title + impact), the AI summary of that incident when present (read from `ai:analysis:*`), a per-category fallback, and a short `ai-watch.dev/p/{slug}` landing link (`SERVICE_ID_TO_SLUG`; omitted for the no-is-down-page services) — or a single "all operational" line. `/p/:slug` is a `vercel.json` **redirect** (config, no Serverless Function) → `/is-:slug-down?utm_source=claude-code&…` so the short model-relay-safe link still attributes plugin inflow via GA4 + the `'plugin'` #842-B bucket. `renderStatuslineBrief` (`worker/src/statusline.ts`) is a text generalization of the ext-claude projection (#837); scores the full set for `getFallbacks`, reads AI summaries only for down/degraded services (bounded). WAE-tagged **`aiwatch-brief`** — deliberately NOT a `statusline-*` tag, so on-demand `/aiwatch` traffic does not pollute the #918 statusline-preset adoption read-back (`queryStatuslineTraffic` selects `LIKE 'statusline-%'`); measurable separately. `max-age=30` on a served briefing, CORS `*`. Routed BEFORE the generic `:preset` route (`brief` is not a preset). **#1227 — an unusable snapshot returns a 200 carrying `STATUSLINE_BRIEF_UNKNOWN`** ("status unknown … NOT an all-clear"), never the "all monitored AI services operational ✅" line an empty service list used to produce. 200 rather than 503 on purpose: `aiwatch-status.sh`'s own failure line blames "(network error)", which would misattribute our cache fault to the user's connection. |
| `GET /api/statusline/:preset` | **#918 — server-rendered Claude Code statusline string.** Reads the lite `services:latest` cache and returns `text/plain` with the FINAL OSC-8 line the statusline shows (`renderStatuslinePreset`, `worker/src/statusline.ts`), so the settings.json snippet is a thin `curl … \|\| true` with **no jq**. `:preset` ∈ `branded`/`clickable`/`degraded_only`/`compact_badge`/`full_list`/`scoped` (allowlist-guarded via `isStatuslinePreset`; unknown → 404). The `+N` overflow / OSC-8 links / severity all live server-side now, so future display changes reach ALREADY-installed statuslines via a worker deploy (the old client-jq model froze formatting on the user's machine — AIWatch has no write access to their config). WAE-tagged `statusline-<preset>` on the PATH (same index as the legacy `?src` tag → the #918 `queryStatuslineTraffic` read-back counts both), `Cache-Control: max-age=30`, CORS `*`. **#1227 — an unusable snapshot no longer renders the healthy world.** The old contract ran the renderer over `[]` on a cache miss, so `branded` printed `AIWatch 🟢` — a green claim from no data. Each preset now returns a neutral `⚪` marker in its own idiom (`renderStatuslinePresetUnknown`; `branded` → `AIWatch ⚪`) at 200 + `no-store`, matching the dashboard's #689/#1004 Unknown pill. Still 200, not 503: the snippet is `curl -sf … || true`, so a non-2xx blanks the line, and a blank line is indistinguishable from a broken snippet — this is a display surface, it should say "unknown" rather than disappear. Migration: an existing jq-preset user re-copies the thin snippet ONCE. The old `?src=statusline-*` projection below stays for back-compat with not-yet-migrated users |
| `GET /api/status/cached` | KV-only (no live fetch), includes `probe24h` — for "Is X Down" SSR + initial load. **`?src=statusline-*`** (legacy, pre-#918) returns a ~KB id/name/status-only projection via `buildStatuslinePayload` (`worker/src/statusline.ts`) — skips the ~2 MB probe/latency/AI reads. The old jq-based statusline snippets (#400) poll this with the tag and target the Worker domain directly, **not** the Vercel-proxied `ai-watch.dev` path, so per-prompt polls don't burn Vercel Fast Data Transfer (#438). Superseded by the server-rendered `/api/statusline/:preset` above (#918), kept for already-installed jq snippets. **#1227 — an unusable snapshot returns `503` + `no-store`** rather than the former "intentional" `200 {services: []}`: that jq is frozen in the user's settings.json and `if ($d | length) == 0 then "🟢"`, so an empty projection prints a confident `AIWatch 🟢`. The status code is the ONLY server-side lever on a frozen client — `curl -sf` drops the 503 and `|| true` blanks the line. **`?src=ext-claude`** (#837) returns a ~0.6 KB projection of ONLY the three Anthropic surfaces (claude/claudeai/claudecode) via `buildExtClaudePayload` (`worker/src/ext-claude.ts`) — for the Claude-only Chrome extension's badge/popup poll. Per surface: `{id,name,status,score,grade,fallback[]}` **plus `incidents[]`** (ACTIVE only — resolved/monitoring excluded — `{id,title,status,impact,aiSummary?}`, `aiSummary` from `ai:analysis` for active Claude incidents) **and `reports{count,recent[]}`** (the GATED #575 crowd-report map via `buildReportFeedMap` — only corroborated services have a count; free-text `desc` dropped). Checked BEFORE the statusline branch; CORS `*` (extension bypasses CORS via MV3 `host_permissions`); served from an in-worker `caches.default` edge cache (canonical key, `s-maxage=60`) so polls at scale collapse to ~1 KV/score recompute per PoP per window — true zone-level request elimination is gated on a custom Worker subdomain (#439). Scores the full set (fallback candidate pool) but emits only the 3; WAE-tagged `ext-claude` (#494) for adoption measurement |
| `GET /api/uptime?days=30` | Daily uptime counters |
| `GET /api/probe/history?days=30` | Daily probe RTT summaries (90d max) |
| `GET /api/report?month=YYYY-MM` | Monthly archive JSON (permanent). For the **current** month (no built archive until the 1st of next month) it returns a `partial:true` archive synthesized read-only from the `incidents:monthly:{month}` accumulator (incidentList only) so the dashboard 90-day filter shows current-month incidents that rolled out of the live feed (#587). A KV read/parse error → 502 (not an empty 200); a genuinely absent accumulator → 200 empty partial. Past months with no archive → 404. **#908**: the built-archive 200 emits a weak `ETag` + honors `If-None-Match` → 304, and `max-age` is `300` (was 86400) — so a rebuild (post #904 suppression / #1019 override) un-exposes within ~5 min instead of ≤24h. Shares the `weakFeedEtag`/`isFeedNotModified` primitives via `reportArchiveResponse` (rss.ts) — see the conditional-GET note below |
| `GET /api/v1/status` (+ `/status/:id`) | Public API (lightweight, CORS `*`, rate-limited 60/min/IP). Each served (non-429) request is recorded in Analytics Engine via `recordV1Traffic` (#518) so call volume is queryable via the AE SQL API. **#713**: `aiwatchScore`/`scoreGrade` are **nullable** — a low-confidence service (no official uptime AND no probe, e.g. Bedrock/Azure) returns `null` (score withheld, not 0); `scoreConfidence` (`high`/`medium`/`low`) is included on BOTH the list and single-service responses to disambiguate a withheld score from a missing/errored one. **#1068**: each service also carries `group` — the FINE category (`llm`/`agents`/`voice`/`inference`/`observability`/`video`/`image`/`apps`) beside the coarse `category` (`api`/`app`/`agent`) — sourced from `worker/src/service-groups.ts` (mirror of the frontend `SERVICE_CATEGORIES`, pinned by `service-groups-sync.test.ts`), so external consumers (e.g. the aiwatch-reports breakdown, #98) can derive category counts from data instead of a hand-maintained literal. **#1227** — an unusable snapshot returns 503, including one that parses but carries zero services: a 200 asserting an empty roster reads as "nothing is monitored and nothing is wrong". **#1233 — `status` gained a fourth value, `unknown`**: AIWatch could not READ that service's status source, so it is neither an outage nor an all-clear. An external consumer testing `status !== 'operational'` inherits exactly the defect #1233 fixed internally; test for `'degraded'`/`'down'` explicitly instead |

## Badges / images

| Endpoint | Notes |
|---|---|
| `GET /badge/:serviceId` | SVG status badge. **#1157** — WAE-instrumented (`recordBadgeTraffic`, index `badge-request`, blob1=serviceId): a 200 records the real id, a 404 records the `BADGE_UNKNOWN_SERVICE` sentinel (not the raw miss string — keeps blob1 cardinality bounded regardless of caller input), the 400 invalid-id branch records nothing. **#1227 — an unusable snapshot returns 503 + `no-store` with an `unknown` badge and records NOTHING**: a 404 `not found` would be a confident wrong answer about a service we do monitor, and booking our own read failure as an unknown-id embed polluted this very signal. `queryBadgeTraffic` read-back surfaces a daily-summary "🖼️ Badge Requests" section (top-3 services + a separate "N unknown-id" count). See `api-traffic.ts` in directory-map.md |
| `GET /api/og` | Dynamic OG image PNG (1200×630, resvg-wasm). Purely query-param-driven — the PNG is drawn from `service`/`status`/`score`/`uptime` alone, no live status re-fetch. The is-down page sets the `status` param from the share `?e=` hint when present (pins a tweet's card to the post moment, see status-determination.md), else from live status. **`v` is a cache-bust the caller adds, not a param this endpoint reads** — it reaches no drawing code. The is-down page emits it only when the share is NOT pinned, so a pinned card's image URL stops moving with the wall clock (#1103); the pin rules and the residual are at the `v` line in `api/_is-down/html-template.ts` |

## Incident RSS feed (#54, #467)

| Endpoint | Notes |
|---|---|
| `GET /feed.xml` | All-services incident RSS 2.0; served as `text/xml` with an `<?xml-stylesheet href="/feed.xsl"?>` PI so browsers render a friendly page (#467). A multi-surface incident (one incidentId across several services) is collapsed to ONE item via `dedupeSharedIncidents` (#520) |
| `GET /feed/:slug` | Per-service incident RSS — slug matches `/is-{slug}-down`. KV-unavailable → 503, unknown slug → 404 (#54) |
| `GET /feed.xsl` | Static client-side XSLT for feed rendering (#467) |

**Conditional GET + caching (#860).** Both feed endpoints emit a weak `ETag` (FNV-1a over the body) and honor `If-None-Match` → **304 Not Modified** (empty body, validators re-sent on the 304 too), so RSS pollers (incl. Slack's native `/feed`) + the Vercel edge revalidate cheaply and a healthy revalidatable feed makes pollers back off less (the root cause of a multi-hour Slack `/feed` silence while Discord kept alerting). The body is byte-deterministic: `<lastBuildDate>` is the newest item's pubDate (via `buildFeedWithMeta`), and an **empty feed omits `<lastBuildDate>` entirely** so the dominant no-incident steady state has a stable ETag and 304s. `Cache-Control` is `max-age=60, s-maxage=60` (was 300) + a `<ttl>1</ttl>` hint. A `Last-Modified` header is emitted (newest incident time) but is **informational only** — 304 is gated ONLY on the byte-exact ETag, never `If-Modified-Since`, because the newest-pubDate is coarser than actual body change (a #759 AI block landing / #768 monitoring transition / a non-newest incident update mutates the body without advancing it) so an IMS check could return a false 304 and drop an update. Header contract lives in `feedHttpResponse` (rss.ts), the 304 decision in `isFeedNotModified`; the KV side-effects (#750 `feed:firstseen`, #793 `feed:active-emitted`) run before the response is built, so a 304 never skips them.

**#908 — `/api/report` archive reuses the same primitives** via `reportArchiveResponse` (rss.ts): a rebuilt past-month archive changes its body → its weak ETag changes → a browser that cached the pre-rebuild archive revalidates and re-fetches instead of serving it. The short `max-age=300` is load-bearing, **not** redundant with the ETag — a weak ETag layered on the old 24h `max-age` would leave the stale window unchanged, because a browser whose cache entry is still fresh serves it WITHOUT sending `If-None-Match` (the conditional GET only fires once the entry goes stale). So the fix is BOTH: the `max-age` caps the window to ~5 min, the ETag makes each post-expiry revalidation a cheap 304 for the unchanged common case. Neither retroactively refreshes a browser that ALREADY cached the response under the old 24h `max-age` — that bounds FUTURE rebuilds only.

## Alerts / operator / internal

| Endpoint | Auth | Notes |
|---|---|---|
| `POST /api/alert` | — | CORS/SSRF-guarded Discord proxy (Discord hosts only, #468) |
| `POST /api/admin/analyze` | `X-Admin-Key` (`ADMIN_API_KEY`) | Operator Sonnet override on a specific active incident (#299). Accepts only IDs matching an active incident in `services:latest` (scope guard), per-incident rate-limited, `sticky:true` by default so cron won't auto-replace. Use the `scripts/admin-analyze.mjs` helper, not raw curl. Full runbook in [operator-tools.md](operator-tools.md) |
| `POST /api/admin/rebuild-archive` | `X-Admin-Key` | Operator regenerate of `archive:monthly:{YYYY-MM}` after a bug-fix deploy. Body `{ month: 'YYYY-MM', force?: true }`. Refuses (409/503) when the rebuild would hold less than the stored archive or when a source could not be read — see [operator-tools.md](operator-tools.md) (#1260) |
| `GET/POST /api/admin/suppress` | `X-Admin-Key` | Operator incident-suppression list (#904). GET lists; POST `{action:'add'\|'remove', scope:'incident'\|'service-pattern', incId? \| (svcId?+match?), reason?}` mutates the `incident:suppressions` KV. Hides a correctly-attributed incident (e.g. OpenAI FedRAMP) from the live list + Score + monthly accumulator + rebuilt archives — no deploy, reversible; add is idempotent. Use `scripts/suppress-incident.mjs`. Full runbook in [operator-tools.md](operator-tools.md) |
| `GET/POST /api/admin/duration-override` | `X-Admin-Key` | Operator incident duration-override list (#1019). GET lists; POST `{action:'add'\|'remove', id, durationMin?, reason?}` mutates `incident:duration-overrides`. KEEPS the incident but PINS a paperwork-inflated `duration` to the real value across the monthly archive, the `/api/report` partial and the weekly briefing. Full runbook in [operator-tools.md](operator-tools.md) |
| `GET /api/admin/withdrawals` | `X-Admin-Key` | Durable record of provider-DELETED incidents and whether each one's ⚪ closing notice went out (#1106 Part 5). `?month=YYYY-MM` (default: current) and `?months=1-24` for a lookback. READ-ONLY — a history record, not a control; buckets are `announced` / `pending` / `neverClosed` (= #1106 recurring) / `malformedTimestamp`, and they partition `count`. A range it could not fully open answers `ok:false` + `partial:true` (still 200, rows included) with `unreadableMonths` + `malformedByMonth` saying which key to repair. 502 when every month in the range is unreadable, which is permanent until the KV value is repaired by hand. Full runbook in [operator-tools.md](operator-tools.md) |
| `POST /api/internal/edge-fallback` | Bearer `EDGE_ALERT_TOKEN` | Called by Vercel Edge Functions on a degraded fallback render; dedups via `alerted:edge-fallback:*` and fires Discord (#378) |
| `POST /api/report-issue` | — (CORS, per-IP rate-limit) | Crowd "Report an issue" collect endpoint (#575). Body `{svcId, category, description?}` — validates svcId + category, sanitizes description, IP-hash per-day dedup, increments `report:count:*` + appends `report:feed:*`. Always returns an honest 200 ack (never a count). COLLECT only — display is gated, see below |
| `GET /api/report-feed?svc=:id` | — (CORS, `max-age=30`) | Recent 24h crowd reports for one service (#575). The **is-down Edge** fetches this (gate at the call site). The **dashboard** does NOT use it — it reads the centralized gated `reportFeed` map on `/api/status` instead (no per-service fan-out). A public list never contradicts an `operational` page either way |
