# KV Key Schema (STATUS_CACHE namespace)

> Extracted from CLAUDE.md to keep the auto-loaded project file lean. CLAUDE.md links here; this is the canonical reference.

| Key Pattern | Value | TTL | Writes/Day | Purpose |
|---|---|---|---|---|
| `services:latest` | `{ services, cachedAt }` JSON | 5min | ~288 + a few | Real-time status cache (all 37 services). Written by the throttled `/api/status` `cacheWrite` (10-min) **and** by the cron on each status-change edge (#488, `cache-refresh.ts`) so OG/SEO previews (`/api/status/cached` readers) reflect an incident within one cron cycle — the edge writes are rare (incident start/recovery), negligible vs. the budget |
| `daily:{YYYY-MM-DD}` | `{ [svcId]: { ok, total, officialUptime } }` JSON | 2d | ~288 | Daily uptime counters. `ok` increments via `countsAsUptimeOk` (#733): `operational` → up, `down` → down, `degraded` → down **only** when a major/critical unresolved incident backs it (minor/partial-scope or no-incident degraded counts as up, mirroring official rolling-uptime weighting). Feeds /api/uptime + the AIWatch Score's uptime component. `officialUptime` = the status-page rolling-30d snapshot (#586); the **weekly Stability Trend** uses it for the **previous-week** value (#733) — the current week comes from the LIVE `services:latest` `uptime30d` (gated on `isUnreliableUptime` so no-official-uptime/stale services like Bedrock/Azure/Deepgram are excluded — a live gate, because their historical `officialUptime` snapshots are intermittently non-null pre-#713 residue). Compares official figures, not the served-status `ok/total` (noise for incident-only/probeless services) |
| `history:{YYYY-MM-DD}` | Same as daily | 90d | 1 | Archived yesterday's counters |
| `latency:24h` | `{ snapshots: [{ t, data }] }` JSON | 25h | ~48 | 30-min latency snapshots (max 48) |
| `probe:24h` | `{ snapshots: [{ t, data }] }` JSON | 7d | ~288 | 5-min health check probe results (max 2016, 24 API services) |
| `probe:daily:{YYYY-MM-DD}` | `{ [svcId]: { p50, p75, p95, min, max, count, spikes } }` JSON | 90d | 1 | Daily probe RTT summary for monthly reports |
| `probe:summaries` | `[svcId, ProbeSummary][]` JSON | 80min | ~48 | Cron-cached 7-day probe summaries (p50, p95, cvCombined, validDays); refreshed every 30min via in-memory slot guard, TTL covers up to 2 missed 30-min refresh cycles |
| `alerted:new:{incId}` | `JSON.stringify(svcIds)` (e.g. `["codex","chatgpt"]`); legacy `"1"` auto-migrated | 7d | ~5 | Incident alert dedup — now the **per-service roster** already alerted for the incident (#545). A service that JOINS a multi-service incident after the first alert fired (e.g. ChatGPT joining a Codex incident after OpenAI renamed the title) is alerted only if NOT in this set, then merged in. Read via `parseAlertedRoster` (legacy `"1"` → seed with the currently-matching service, no re-alert storm on deploy). The cron's dedup loop bypasses the key-exists skip for `alerted:new:` (per-service dedup already happened in `buildIncidentAlerts`); a failed roster write is logged loudly since it would re-fire the alert next cycle |
| `alerted:res:{incId}` | `"1"` | 7d | ~2 | Resolved incident alert dedup |
| `feed:firstseen:{incId}` | ISO timestamp | 7d | ~5 | #750 — AIWatch's first-detected time for the incident, written ONCE (get-or-set, first write wins → stable) alongside the `alerted:new:` roster. The `/feed` handler reads it as the **active item's `pubDate`** so a provider-backdated `startedAt` (BetterStack flap / #633-held incident surfacing hours late) can't make Slack /feed treat the outage post as "already past" and skip it (Discord push is unaffected). Absent → rss.ts falls back to `startedAt`. **#748** — the daily summary also READS these markers (`countNewFeedItems`: list + count those first-seen in the last 24h) to show "· N new items" beside the poll volume |
| `feed:active-emitted:{incId}` | ISO timestamp | 7d | ~5 | #793 — written by the `/feed` handler the first time an incident's ACTIVE item is actually SERVED in a feed response (i.e. NOT held by the #759 AI-hold, via the shared `isActiveItemHeld` predicate), get-or-set, scoped to the services the polled feed actually carries. On resolution the handler reads it: a resolved incident WITHOUT this marker had its outage never announced, so `buildRssFeed` suppresses the lone "Resolved" item (prevents a Slack **orphan resolution** — "Resolved · 19m" with no prior outage post — for a short blip whose entire active window fell between reader polls). Absent on a clean miss → suppress; a KV read THROW fails open (emit the resolved). Sibling of the Discord half #792 |
| `alerted:down:{svcId}` | ISO timestamp | 2h | ~2 | Service down alert dedup + recovery duration |
| `alerted:degraded:{svcId}` | ISO timestamp | 2h | ~2 | Service degraded alert dedup |
| `alerted:recovered:{svcId}` | `"1"` | 2h | ~2 | Recovery alert dedup |
| `recovered:{svcId}:{incId}` | `{ resolvedAt, incidentTitle, duration }` JSON | 2h (`RESOLVED_TTL_S`) | ~1 per resolved incident **per affected service** | Independent recovery marker (powers the Recently Resolved banner without AI analysis; only its EXISTENCE is read — `/api/status` + `/api/status/cached` — the payload is forensics). **#1003 — written by `markIncidentResolved` (`recovery-mark.ts`) from BOTH cron resolution paths.** It previously lived only in the `alerted:recovered:` status-edge block, which the code itself calls "rarely-firing … only fires in the incident-less gap", while a normal incident ends via `alerted:res:` — so the banner (and, via the paired `resolvedAt` stamp below, the Analyze modal's + is-down's predicted-vs-actual verdict) effectively never appeared. Only TERMINAL incidents (`resolved`/`monitoring`) are marked; a merged alert marks every incident it collapsed |
| `alerted:probe-spike:{svcId}` | `"1"` | 1h | ~2 | Probe RTT spike alert dedup (early detection) |
| `alerted:source-dead:{svcId}` | `"1"` | 7d | ~0-2 | #689 — dedup for the distinct **"status source inactive"** operator alert. Written on the rising edge (a service's status-page API returned a 4xx → `sourceDead`, e.g. Character.AI's Statuspage deactivated → 401 "page inactive"), so the operator gets ONE accurate "source inactive" embed (not a misleading "degraded" — the service is shown operational+stale, excluded from rankings). Deleted on the falling edge (source responds again) along with a green "source recovered" note. `shouldAlertSourceDead` drives the decision. **#800** — for a `statusSourceDeactivated` service (a KNOWN, acknowledged, long-running deactivation, e.g. Character.AI's 401 page), the rising-edge "Inactive" SEND is suppressed (`shouldSuppressSourceDeadAlert`) but this marker is still written, so the weekly re-alert stops while a RECOVERY is still detected + notified; the #500 persistent-failure daily warning is likewise skipped for these ids |
| `alerted:flap:{svcId}:{normalizedTitle}` | `"1"` | 1h | ~5-20 | BetterStack auto-recovery flap suppression (#283) — 60-min window per service + title. Written on the `alerted:res:` fire of the first flap; checked on next cron cycle to drop both down + resolved halves of subsequent identical flaps. Opt-in via `ServiceConfig.flapSuppression: true`; applies to `together`, `fireworks`, `huggingface`, `modal`, `luma`. Tier-1 (`claude`/`openai`/`gemini`) never suppressed as defense-in-depth |
| `pending:degraded:{svcId}` | `"1"` | 10min | ~5 | Anti-flapping: 2-cycle consecutive detection |
| `pending:new:{incId}` | first-seen epoch ms (write-once / get-or-set; #835 — was `"1"`) | 30min (#835 — was 10min; must outlast the ~2-cycle window) | ~0-5 | First-seen confirmation gate (#633/#792/#835) — stamped with the first-sighting time when a NEW incident is HELD, via `shouldHoldNewIncident`. **Two writers:** (a) #633 — a flap-shaped incident (`isFlapNotice`: "— down/recovered" title + impact **not `major`**; #564/#565 maps a BetterStack monitor flap to `minor`/null, so the gate excludes only `major`, not all non-null impact) on a `flapSuppression` service (together/fireworks/huggingface/modal/luma); (b) #792 — ANY non-`major`/`critical` incident (`isShortIncidentHoldable`, no title shape required) on a `holdShortIncidents` service (langfuse — frequent short `minor` ingestion blips that backdate resolution → New+Resolved double-alert; **mistral #929** — Instatus/Nuxt auto-monitor `"○○ API Degraded"` minor flaps that self-resolve then get pruned → phantom "New Incident"). **#835**: held until first-seen ≥ `FLAP_HOLD_MS` (~9min ≈ 2 `*/5` cycles), not just one — a flap that lingered just past one cycle then resolved still double-alerted (Modal "Storage degraded" 1m). A blip that self-recovers inside the window fires neither New nor Resolved (the `alertedNewMap.has` guard). Mirrors `pending:degraded` on the new-incident path |
| `pending:ai:{incId}` | first-seen epoch ms (write-once / get-or-set) | 30min (`PENDING_NEW_TTL_S`; must outlast the `AI_HOLD_MS`≈10min window) | ~0-5 | #882 new-incident **AI-hold** window marker. Stamped when a **non-Tier-1** `alerted:new:` alert is HELD because its 8s inline AI analysis overran (`shouldHoldForAiAnalysis`) — the send loop `continue`s before the send, and a later cron cycle releases the alert WITH the AI section once `refreshOrReanalyze` has backfilled `ai:analysis`. Bounded: past `AI_HOLD_MS` the gate fail-opens (ships AI-less). Deleted best-effort on release. **Distinct** from `pending:new:` (which holds a *phantom* short/flap alert) — this holds a *real* alert for AI completeness; the two markers never clobber. Tier-1 (claude/openai/gemini) is never held so no marker is written for them |
| `detected:{svcId}` | ISO timestamp | 7d | ~5 | Earliest detection time (probe spike or status page, whichever is earlier). Feeds the MTTD framing + reused by #677 as the AWS/Bedrock incident-start anchor. **#679** — the per-incident "detection lead" (faster-than-official) surfacing + the `detection:lead:{date}`/`:monthly`/`:diag` accumulators were REMOVED (the lead was structurally null — status-page polling is always later than the official publish; #464 already retired the framing). This key itself is KEPT |
| `probe-degradation:daily:{svcId}:{YYYY-MM-DD}` | counter string | 48h | ~0-N | RTT degradation counter (#464) — incremented on the **rising edge** of a probe-spike streak (gated by the existing `alerted:probe-spike:` 1h dedup). The honest differentiator: AIWatch's direct RTT probe catches latency degradation that status pages often never report. Read at the daily summary via `formatDegradationSection` |
| `probe-degradation:nostatus:daily:{svcId}:{YYYY-MM-DD}` | counter string | 48h | ~0-N | Subset of `probe-degradation:daily` where the service's official status was still `operational` at spike time — i.e. the degradation is NOT on the status page. The headline figure for "degradations status pages never report" (#464). Classified by `classifyDegradation` against the cached `services:latest` snapshot |
| `probe-degradation:monthly:{YYYY-MM}` | `DegradationMonthly` JSON `{byService,noStatusByService}` | 60d | ~0-N | RTT degradation monthly accumulator (#511) — dual-written by the spike loop alongside the daily counters (read-modify-write via `addDegradationToMonthly`) so the monthly archive cron can read month-complete counts past the daily 48h TTL. Summarized into `MonthlyArchive.degradation` (total / noStatusTotal / byService / noStatusByService) and exposed via `/api/report`. Mirrors the `security:monthly` accumulator pattern |
| `reddit:seen:{postId}` | `"1"` | 24h | ~120 | Reddit post dedup (hourly scan, max 5/hour) |
| `security:seen:hn:{objectId}` | `SecurityAlertMeta` JSON | 7d | ~0 | HN security post dedup + display. **#892 — PUBLIC display (dashboard `securityAlerts`) is gated to entries whose title carries a `CVE-YYYY-NNNN`** (`isPubliclyVerifiedAlert`); non-CVE HN chatter is operator-Discord-only (still stored for dedup) |
| `security:seen:osv:{vulnId}` | `SecurityAlertMeta` JSON | 7d | ~0 | OSV.dev vulnerability dedup + dashboard display (always public — CVE-backed, #892; includes `epssPercentile` / `epssPercentage` from #326 when GitHub Advisories enrichment succeeded) |
| `security:monthly:{YYYY-MM}` | `SecurityAlertMeta[]` JSON | 60d | ~1/day | Monthly security alert accumulation for reports (entries carry EPSS fields when available, #326). **#892 — `buildMonthlyArchive` applies the same `isPubliclyVerifiedAlert` gate before summarizing**, so the public `/api/report` archive counts/topFindings exclude unverified HN chatter |
| `enrich:epss:{ghsaId}` | `EpssScore` JSON (`{percentile, percentage}`) | 24h | ~0-15/day | EPSS (Exploit Prediction Scoring System) cache (#326). Hit once per new OSV vuln against GitHub Advisories API, cached 24h (EPSS recomputes daily). Missing = enrichment unavailable → alert still surfaces without the exploit-probability tag. Rate-limited to 60/hr unauth (not a practical concern given 24h cache + #323 15-per-cycle cap) |
| `security:detected:{YYYY-MM-DD}` | integer string | 3d | ~0-3/day | Daily counter of newly-detected security alerts (#288). Incremented by `securityAlerts.length` when HN/OSV detection fires. Daily summary reads this instead of counting `security:seen:*` (which accumulates over 7d and inflates the figure) |
| `ai:analysis:{svcId}:{incId}` | `AIAnalysisResult` JSON | 1h (active) / 2h (resolved, `RESOLVED_TTL_S`) | ~6 per incident (the `resolvedAt` stamp at resolution is #1003's — it previously never happened on the normal path) | Hybrid AI analysis result — Gemma 4 primary + Sonnet fallback (TTL refreshed while active; on recovery, `resolvedAt` added instead of deleting — kept 2h for "Recently Resolved" UI). `model` field tracks which model produced the analysis. `sticky: true` (#299) marks a manual operator override — cron skips re-analysis and only refreshes TTL; cleared naturally when incident resolves. **`firstEstimatedRecoveryHours` (#1003)** — the FIRST estimate ever made for the incident, stamped on every write by **`putAnalysis`, the single chokepoint through which all `ai:analysis:` writes must go** (CI-enforced: `first-estimate-write-paths.test.ts` fails on any analysis-key write outside it), and read back from the durable `ai:first-est:` key below. Needed because re-analysis fires only once an incident outruns its own estimate and its prompt forbids a new upper bound below the elapsed hours — so `estimatedRecoveryHours` can only ratchet UP with hindsight. **Live surfaces read `estimatedRecoveryHours` (the current ETA); anything that SCORES the prediction reads `firstEstimatedRecoveryHours` via `scoringBaselineHours`** |
| `ai:first-est:{svcId}:{incId}` | recovery-estimate upper bound in hours, as a string (e.g. `"4"`) | 30d (`FIRST_ESTIMATE_TTL_S`) | **≤1 per service+incident** (write-once / get-or-set; a grouped incident pins one key per affected service, via the sibling-copy path) | #1003 — the durable **scoring baseline**: the first recovery estimate made for an incident, the value its resolution is graded against. Separate from `ai:analysis:` because that key is deliberately allowed to **lapse** mid-incident (once an analysis is 2h+ old and the per-cron re-analysis cap is exhausted, `refreshOrReanalyze` stops refreshing its TTL so a later cycle re-analyzes from scratch) — a broad outage can starve one long incident for the ~12 cycles that takes, and the replacement analysis would otherwise install ITS hours-in estimate as "the first" one, re-running the bug on exactly the long incidents where scoring matters most. `pinFirstEstimate` reads it before every fresh-result write and only writes when absent, so no re-analysis can move it. Best-effort: a KV failure degrades to the in-value carry (the prior analysis), never to dropping the estimate |
| `ai:reanalysis-skip:{svcId}:{incId}` | `"1"` | **outcome-scaled** (`reanalysisLockTtlSec`): 30min `permanent` · 5min `unknown` · **not written** for `transient`/`aborted` | ~2 per incident | Per-incident re-analysis failure cooldown. **#955** — was a flat 30min for EVERY failure, written on both the null and the throw path. With the `*/5` cron that skipped the next six cycles, and because the key is per-INCIDENT (not per-model) a single transient Gemma parse failure that fell through to a broken Sonnet froze the incident for half an hour even though Gemma would have succeeded on the next cycle. It also outlived the #882 `AI_HOLD_MS`≈10min window, so the held alert was *guaranteed* to ship AI-less. Only a `permanent` failure (retired model id, revoked key, unparseable 200) earns the long lock now |
| `ai:usage:{YYYY-MM-DD}` | `{ calls, success, failed, timedOut?, gemma?, sonnet?, gemmaAttempts?, sonnetAttempts? }` JSON | **30d** (#995, was 2d) | ~5 | Daily AI analysis usage counter (includes re-analysis, model breakdown). Manual `/api/admin/analyze` (#299) calls also increment here so the daily summary attributes them. **#995** — retention raised 2d→30d (`AI_USAGE_TTL_S`) so a rolling trend survives: the **weekly briefing** reads the week's keys → `summarizeAiUsageTrend` → a `🤖 AI Analysis (7d): … · N timed out · M failed` line, so "is the Gemma timeout/fallback rate rising?" is answerable from data (previously the counters evaporated after 48h, and the `timedOut` metric is itself new so had no baseline). **#955** — `gemma`/`sonnet` count SUCCESSES; the `*Attempts` fields count calls actually issued, because a fallback that is always reached and never succeeds was previously indistinguishable from one that is never reached (both read `sonnet: 0`) — which is how a retired Sonnet model id 404'd for weeks unnoticed. `timedOut` splits budget/timeout aborts out of `failed`. `calls` is now booked from the returned attempt on EVERY path — including the throw path, which previously incremented neither `calls` nor `failed` (the old `usage.calls++` sat after the `await` inside the `try`, so a thrown error vanished from the ledger). Reader is tolerant of the pre-#955 shape (`parseUsage`) |
| `incident:history:{svcId}` | `IncidentHistoryRecord[]` JSON — rolling, capped at `HISTORY_CAP=50` (newest last), **dedup by incId** | **none (permanent)** | ~0-2 (per resolved incident) | #827 Phase 1 keystone — one durable record per RESOLVED incident joining the AI prediction (`predictedRecoveryHours`/`predictedSummary`/`model`, copied from the soon-to-expire `ai:analysis:` key) with the actual outcome (`durationMin`, from `startedAt`→resolution). **#1003 — `predictedRecoveryHours` is the FIRST (hindsight-free) estimate** (`scoringBaselineHours` → `firstEstimatedRecoveryHours`, falling back to `estimatedRecoveryHours` for pre-#1003 analyses), NOT the re-analysis-inflated current one: re-analysis only fires on incidents the model got WRONG and can only raise the bound, so grading against the current estimate scored every miss as a win ("4h 55m — faster than ~15h est." on a Pinecone incident first estimated 1–4h) and fed the inflated number into both the accuracy aggregate and the RAG corpus below. Written by the cron's recovery handler (`appendIncidentHistory`, `incident-history.ts`) the moment an incident resolves — outlives the 2h `ai:analysis:`/`recovered:` TTLs that otherwise drop both halves. Simultaneously the **prediction-accuracy ledger** (Feature 1: `accuracyOf` per-record → `summarizeAccuracy` aggregate, surfaced as the daily-summary `🎯 AI Recovery Prediction Accuracy` line; Feature 3 aggregates it per-month via `buildMonthlyAccuracy` → `MonthlyArchive.predictionAccuracy` → `/api/report`), the **RAG corpus** analyses retrieve from (Feature 2: `findSimilarHistory` → prompt grounding), and the **predicted-vs-actual display** source (Feature 4: `predictedVsActualText` on the recovery alert / RSS / is-down surfaces). Records WITHOUT an AI analysis at resolution omit the `predicted*` fields (the actual outcome alone is corpus-worthy). Best-effort (a KV failure is logged + swallowed, never aborts recovery); idempotent so a repeated recovery cycle never double-records |

| `growth:daily:{YYYY-MM}` | `GrowthDailyRow[]` JSON — one row per day: `date`, `alertedIncidents`/`alertedResolved` (the outage-day axis), `referralTotal`, `subscribers` (snapshot) + `subscriberNewToday`, `audienceTotal`/`audienceActiveTotal`/`audienceBySource` | **none (permanent)** | 1 | #986 — the durable series the #547·16 lift measurement reads.
