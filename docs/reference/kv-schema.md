# KV Key Schema (STATUS_CACHE namespace)

> Extracted from CLAUDE.md to keep the auto-loaded project file lean. CLAUDE.md links here; this is the canonical reference.

| Key Pattern | Value | TTL | Writes/Day | Purpose |
|---|---|---|---|---|
| `services:latest` | `{ services, upstreamFeeds, cachedAt }` JSON (shape MUST match `cache-refresh.ts` `writeStatusCache`) | 5min | ~288 + a few | Real-time status cache (every monitored service — `SERVICES`). Written by the throttled `/api/status` `cacheWrite` (10-min) **and** by two event-driven edge refreshes that bypass the throttle (`cache-refresh.ts`, CACHE_KEY-only, never the daily counters): the **cron** on each status-change edge (#488) — covers the no-live-traffic case; and the **live `/api/status` handler** on a poll whose status differs from the cached snapshot (#1057, `refreshStatusCacheOnLiveEdge`) — so OG/SEO previews (`/api/status/cached` readers) flip on the live poll, *ahead of* the Discord alert instead of in lockstep with the cron. Both edges are rare (incident start/recovery) and self-silencing (next read sees the fresh snapshot), so negligible vs. the budget |
| `daily:{YYYY-MM-DD}` | `{ [svcId]: { ok, total, officialUptime, weightedOutageSec } }` JSON | 2d | ~288 | Daily uptime counters. The 2d TTL is slack for the archival into `history:{date}`, which happens inside the throttled `cacheWrite` on the `/api/status` request path — **not** in the cron. So it depends on inbound traffic. `ok` increments via `countsAsUptimeOk` (#733): `operational` → up, `down` → down, `degraded` → down **only** when a major/critical unresolved incident backs it (minor/partial-scope or no-incident degraded counts as up, mirroring official rolling-uptime weighting). Feeds /api/uptime + the AIWatch Score's uptime component. `officialUptime` = the status-page rolling-30d snapshot (#586); the **weekly Stability Trend** uses it for the **previous-week** value (#733) — the current week comes from the LIVE `services:latest` `uptime30d` (gated on `isUnreliableUptime` so no-official-uptime/stale services like Bedrock/Azure/Deepgram are excluded — a live gate, because their historical `officialUptime` snapshots are intermittently non-null pre-#713 residue). Compares official figures, not the served-status `ok/total` (noise for incident-only/probeless services). **#1017** — `weightedOutageSec` (nullable) is that UTC day's weighted outage seconds (`ServiceStatus.todayWeightedOutageSec`), populated for all 5 "official" sources (Statuspage/incident.io/Instatus×2/Flashduty/OnlineOrNot) — the latter 4 via a second `weightedDowntimeSeconds` call (see `uptime-interval.ts`), Statuspage via its own last-published-day-bucket read (not the interval sweep-line); absent for Better Stack (`platform_avg`, a different weighting scheme, #1110) and no-uptime sources. Rides this same key's existing write (+0 new KV writes) — the durable per-day input `uptime-archive.ts` reads back from `history:{date}` to reconstruct a calendar window a provider status-page migration blanked (#1004) |
| `history:{YYYY-MM-DD}` | Same as daily | 90d | 1 | Archived yesterday's counters. **After expiry the day is unrecoverable, not merely unqueried (#988)** — `archive:monthly` holds monthly aggregates rather than the daily grid. `/api/uptime` clamps `?days=` to the same `HISTORY_RETENTION_DAYS` constant. **#1017** — this is the actual archive `restoreArchivedCalendar` (`uptime-archive.ts`) reads: for a service whose `uptimeWindowDays` is present (the disclosed "migration reset the live window" signal), it reads back up to `calendarDays − uptimeWindowDays` of these entries to fill the resulting `dailyImpact` gap, classified from `weightedOutageSec` (see `uptime-archive.ts`'s `classifyArchivedDay` thresholds). Gated so the extra reads are paid only by a flagged-short service, never on the common full-window path |
| `uptime-archive:restored` | `{ [svcId]: { firstEligibleAt, firstRestoredAt, lastRestoredDate, maxDaysRestored, uptimeWindowDays } }` JSON | **none (permanent)** | 0 whenever no service is eligible; otherwise one MERGED write per cycle (all eligible services in one key), only when a field actually changes | **#1017 follow-up** — the durable trace that the archive RESTORE path fired, and the answer to a question no dated reminder can be aimed at (a status-page migration is an external event). Read: `wrangler kv key get "uptime-archive:restored" --config worker/wrangler.toml --binding STATUS_CACHE --remote`. No TTL and a fail-closed CONTAINER read, so an unreadable value is a PERMANENT wedge: writes stall until an operator runs `wrangler kv key delete` on it. That is the intended trade for a key with no second chance, and the `WEDGED` log line names the remedy and prints the offending payload. A corrupt field inside an otherwise readable record is coerced instead, so one bad record never freezes the key for other services. The rationale, the field semantics and the coverage limit live in `worker/src/uptime-archive-trace.ts` — deliberately not restated here |
| `latency:24h` | `{ snapshots: [{ t, data }] }` JSON | 25h | ~48 | 30-min latency snapshots (max 48). **Fail-closed write (#1256)** — see the note below. Also skipped when the poll measured no latencies at all, since an empty payload would claim the slot and the dedup would then drop the healthy poll |
| `probe:24h` | `{ snapshots: [{ t, data }] }` JSON | 7d | ~288 | 5-min health check probe results (max 2016, one entry per `PROBE_TARGETS` target). **Fail-closed write (#1256)** — see the note below |
| `probe:daily:{YYYY-MM-DD}` | `{ [svcId]: { p50, p75, p95, min, max, count, spikes } }` JSON | 90d | 1 | Daily probe RTT summary for monthly reports |
| `probe:summaries` | `[svcId, ProbeSummary][]` JSON | 80min | ~48 | Cron-cached 7-day probe summaries (p50, p95, cvCombined, validDays); refreshed every 30min via in-memory slot guard, TTL covers up to 2 missed 30-min refresh cycles |
| `alerted:new:{incId}` | `JSON.stringify(svcIds)` (e.g. `["codex","chatgpt"]`); legacy `"1"` auto-migrated | 7d | ~5 | Incident alert dedup — now the **per-service roster** already alerted for the incident (#545). A service that JOINS a multi-service incident after the first alert fired (e.g. ChatGPT joining a Codex incident after OpenAI renamed the title) is alerted only if NOT in this set, then merged in. Read via `parseAlertedRoster` (legacy `"1"` → seed with the currently-matching service, no re-alert storm on deploy). The cron's dedup loop bypasses the key-exists skip for `alerted:new:` (per-service dedup already happened in `buildIncidentAlerts`); a failed roster write is logged loudly since it would re-fire the alert next cycle. **#1224 — the cron's per-incident loop no longer READS this key for an incident past `INCIDENT_ALERT_MAX_AGE_MS`** (24h, `alerts.ts`), the same constant `buildIncidentAlerts` applies to BOTH its new and resolved branches — so an incident it skips could not have produced an alert anyway. Deliberately the SAME constant rather than two numbers that agree, and evaluated on the SAME clock, so widening the cutoff widens the gate in the same edit. The decision itself lives in `markerReadPlan`, not spelled out at the call site. **Not gated on this key's 7d TTL**, which was the first form of the gate and is unsound — the TTL runs from the SEND (up to 24h after `startedAt`), so the key outlives `startedAt + 7d` and a live marker would have been skipped. Measured 2026-08-17: the loop iterated 1,131 (service, incident) pairs, of which 1,124 were past the bound, so this key's read went 1,131 → 7 per run (~326k → ~2.0k/day). A read ERROR here is now logged and counted separately from a `pending:new:` one (it is not a skip: it makes the dedup bypass re-emit the 🔴 New alert every 5 min, and for a resolved incident drops its Resolved notice), and the run's read accounting is one line per cron tick, `[cron] #1224 marker reads —` |
| `alerted:res:{incId}` | `"1"` | 7d | ~2 | Resolved incident alert dedup |
| `feed:firstseen:{incId}` | ISO timestamp | 7d | ~5 | #750 — AIWatch's first-detected time for the incident, written ONCE (get-or-set, first write wins → stable) alongside the `alerted:new:` roster. The `/feed` handler reads it as the **active item's `pubDate`** so a provider-backdated `startedAt` (BetterStack flap / #633-held incident surfacing hours late) can't make Slack /feed treat the outage post as "already past" and skip it (Discord push is unaffected). Absent → rss.ts falls back to `startedAt`. **#748** — the daily summary also READS these markers (`countNewFeedItems`: list + count those first-seen in the last 24h) to show "· N new items" beside the poll volume |
| `feed:active-emitted:{incId}` | ISO timestamp | 7d | ~5 | #793 — written by the `/feed` handler the first time an incident's ACTIVE item is actually SERVED in a feed response (i.e. NOT held by the #759 AI-hold, via the shared `isActiveItemHeld` predicate), get-or-set, scoped to the services the polled feed actually carries. On resolution the handler reads it: a resolved incident WITHOUT this marker had its outage never announced, so `buildRssFeed` suppresses the lone "Resolved" item (prevents a Slack **orphan resolution** — "Resolved · 19m" with no prior outage post — for a short blip whose entire active window fell between reader polls). Absent on a clean miss → suppress; a KV read THROW fails open (emit the resolved). Sibling of the Discord half #792 |
| `alerted:wd:{incId}` | `"1"` | 7d | ~0 | #1106 — **withdrawal** alert dedup, the third terminal alert kind beside `alerted:res:`. Fires when a provider DELETES an announced incident from its status page instead of resolving it; a deleted incident can never re-enter the live list with `status === 'resolved'`, so `buildIncidentAlerts`' resolved branch is structurally unreachable for it and the 🔴 New alert would otherwise never be closed on any channel. Written by the ordinary post-send `keysToWrite` path (no special casing), so the standard key-exists skip in the cron dedup loop is what prevents a re-fire while the tombstone lives. Emitted ONLY when `alerted:new:{incId}` is still present — a withdrawal we never announced must produce no orphan notice (the Discord twin of #793's rule) |
| `incidents:withdrawn` | `WithdrawnIncident[]` JSON (`{svcId, incId, title, startedAt, prunedAt}`) | key 7d / entries 6d (#1153) | ~0 | #1106 — **tombstones** for incidents the #975 phantom prune deleted, i.e. incidents the provider removed upstream. The prune is the last moment we hold the title + start time, so `accumulateIncidentsOnlyIfChanged` diffs `incidentIds` before/after (`diffPrunedIncidents` — keeps `prunePhantomIncidents` pure) and records them here AFTER the accumulator write lands (a tombstone for an unpersisted prune would re-announce next cycle). This roster is the ONLY material both withdrawal emitters have: the Discord alert and the RSS `:withdrawn` item render from it, because the incident no longer exists in any live list. Deliberately ONE roster key, not one key per incident: the feed renderer must ENUMERATE tombstones rather than look up a known id, and KV `list` is eventually consistent + adds a request-path round trip. Merge is first-write-wins per `(svcId, incId)` so `prunedAt` never moves (it is the RSS item's `pubDate` — a moving value would drift the pubDate after the item was served and churn the #860 ETag), and age is filtered on **read** as well as write: every write refreshes the KEY's TTL, so with a trickle of new tombstones an entry would otherwise outlive its own window. **The key deliberately outlives the entry window by a day** (7d vs 6d) — if they expired together, the ordinary single-tombstone case would evict the key at the same instant the entry aged out, so the "expired without ever notifying" warning (the only signal that a thread was never closed) could fire only in the minority case where a later write had refreshed the key. **#1153 — the entry window was 48h, but `withdrawalHold` withholds a notice until the PROVIDER resolves the incident the withdrawn one duplicated, on the provider's clock, so a slow provider (11h+ in `monitoring` with its own indicator green) could outlast 48h and lose the notice.** Widened to 6d — chosen to sit strictly under the `alerted:new:` 7d marker `buildWithdrawalAlerts` gates on, past which the notice is structurally impossible anyway. Because that key TTL is frozen at write time and `appendWithdrawn` (the prune) is the only writer, a tombstone already in KV keeps its old, shorter key life; the cron therefore re-puts the roster VERBATIM once an hour while an entry is pending (`refreshWithdrawnKey` — raw re-read, not the read-filtered snapshot, so it never clobbers a concurrent append or compacts a skipped entry). Hard-capped at 50 (eviction is logged — the oldest entries are the ones most likely still waiting on a gate). Read is fail-CLOSED: an unreadable, corrupt, or malformed-element value reads as `[]` → emit nothing, so a roster blip can never FABRICATE a withdrawal notice (the per-element check also matters because a malformed entry would throw in `sanitize()` inside the unguarded cron alert build). Note the two EMITTER gates do not share that direction — Discord fails closed, RSS fails open per #793. The TTL is not the re-fire guard — `alerted:wd:{incId}` and the feed guid are |
| `incidents:withdrawn:log:{YYYY-MM}` | `WithdrawalLogEntry[]` JSON (`{svcId, incId, title, startedAt, prunedAt, announcedAt?}`) | **none (durable)** | ~0 | #1106 Part 5 — the DURABLE record that a withdrawal happened, and whether its ⚪ closing notice went out. Every other trace is short-lived by design (`incidents:withdrawn` 6d, `alerted:wd:` 7d, `alert:feed:recent` 2h, Workers Logs ~3d) and the accumulator row is gone by definition — its prune is what starts all of this — so past a week nothing could answer *"did the ⚪ path ever fire?"*. That matters because #1106's exit condition is a production OBSERVATION that cannot be scheduled (it needs a provider to delete an announced incident), so a `verify-after` date would fire on an absence: the instrumentation IS the deliverable. Two write points only — the prune (`recordWithdrawalsPruned`, beside the tombstone write) records the row with `announcedAt` ABSENT, and the cron stamps it AFTER the ⚪ Discord send and GATED on that send's result (`markWithdrawalsAnnounced`, which checks the current AND previous month because a 6d tombstone can cross a boundary). The gate matters: `sendDiscordAlert` returns `false` rather than throwing, and the `alerted:wd:` dedup key is written before the send, so a rejected send never retries — stamping before it would record "the thread was closed" for a notice nobody received. A row still lacking `announcedAt` once the notice can no longer be sent is a thread opened and never closed — DERIVED on read (`isPermanentlyUnclosed`), never stored, which is why no third writer is needed. That deadline is the EARLIER of two clocks (#1153): the tombstone ageing out (`prunedAt + WITHDRAWN_TTL_S`, so the roster and this verdict cannot drift) and the `alerted:new:` marker expiring (`startedAt + 7d`), after which the alert build skips the tombstone even while it still exists — so a provider that withdraws late is judged by the marker, not the roster. Holds are deliberately NOT rows: `withdrawalHold` re-evaluates every 5 min, so a held notice is a STATE, not an event, and one row per evaluation would turn a bounded log into a per-cycle write; a hold that never clears simply leaves the row un-announced. Both writers are first-write-wins, and a read failure ABORTS the write rather than starting from `[]` (an empty start would republish the month and destroy the history the key exists to keep). Capped at 200 rows/month. Read via `GET /api/admin/withdrawals?month=YYYY-MM&months=1-24` (X-Admin-Key; read-ONLY — nothing an operator could edit here would be anything but a falsified history), which 502s when every month in the range is unreadable rather than answering zero, and answers `ok:false`+`partial:true` when only part of it was. An unreadable month is PERMANENT (every writer refuses to start from `[]`), so it needs a by-hand KV repair — `unreadableMonths`/`malformedByMonth` name which key. KV and not WAE (#518/#548): withdrawals are single digits per MONTH, not traffic-proportional, and the question asked is "show me the rows", not "aggregate a rate" — the same volatile→durable promotion as `growth-series.ts` (#986) |

| `alerted:recovered:{svcId}` | `"1"` | 2h | ~2 | Recovery alert dedup |
| `recovered:{svcId}:{incId}` | `{ resolvedAt, incidentTitle, duration }` JSON | 2h (`RESOLVED_TTL_S`) | ~1 per resolved incident **per affected service** | Independent recovery marker (powers the Recently Resolved banner without AI analysis; only its EXISTENCE is read — `/api/status` + `/api/status/cached` — the payload is forensics). **#1003 — written by `markIncidentResolved` (`recovery-mark.ts`) from BOTH cron resolution paths.** It previously lived only in the `alerted:recovered:` status-edge block, which the code itself calls "rarely-firing … only fires in the incident-less gap", while a normal incident ends via `alerted:res:` — so the banner (and, via the paired `resolvedAt` stamp below, the Analyze modal's + is-down's predicted-vs-actual verdict) effectively never appeared. Only TERMINAL incidents (`resolved`/`monitoring`) are marked; a merged alert marks every incident it collapsed |
| `alerted:probe-spike:{svcId}` | `"1"` | 1h | ~2 | Probe RTT spike alert dedup (early detection) |
| `alerted:source-dead:{svcId}` | `"1"` | 7d | ~0-2 | #689 — dedup for the distinct **"status source inactive"** operator alert. Written on the rising edge (a service's status-page API returned a 4xx → `sourceDead`, e.g. Character.AI's Statuspage deactivated → 401 "page inactive"), so the operator gets ONE accurate "source inactive" embed (not a misleading "degraded" — the service is shown operational+stale, excluded from rankings). Deleted on the falling edge (source responds again) along with a green "source recovered" note. `shouldAlertSourceDead` drives the decision. **#800** — for a `statusSourceDeactivated` service (a KNOWN, acknowledged, long-running deactivation, e.g. Character.AI's 401 page), the rising-edge "Inactive" SEND is suppressed (`shouldSuppressSourceDeadAlert`) but this marker is still written, so the weekly re-alert stops while a RECOVERY is still detected + notified; the #500 persistent-failure daily warning is likewise skipped for these ids |
| `alerted:flap:{svcId}:{normalizedTitle}` | `"1"` | 1h | ~5-20 | BetterStack auto-recovery flap suppression (#283) — 60-min window per service + title. Written on the `alerted:res:` fire of the first flap; checked on next cron cycle to drop both down + resolved halves of subsequent identical flaps. Opt-in via `ServiceConfig.flapSuppression: true` (fireworks left this group in #1198 — see the `holdShortIncidents` row below). Tier-1 (`claude`/`openai`/`gemini`) never suppressed as defense-in-depth. **#1224 — this read is age-gated with the two markers above** (`markerReadPlan(...).alertable`): `isFlapSuppressible` bounds on the incident's RUN time, so an old SHORT resolved flap still qualified and the read fired every cycle forever — measured 2026-08-17 it was 29 reads/run, ALL 29 for incidents past the 24h bound, i.e. the loop's largest remaining read at ~8.4k/day. Safe by the same argument as the roster read: the suppression only subtracts from an alert build that already dropped those incidents by age, and this key is written only on an `alerted:res:` that actually SENT, which the build caps at the same bound |
| `pending:degraded:{svcId}` | `"1"` | 10min | ~5 | Anti-flapping: 2-cycle consecutive detection |
| `pending:new:{incId}` | first-seen epoch ms (write-once / get-or-set; #835 — was `"1"`) | 30min (#835 — was 10min; must outlast the ~2-cycle window) | ~0-5 | First-seen confirmation gate (#633/#792/#835) — stamped with the first-sighting time when a NEW incident is HELD, via `shouldHoldNewIncident`. **Two writers:** (a) #633 — a flap-shaped incident (`isFlapNotice`: "— down/recovered" title + impact **not `major`**; #564/#565 maps a BetterStack monitor flap to `minor`/null, so the gate excludes only `major`, not all non-null impact) on a `flapSuppression` service; (b) #792 — ANY non-`major`/`critical` incident (`isShortIncidentHoldable`, no title shape required) on a `holdShortIncidents` service (langfuse — frequent short `minor` ingestion blips that backdate resolution → New+Resolved double-alert; **mistral #929** — Instatus/Nuxt auto-monitor `"○○ API Degraded"` minor flaps that self-resolve then get pruned → phantom "New Incident"; **fireworks #1198** — migrated off BetterStack to incident.io, whose per-model `"Service Degradation for …"` titles (8-41min observed 2026-08-02) carry no "— down/recovered" suffix for `isFlapNotice` to match, so it holds on real incident.io `impact` instead). **#835**: held until first-seen ≥ `FLAP_HOLD_MS` (~9min ≈ 2 `*/5` cycles), not just one — a flap that lingered just past one cycle then resolved still double-alerted (Modal "Storage degraded" 1m). A blip that self-recovers inside the window fires neither New nor Resolved (the `alertedNewMap.has` guard). Mirrors `pending:degraded` on the new-incident path. **#1224 — the cron skips this read for a RESOLVED incident**, where the value is provably unused (`shouldHoldNewIncident` returns false on `status === 'resolved'` before it consults `firstSeenMs`, and the only other consumer is the stamp inside that same branch). Its own 30-min TTL is NOT part of that decision: **the TTL runs from the first SIGHT, not from `startedAt`**, so an ongoing long-running incident has a LIVE marker no matter how old it is, and skipping that read would pin `firstSeenMs` at `null` → held every cycle forever (AI analysis never refreshed, and the marker re-stamped every cycle instead of once per TTL). The skip value is `null` — "no marker", i.e. first sight — never the `'0'` KV-read-error sentinel, which parses to `firstSeenMs = 0` and would claim a marker had existed |
| `pending:ai:{incId}` | first-seen epoch ms (write-once / get-or-set) | 30min (`PENDING_NEW_TTL_S`; must outlast the `AI_HOLD_MS`≈10min window) | ~0-5 | #882 new-incident **AI-hold** window marker. Stamped when an out-of-`NEVER_AI_HELD` (#1148) `alerted:new:` alert is HELD because its inline AI analysis overran (`shouldHoldForAiAnalysis`) — the send loop `continue`s before the send, and a later cron cycle releases the alert WITH the AI section once `refreshOrReanalyze` has backfilled `ai:analysis`. Bounded: past `AI_HOLD_MS` the gate fail-opens (ships AI-less). Deleted best-effort on release. **Distinct** from `pending:new:` (which holds a *phantom* short/flap alert) — this holds a *real* alert for AI completeness; the two markers never clobber. A `NEVER_AI_HELD` service is never held, so no marker is written for one |

Feeds the MTTD framing + reused by #677 as the AWS/Bedrock incident-start anchor. **#679** — the per-incident "detection lead" (faster-than-official) surfacing + the `detection:lead:{date}`/`:monthly`/`:diag` accumulators were REMOVED (the lead was structurally null — status-page polling is always later than the official publish; #464 already retired the framing). This key itself is KEPT |

The headline figure for "degradations status pages never report" (#464). Classified by `classifyDegradation` against the cached `services:latest` snapshot |

| `reddit:seen:{postId}` | `"1"` | 24h | ~5400/day worst case (225/hour × 24 — #820 round 2 — every keyword-matching outage-mode post gets marked, not just the first 5; real volume is far lower, both because most fetched posts don't match `matchesKeywords` and because the ~85% 429 rate on the fetch itself caps how many subreddits return posts at all) | Reddit post dedup (hourly scan) |
| `reddit:source-dead` | `{reason:'block'\|'partial'\|'streak'\|'throttled', at: epoch ms}` JSON | 26h (survives to the next daily-summary read; self-expires if the cron stops) | ~0-24/day (re-put each hourly run while unhealthy) | #820 observability — written when the hourly scan found NO ok response and at least one 401/403 (`block`), some ok alongside at least one 401/403 (`partial`), a streak of fully-unreachable runs (all-transient OR all-429, see below) crossed the limit (`streak`), or some ok alongside at least one 429 with no 401/403 present (`throttled` — immediate, since real evidence of life is in hand). `throttled` is split from `block`/`streak` because it's a materially different, usually self-healing condition (empirically ~85% of requests 429 against Reddit's rate limit on the shared Cloudflare egress-IP pool, REGARDLESS of this Worker's own request pacing) — but a ZERO-ok throttled run does NOT take the immediate `throttled` path (round 1 shipped this as a bug: it collapsed "partial coverage" and "total blackout" into the same quiet marker and reset the escalation streak, so a genuine sustained outage could never alarm). Zero-ok throttled runs instead accumulate via the same streak counter transient failures use, surfacing as plain `streak` (still an alarm) only once sustained — round 2 first shipped this escalated case as its OWN reason (`throttled-streak`), but round 3 found that broke `markRedditSourceDead`'s `at`-preservation whenever a streak's failure flavor flipped between runs (re-stamping the marker's start time on every flip, understating a genuinely long outage's duration); one terminal `streak` reason avoids that, and its daily-summary message names rate-limiting as a possible cause instead of assuming a broken egress. Makes "403 → 0 posts" surface as a **Reddit source DOWN** warning in the daily summary instead of reading as a quiet day. Deleted (only when present) once a run is fully ok |
| `reddit:transient-streak` | consecutive-all-transient-runs count (integer string) | 26h (self-expiring) | ~0-24/day | #820 — counts runs where NO target answered ok and none returned a block status (a throw, a timeout, or any non-block HTTP error such as 5xx/404). One such run proves nothing, so it must not fabricate a marker; at the streak limit (3 → ~3h hourly) it escalates to `reddit:source-dead`. Deleted (only when present) on any run that saw an ok or a block. A KV read failure here counts as already-escalated — a counter that cannot accumulate would otherwise disable the escalation silently |
| `reddit:promote:last` | `{postId, subreddit, sentAt: ISO8601}` JSON | none (permanent, overwritten) | ~0-3/hour | #1202 — the only durable trace that a `📢 Reddit … [🎯 PROMOTE]` alert has actually fired (the #1182 engagement block leaves no KV trace at all, by design). **Fail-closed rolling windows** (#1256) — `probe:24h` and `latency:24h` are the only two keys written by a read-modify-write that REPLACES the whole value, so a read that fails or returns something unusable must not be read as "no history": doing so overwrote up to 7 days (2016 slots × every `PROBE_TARGETS` entry) with a single snapshot. Both writers now skip the slot instead, via the shared `parseSnapshotWindow` in `worker/src/utils.ts` — `null` means present-but-unusable (skip), `[]` means absent (bootstrap). Four stored states took the destructive path before the guard: a `kv.get()` throw, `{}`, `{"snapshots":null}`, and `''`.

Two consequences for anyone reading these keys or their derivatives: **a stalled window looks like a quiet cron**, because the key simply stops growing — the probe skip logs at `console.error` and the latency skip at `console.warn` (throttled to one line per 10 min, since that writer runs once per inbound request); and **a value that stays unusable stalls writes until the key's own TTL expires**, so clearing it is a manual step. Counting these skips is deferred to #1257.

**KV write budget** (Workers Paid / Standard plan): 1,000,000 writes/month included (~33,333/day); overage billed at $0.50 per additional 1M. Current estimated usage: ~845-958 writes/day + changelog (~3/day) + changelog last-fetch markers (~72/day, 3 sources × 24 hourly cron, #274, #733 dropped Copilot) + weekly briefing (~1/week) + vitals (1 per visit) + platform status (~1/cycle when changed) + recovery markers (~2-5/day) ≈ **~3% of monthly inclusion**. Existing throttling constants (e.g., `KV_WRITE_INTERVAL_MS = 600_000`) are retained for cost hygiene even though the hard free-tier limit no longer applies.

**A throttle is not a hard limit — the ~3% above is what says which.** Without that figure beside them the constants read as a ceiling. **Lengthening a TTL costs no extra writes** — the write cadence sets them, the TTL does not — so that question is bounded by value size and total storage, not by this budget. (Adding a `*/5` key is a different matter: that is ~288 writes/day on its own.)
