# KV Key Schema (STATUS_CACHE namespace)

> Extracted from CLAUDE.md to keep the auto-loaded project file lean. CLAUDE.md links here; this is the canonical reference.

| Key Pattern | Value | TTL | Writes/Day | Purpose |
|---|---|---|---|---|
| `services:latest` | `{ services, upstreamFeeds, cachedAt }` JSON (shape MUST match `cache-refresh.ts` `writeStatusCache`) | 5min | ~288 + a few | Real-time status cache (every monitored service — `SERVICES`). Written by the throttled `/api/status` `cacheWrite` (10-min) **and** by two event-driven edge refreshes that bypass the throttle (`cache-refresh.ts`, CACHE_KEY-only, never the daily counters): the **cron** on each status-change edge (#488) — covers the no-live-traffic case; and the **live `/api/status` handler** on a poll whose status differs from the cached snapshot (#1057, `refreshStatusCacheOnLiveEdge`) — so OG/SEO previews (`/api/status/cached` readers) flip on the live poll, *ahead of* the Discord alert instead of in lockstep with the cron. Both edges are rare (incident start/recovery) and self-silencing (next read sees the fresh snapshot), so negligible vs. the budget |
| `daily:{YYYY-MM-DD}` | `{ [svcId]: { ok, total, officialUptime, weightedOutageSec } }` JSON | 2d | ~288 | Daily uptime counters. `ok` increments via `countsAsUptimeOk` (#733): `operational` → up, `down` → down, `degraded` → down **only** when a major/critical unresolved incident backs it (minor/partial-scope or no-incident degraded counts as up, mirroring official rolling-uptime weighting). Feeds /api/uptime + the AIWatch Score's uptime component. `officialUptime` = the status-page rolling-30d snapshot (#586); the **weekly Stability Trend** uses it for the **previous-week** value (#733) — the current week comes from the LIVE `services:latest` `uptime30d` (gated on `isUnreliableUptime` so no-official-uptime/stale services like Bedrock/Azure/Deepgram are excluded — a live gate, because their historical `officialUptime` snapshots are intermittently non-null pre-#713 residue). Compares official figures, not the served-status `ok/total` (noise for incident-only/probeless services). **#1017** — `weightedOutageSec` (nullable) is that UTC day's weighted outage seconds (`ServiceStatus.todayWeightedOutageSec`), populated for all 5 "official" sources (Statuspage/incident.io/Instatus×2/Flashduty/OnlineOrNot) — the latter 4 via a second `weightedDowntimeSeconds` call (see `uptime-interval.ts`), Statuspage via its own last-published-day-bucket read (not the interval sweep-line); absent for Better Stack (`platform_avg`, a different weighting scheme, #1110) and no-uptime sources. Rides this same key's existing write (+0 new KV writes) — the durable per-day input `uptime-archive.ts` reads back from `history:{date}` to reconstruct a calendar window a provider status-page migration blanked (#1004) |
| `history:{YYYY-MM-DD}` | Same as daily | 90d | 1 | Archived yesterday's counters. **#1017** — this is the actual archive `restoreArchivedCalendar` (`uptime-archive.ts`) reads: for a service whose `uptimeWindowDays` is present (the disclosed "migration reset the live window" signal), it reads back up to `calendarDays − uptimeWindowDays` of these entries to fill the resulting `dailyImpact` gap, classified from `weightedOutageSec` (see `uptime-archive.ts`'s `classifyArchivedDay` thresholds). Gated so the extra reads are paid only by a flagged-short service, never on the common full-window path |
| `latency:24h` | `{ snapshots: [{ t, data }] }` JSON | 25h | ~48 | 30-min latency snapshots (max 48) |
| `probe:24h` | `{ snapshots: [{ t, data }] }` JSON | 7d | ~288 | 5-min health check probe results (max 2016, one entry per `PROBE_TARGETS` target) |
| `probe:daily:{YYYY-MM-DD}` | `{ [svcId]: { p50, p75, p95, min, max, count, spikes } }` JSON | 90d | 1 | Daily probe RTT summary for monthly reports |
| `probe:summaries` | `[svcId, ProbeSummary][]` JSON | 80min | ~48 | Cron-cached 7-day probe summaries (p50, p95, cvCombined, validDays); refreshed every 30min via in-memory slot guard, TTL covers up to 2 missed 30-min refresh cycles |
| `alerted:new:{incId}` | `JSON.stringify(svcIds)` (e.g. `["codex","chatgpt"]`); legacy `"1"` auto-migrated | 7d | ~5 | Incident alert dedup — now the **per-service roster** already alerted for the incident (#545). A service that JOINS a multi-service incident after the first alert fired (e.g. ChatGPT joining a Codex incident after OpenAI renamed the title) is alerted only if NOT in this set, then merged in. Read via `parseAlertedRoster` (legacy `"1"` → seed with the currently-matching service, no re-alert storm on deploy). The cron's dedup loop bypasses the key-exists skip for `alerted:new:` (per-service dedup already happened in `buildIncidentAlerts`); a failed roster write is logged loudly since it would re-fire the alert next cycle |
| `alerted:res:{incId}` | `"1"` | 7d | ~2 | Resolved incident alert dedup |
| `feed:firstseen:{incId}` | ISO timestamp | 7d | ~5 | #750 — AIWatch's first-detected time for the incident, written ONCE (get-or-set, first write wins → stable) alongside the `alerted:new:` roster. The `/feed` handler reads it as the **active item's `pubDate`** so a provider-backdated `startedAt` (BetterStack flap / #633-held incident surfacing hours late) can't make Slack /feed treat the outage post as "already past" and skip it (Discord push is unaffected). Absent → rss.ts falls back to `startedAt`. **#748** — the daily summary also READS these markers (`countNewFeedItems`: list + count those first-seen in the last 24h) to show "· N new items" beside the poll volume |
| `feed:active-emitted:{incId}` | ISO timestamp | 7d | ~5 | #793 — written by the `/feed` handler the first time an incident's ACTIVE item is actually SERVED in a feed response (i.e. NOT held by the #759 AI-hold, via the shared `isActiveItemHeld` predicate), get-or-set, scoped to the services the polled feed actually carries. On resolution the handler reads it: a resolved incident WITHOUT this marker had its outage never announced, so `buildRssFeed` suppresses the lone "Resolved" item (prevents a Slack **orphan resolution** — "Resolved · 19m" with no prior outage post — for a short blip whose entire active window fell between reader polls). Absent on a clean miss → suppress; a KV read THROW fails open (emit the resolved). Sibling of the Discord half #792 |
| `alerted:wd:{incId}` | `"1"` | 7d | ~0 | #1106 — **withdrawal** alert dedup, the third terminal alert kind beside `alerted:res:`. Fires when a provider DELETES an announced incident from its status page instead of resolving it; a deleted incident can never re-enter the live list with `status === 'resolved'`, so `buildIncidentAlerts`' resolved branch is structurally unreachable for it and the 🔴 New alert would otherwise never be closed on any channel. Written by the ordinary post-send `keysToWrite` path (no special casing), so the standard key-exists skip in the cron dedup loop is what prevents a re-fire while the tombstone lives. Emitted ONLY when `alerted:new:{incId}` is still present — a withdrawal we never announced must produce no orphan notice (the Discord twin of #793's rule) |
| `incidents:withdrawn` | `WithdrawnIncident[]` JSON (`{svcId, incId, title, startedAt, prunedAt}`) | key 7d / entries 6d (#1153) | ~0 | #1106 — **tombstones** for incidents the #975 phantom prune deleted, i.e. incidents the provider removed upstream. The prune is the last moment we hold the title + start time, so `accumulateIncidentsOnlyIfChanged` diffs `incidentIds` before/after (`diffPrunedIncidents` — keeps `prunePhantomIncidents` pure) and records them here AFTER the accumulator write lands (a tombstone for an unpersisted prune would re-announce next cycle). This roster is the ONLY material both withdrawal emitters have: the Discord alert and the RSS `:withdrawn` item render from it, because the incident no longer exists in any live list. Deliberately ONE roster key, not one key per incident: the feed renderer must ENUMERATE tombstones rather than look up a known id, and KV `list` is eventually consistent + adds a request-path round trip. Merge is first-write-wins per `(svcId, incId)` so `prunedAt` never moves (it is the RSS item's `pubDate` — a moving value would drift the pubDate after the item was served and churn the #860 ETag), and age is filtered on **read** as well as write: every write refreshes the KEY's TTL, so with a trickle of new tombstones an entry would otherwise outlive its own window. **The key deliberately outlives the entry window by a day** (7d vs 6d) — if they expired together, the ordinary single-tombstone case would evict the key at the same instant the entry aged out, so the "expired without ever notifying" warning (the only signal that a thread was never closed) could fire only in the minority case where a later write had refreshed the key. **#1153 — the entry window was 48h, but `withdrawalHold` withholds a notice until the PROVIDER resolves the incident the withdrawn one duplicated, on the provider's clock, so a slow provider (11h+ in `monitoring` with its own indicator green) could outlast 48h and lose the notice.** Widened to 6d — chosen to sit strictly under the `alerted:new:` 7d marker `buildWithdrawalAlerts` gates on, past which the notice is structurally impossible anyway. Because that key TTL is frozen at write time and `appendWithdrawn` (the prune) is the only writer, a tombstone already in KV keeps its old, shorter key life; the cron therefore re-puts the roster VERBATIM once an hour while an entry is pending (`refreshWithdrawnKey` — raw re-read, not the read-filtered snapshot, so it never clobbers a concurrent append or compacts a skipped entry). Hard-capped at 50 (eviction is logged — the oldest entries are the ones most likely still waiting on a gate). Read is fail-CLOSED: an unreadable, corrupt, or malformed-element value reads as `[]` → emit nothing, so a roster blip can never FABRICATE a withdrawal notice (the per-element check also matters because a malformed entry would throw in `sanitize()` inside the unguarded cron alert build). Note the two EMITTER gates do not share that direction — Discord fails closed, RSS fails open per #793. The TTL is not the re-fire guard — `alerted:wd:{incId}` and the feed guid are |
| `incidents:withdrawn:log:{YYYY-MM}` | `WithdrawalLogEntry[]` JSON (`{svcId, incId, title, startedAt, prunedAt, announcedAt?}`) | **none (durable)** | ~0 | #1106 Part 5 — the DURABLE record that a withdrawal happened, and whether its ⚪ closing notice went out. Every other trace is short-lived by design (`incidents:withdrawn` 6d, `alerted:wd:` 7d, `alert:feed:recent` 2h, Workers Logs ~3d) and the accumulator row is gone by definition — its prune is what starts all of this — so past a week nothing could answer *"did the ⚪ path ever fire?"*. That matters because #1106's exit condition is a production OBSERVATION that cannot be scheduled (it needs a provider to delete an announced incident), so a `verify-after` date would fire on an absence: the instrumentation IS the deliverable. Two write points only — the prune (`recordWithdrawalsPruned`, beside the tombstone write) records the row with `announcedAt` ABSENT, and the cron stamps it AFTER the ⚪ Discord send and GATED on that send's result (`markWithdrawalsAnnounced`, which checks the current AND previous month because a 6d tombstone can cross a boundary). The gate matters: `sendDiscordAlert` returns `false` rather than throwing, and the `alerted:wd:` dedup key is written before the send, so a rejected send never retries — stamping before it would record "the thread was closed" for a notice nobody received. A row still lacking `announcedAt` once the notice can no longer be sent is a thread opened and never closed — DERIVED on read (`isPermanentlyUnclosed`), never stored, which is why no third writer is needed. That deadline is the EARLIER of two clocks (#1153): the tombstone ageing out (`prunedAt + WITHDRAWN_TTL_S`, so the roster and this verdict cannot drift) and the `alerted:new:` marker expiring (`startedAt + 7d`), after which the alert build skips the tombstone even while it still exists — so a provider that withdraws late is judged by the marker, not the roster. Holds are deliberately NOT rows: `withdrawalHold` re-evaluates every 5 min, so a held notice is a STATE, not an event, and one row per evaluation would turn a bounded log into a per-cycle write; a hold that never clears simply leaves the row un-announced. Both writers are first-write-wins, and a read failure ABORTS the write rather than starting from `[]` (an empty start would republish the month and destroy the history the key exists to keep). Capped at 200 rows/month. Read via `GET /api/admin/withdrawals?month=YYYY-MM&months=1-24` (X-Admin-Key; read-ONLY — nothing an operator could edit here would be anything but a falsified history), which 502s when every month in the range is unreadable rather than answering zero, and answers `ok:false`+`partial:true` when only part of it was. An unreadable month is PERMANENT (every writer refuses to start from `[]`), so it needs a by-hand KV repair — `unreadableMonths`/`malformedByMonth` name which key. KV and not WAE (#518/#548): withdrawals are single digits per MONTH, not traffic-proportional, and the question asked is "show me the rows", not "aggregate a rate" — the same volatile→durable promotion as `growth-series.ts` (#986) |

| `alerted:source-dead:{svcId}` | `"1"` | 7d | ~0-2 | #689 — dedup for the distinct **"status source inactive"** operator alert. Written on the rising edge (a service's status-page API returned a 4xx → `sourceDead`, e.g. Character.AI's Statuspage deactivated → 401 "page inactive"), so the operator gets ONE accurate "source inactive" embed (not a misleading "degraded" — the service is shown operational+stale, excluded from rankings). Deleted on the falling edge (source responds again) along with a green "source recovered" note. `shouldAlertSourceDead` drives the decision. **#800** — for a `statusSourceDeactivated` service (a KNOWN, acknowledged, long-running deactivation, e.g. Character.AI's 401 page), the rising-edge "Inactive" SEND is suppressed (`shouldSuppressSourceDeadAlert`) but this marker is still written, so the weekly re-alert stops while a RECOVERY is still detected + notified; the #500 persistent-failure daily warning is likewise skipped for these ids |

| `pending:new:{incId}` | first-seen epoch ms (write-once / get-or-set; #835 — was `"1"`) | 30min (#835 — was 10min; must outlast the ~2-cycle window) | ~0-5 | First-seen confirmation gate (#633/#792/#835) — stamped with the first-sighting time when a NEW incident is HELD, via `shouldHoldNewIncident`. **Two writers:** (a) #633 — a flap-shaped incident (`isFlapNotice`: "— down/recovered" title + impact **not `major`**; #564/#565 maps a BetterStack monitor flap to `minor`/null, so the gate excludes only `major`, not all non-null impact) on a `flapSuppression` service (together/fireworks/huggingface/modal/luma); (b) #792 — ANY non-`major`/`critical` incident (`isShortIncidentHoldable`, no title shape required) on a `holdShortIncidents` service (langfuse — frequent short `minor` ingestion blips that backdate resolution → New+Resolved double-alert; **mistral #929** — Instatus/Nuxt auto-monitor `"○○ API Degraded"` minor flaps that self-resolve then get pruned → phantom "New Incident"). **#835**: held until first-seen ≥ `FLAP_HOLD_MS` (~9min ≈ 2 `*/5` cycles), not just one — a flap that lingered just past one cycle then resolved still double-alerted (Modal "Storage degraded" 1m). A blip that self-recovers inside the window fires neither New nor Resolved (the `alertedNewMap.has` guard). Mirrors `pending:degraded` on the new-incident path |
| `pending:ai:{incId}` | first-seen epoch ms (write-once / get-or-set) | 30min (`PENDING_NEW_TTL_S`; must outlast the `AI_HOLD_MS`≈10min window) | ~0-5 | #882 new-incident **AI-hold** window marker. Bounded: past `AI_HOLD_MS` the gate fail-opens (ships AI-less). Deleted best-effort on release. **Distinct** from `pending:new:` (which holds a *phantom* short/flap alert) — this holds a *real* alert for AI completeness; the two markers never clobber. A `NEVER_AI_HELD` service is never held, so no marker is written for one |

| `ai:analysis:{svcId}:{incId}` | `AIAnalysisResult` JSON | 1h (active) / 2h (resolved, `RESOLVED_TTL_S`) | ~6 per incident (the `resolvedAt` stamp at resolution is #1003's — it previously never happened on the normal path) | Hybrid AI analysis result — Gemma 4 primary + Sonnet fallback (TTL refreshed while active; on recovery, `resolvedAt` added instead of deleting — kept 2h for "Recently Resolved" UI). `model` field tracks which model produced the analysis. `sticky: true` (#299) marks a manual operator override — cron skips re-analysis and only refreshes TTL; cleared naturally when incident resolves. **`firstEstimatedRecoveryHours` (#1003)** — the FIRST estimate ever made for the incident, stamped on every write by **`putAnalysis`, the single chokepoint through which all `ai:analysis:` writes must go** (CI-enforced: `first-estimate-write-paths.test.ts` fails on any analysis-key write outside it), and read back from the durable `ai:first-est:` key below. | `ai:first-est:{svcId}:{incId}` | recovery-estimate upper bound in hours, as a string (e.g. `"4"`) | 30d (`FIRST_ESTIMATE_TTL_S`) | **≤1 per service+incident** (write-once / get-or-set; a grouped incident pins one key per affected service, via the sibling-copy path) | #1003 — the durable **scoring baseline**: the first recovery estimate made for an incident, the value its resolution is graded against. Separate from `ai:analysis:` because that key is deliberately allowed to **lapse** mid-incident (once an analysis is 2h+ old and the per-cron re-analysis cap is exhausted, `refreshOrReanalyze` stops refreshing its TTL so a later cycle re-analyzes from scratch) — a broad outage can starve one long incident for the ~12 cycles that takes, and the replacement analysis would otherwise install ITS hours-in estimate as "the first" one, re-running the bug on exactly the long incidents where scoring matters most. `pinFirstEstimate` reads it before every fresh-result write and only writes when absent, so no re-analysis can move it. | `ai:usage:{YYYY-MM-DD}` | `{ calls, success, failed, timedOut?, timedOutBy?, held?, heldReleasedWithAi?, heldReleasedWithoutAi?, gemma?, sonnet?, gemmaAttempts?, sonnetAttempts? }` JSON | **30d** (#995, was 2d) | ~5, +2 per held alert (#1080: one `held`, one release — same key, so no new keys) | Daily AI analysis usage counter (includes re-analysis, model breakdown). Manual `/api/admin/analyze` (#299) calls also increment here so the daily summary attributes them. **#995** — retention raised 2d→30d (`AI_USAGE_TTL_S`) so a rolling trend survives: the **weekly briefing** reads the week's keys → `summarizeAiUsageTrend` → a `🤖 AI Analysis (7d): … · N timed out · M failed` line, so "is the Gemma timeout/fallback rate rising?" is answerable from data (previously the counters evaporated after 48h, and the `timedOut` metric is itself new so had no baseline). **#955** — `gemma`/`sonnet` count SUCCESSES; the `*Attempts` fields count calls actually issued, because a fallback that is always reached and never succeeds was previously indistinguishable from one that is never reached (both read `sonnet: 0`) — which is how a retired Sonnet model id 404'd for weeks unnoticed. `timedOut` splits budget/timeout aborts out of `failed`. `calls` is now booked from the returned attempt on EVERY path — including the throw path, which previously incremented neither `calls` nor `failed` (the old `usage.calls++` sat after the `await` inside the `try`, so a thrown error vanished from the ledger).
