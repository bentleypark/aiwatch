# KV Key Schema (STATUS_CACHE namespace)

> Extracted from CLAUDE.md to keep the auto-loaded project file lean. CLAUDE.md links here; this is the canonical reference.

| Key Pattern | Value | TTL | Writes/Day | Purpose |
|---|---|---|---|---|
| `services:latest` | `{ services, cachedAt }` JSON | 5min | ~288 + a few | Real-time status cache (all 37 services). Written by the throttled `/api/status` `cacheWrite` (10-min) **and** by the cron on each status-change edge (#488, `cache-refresh.ts`) so OG/SEO previews (`/api/status/cached` readers) reflect an incident within one cron cycle — the edge writes are rare (incident start/recovery), negligible vs. the budget |
| `daily:{YYYY-MM-DD}` | `{ [svcId]: { ok, total, officialUptime } }` JSON | 2d | ~288 | Daily uptime counters. `ok` increments via `countsAsUptimeOk` (#733): `operational` → up, `down` → down, `degraded` → down **only** when a major/critical unresolved incident backs it (minor/partial-scope or no-incident degraded counts as up, mirroring official rolling-uptime weighting). Feeds /api/uptime + the AIWatch Score's uptime component. `officialUptime` = the status-page rolling-30d snapshot (#586); the **weekly Stability Trend** uses it for the **previous-week** value (#733) — the current week comes from the LIVE `services:latest` `uptime30d` (gated on `isUnreliableUptime` so no-official-uptime/stale services like Bedrock/Azure/Deepgram are excluded — a live gate, because their historical `officialUptime` snapshots are intermittently non-null pre-#713 residue). Compares official figures, not the served-status `ok/total` (noise for incident-only/probeless services) |
| `history:{YYYY-MM-DD}` | Same as daily | 90d | 1 | Archived yesterday's counters |
| `latency:24h` | `{ snapshots: [{ t, data }] }` JSON | 25h | ~48 | 30-min latency snapshots (max 48) |
| `probe:24h` | `{ snapshots: [{ t, data }] }` JSON | 7d | ~288 | 5-min health check probe results (max 2016, 24 API services) |
| `probe:daily:{YYYY-MM-DD}` | `{ [svcId]: { p50, p75, p95, min, max, count, spikes } }` JSON | 90d | 1 | Daily probe RTT summary for monthly reports |
| `probe:summaries` | `[svcId, ProbeSummary][]` JSON | 80min | ~48 | Cron-cached 7-day probe summaries (p50, p95, cvCombined, validDays); refreshed every 30min via in-memory slot guard, TTL covers up to 2 missed 30-min refresh cycles |
| `alerted:new:{incId}` | `JSON.stringify(svcIds)` (e.g. `["codex","chatgpt"]`); legacy `"1"` auto-migrated | 7d | ~5 | Incident alert dedup — now the **per-service roster** already alerted for the incident (#545). A service that JOINS a multi-service incident after the first alert fired (e.g. ChatGPT joining a Codex incident after OpenAI renamed the title) is alerted only if NOT in this set, then merged in. Read via `parseAlertedRoster` (legacy `"1"` → seed with the currently-matching service, no re-alert storm on deploy). The cron's dedup loop bypasses the key-exists skip for `alerted:new:` (per-service dedup already happened in `buildIncidentAlerts`); a failed roster write is logged loudly since it would re-fire the alert next cycle |
| `alerted:res:{incId}` | `"1"` | 7d | ~2 | Resolved incident alert dedup |
| `feed:firstseen:{incId}` | ISO timestamp | 7d | ~5 | #750 — AIWatch's first-detected time for the incident, written ONCE (get-or-set, first write wins → stable) alongside the `alerted:new:` roster. The `/feed` handler reads it as the **active item's `pubDate`** so a provider-backdated `startedAt` (BetterStack flap / #633-held incident surfacing hours late) can't make Slack /feed treat the outage post as "already past" and skip it (Discord push is unaffected). Absent → rss.ts falls back to `startedAt`. **#748** — the daily summary also READS these markers (`countNewFeedItems`: list + count those first-seen in the last 24h) to show "· N new items" beside the poll volume |
| `feed:active-emitted:{incId}` | ISO timestamp | 7d | ~5 | #793 — written by the `/feed` handler the first time an incident's ACTIVE item is actually SERVED in a feed response (i.e. NOT held by the #759 AI-hold, via the shared `isActiveItemHeld` predicate), get-or-set, scoped to the services the polled feed actually carries. On resolution the handler reads it: a resolved incident WITHOUT this marker had its outage never announced, so `buildRssFeed` suppresses the lone "Resolved" item (prevents a Slack **orphan resolution** — "Resolved · 19m" with no prior outage post — for a short blip whose entire active window fell between reader polls). Absent on a clean miss → suppress; a KV read THROW fails open (emit the resolved). Sibling of the Discord half #792 |
| `alerted:down:{svcId}` | ISO timestamp | 2h | ~2 | Service down alert dedup + recovery duration |
| `alerted:degraded:{svcId}` | ISO timestamp | 2h | ~2 | Service degraded alert dedup |
| `alerted:recovered:{svcId}` | `"1"` | 2h | ~2 | Recovery alert dedup |
| `recovered:{svcId}:{incId}` | `{ resolvedAt, incidentTitle, duration }` JSON | 2h | ~2 | Independent recovery marker (powers Recently Resolved banner without AI analysis) |
| `alerted:probe-spike:{svcId}` | `"1"` | 1h | ~2 | Probe RTT spike alert dedup (early detection) |
| `alerted:source-dead:{svcId}` | `"1"` | 7d | ~0-2 | #689 — dedup for the distinct **"status source inactive"** operator alert. Written on the rising edge (a service's status-page API returned a 4xx → `sourceDead`, e.g. Character.AI's Statuspage deactivated → 401 "page inactive"), so the operator gets ONE accurate "source inactive" embed (not a misleading "degraded" — the service is shown operational+stale, excluded from rankings). Deleted on the falling edge (source responds again) along with a green "source recovered" note. `shouldAlertSourceDead` drives the decision. **#800** — for a `statusSourceDeactivated` service (a KNOWN, acknowledged, long-running deactivation, e.g. Character.AI's 401 page), the rising-edge "Inactive" SEND is suppressed (`shouldSuppressSourceDeadAlert`) but this marker is still written, so the weekly re-alert stops while a RECOVERY is still detected + notified; the #500 persistent-failure daily warning is likewise skipped for these ids |
| `alerted:flap:{svcId}:{normalizedTitle}` | `"1"` | 1h | ~5-20 | BetterStack auto-recovery flap suppression (#283) — 60-min window per service + title. Written on the `alerted:res:` fire of the first flap; checked on next cron cycle to drop both down + resolved halves of subsequent identical flaps. Opt-in via `ServiceConfig.flapSuppression: true`; applies to `together`, `fireworks`, `huggingface`, `modal`, `luma`. Tier-1 (`claude`/`openai`/`gemini`) never suppressed as defense-in-depth |
| `pending:degraded:{svcId}` | `"1"` | 10min | ~5 | Anti-flapping: 2-cycle consecutive detection |
| `pending:new:{incId}` | first-seen epoch ms (write-once / get-or-set; #835 — was `"1"`) | 30min (#835 — was 10min; must outlast the ~2-cycle window) | ~0-5 | First-seen confirmation gate (#633/#792/#835) — stamped with the first-sighting time when a NEW incident is HELD, via `shouldHoldNewIncident`. **Two writers:** (a) #633 — a flap-shaped incident (`isFlapNotice`: "— down/recovered" title + impact **not `major`**; #564/#565 maps a BetterStack monitor flap to `minor`/null, so the gate excludes only `major`, not all non-null impact) on a `flapSuppression` service (together/fireworks/huggingface/modal/luma); (b) #792 — ANY non-`major`/`critical` incident (`isShortIncidentHoldable`, no title shape required) on a `holdShortIncidents` service (langfuse — frequent short `minor` ingestion blips that backdate resolution → New+Resolved double-alert). **#835**: held until first-seen ≥ `FLAP_HOLD_MS` (~9min ≈ 2 `*/5` cycles), not just one — a flap that lingered just past one cycle then resolved still double-alerted (Modal "Storage degraded" 1m). A blip that self-recovers inside the window fires neither New nor Resolved (the `alertedNewMap.has` guard). Mirrors `pending:degraded` on the new-incident path |

**KV write budget** (Workers Paid / Standard plan): 1,000,000 writes/month included (~33,333/day); overage billed at $0.50 per additional 1M. Current estimated usage: ~845-958 writes/day + changelog (~3/day) + changelog last-fetch markers (~72/day, 3 sources × 24 hourly cron, #274, #733 dropped Copilot) + weekly briefing (~1/week) + vitals (1 per visit) + platform status (~1/cycle when changed) + recovery markers (~2-5/day) ≈ **~3% of monthly inclusion**. Existing throttling constants (e.g., `KV_WRITE_INTERVAL_MS = 600_000`) are retained for cost hygiene even though the hard free-tier limit no longer applies.
